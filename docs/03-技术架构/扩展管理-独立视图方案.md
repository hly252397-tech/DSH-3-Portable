# 扩展管理独立视图方案（草案 · 待评审）

> 需求：`扩展管理` 组内的项目（专家 / 技能 / 插件 / 连接器 / 定时任务）不再套在「设置」弹窗里显示，改为独立整页；同时「设置」里不再重复出现这些项。
> 状态：仅调研，未开工。核验日期 2026-09-06，基准为便携版内置 `@deepseek-ai/dsh 0.1.2-alpha.3` 实包。

---

## 1. 已核验现状

**导航项全部只是"打开设置弹窗并选中某项"的快捷方式。** `@michengai/dsh-codex-ui` 里 `selectSection`、`selectPluginSection`、`selectExternalSection` 三个函数最终都调 `openSettingsSection(...)`（`dist/client.js:3634-3648`、`:3910-3920`）。也就是说"独立视图"这一形态目前只有连接器具备。

| 项目 | 归属包 | 注册的槽位 | 有独立视图？ |
|---|---|---|---|
| 专家 | `@michengai/dsh-agency-agents` | `settings.section`、`conversation.input.left` | ❌ |
| 技能 | `@michengai/dsh-skills-manager` | `settings.section` | ❌ |
| 插件 | `dshmarket` | `settings.section`、`settings.plugin.item`、`shell.overlay` | ❌（其 `shell.overlay` 只是安装后的 toast，`client/client.js:9943-9947`） |
| 连接器 | `dsh-mcp-connector` | `shell.overlay` + `sidebar.footer.action` | ✅ 已是目标形态 |
| 定时任务 | `@michengai/dsh-automation` | 未核验（本次只确认导航落点是设置弹窗） | 待确认 |

**连接器就是我们要的范式**（`lib/client.js:1125-1156`）：建一个可见性 store，`shell.overlay` 挂整页组件、`sidebar.footer.action` 挂导航按钮，两者共享同一 store。

## 2. 官方机制支撑

- `shell.overlay` 由官方 `dsh-client-ui-layout` 在 AppFrame 的独立 overlay 层渲染，槽声明为 `kind: "list"`、`scope: "root"`（`lib/client.js:259-263`、`:454-457`）。多插件可各自注入。
- **跨槽复用组件是官方设计允许的**：槽组件可声明 `__renders`，runner 会向其注入 `renderSlot`（见 `dsh-cordis-client-runner` 的 `PropsRenderSlots` 类型声明）。这是唯一不碰 DOM 的复用途径。
- 未找到"隐藏/过滤他人 `settings.section` 条目"的官方 API（`dsh-client-ui-settings` 里的 `hidden` 是 Schemastery 字段 meta，不是导航可见性）。

## 3. 三条路径

| | A 上游改造 | B 我们做视图宿主 | C DOM 搬运 |
|---|---|---|---|
| 做法 | 每个包自己加 `shell.overlay` + 导航，设置里只留配置项 | 我们注入一个 `shell.overlay` + 标签条，用 `renderSlot("settings.section")` 渲染各包组件 | 程序化打开设置→选中 section→把面板 DOM 节点搬进我们的容器 |
| 覆盖范围 | 需逐包改（3~4 个包） | 一处改动覆盖全部（若可行） | 一处改动覆盖全部 |
| 是否碰三方源码 | 是（PR 或 fork） | 否 | 否 |
| 风险 | 上游节奏不可控 | 中：`renderSlot` 能否只渲染指定 entry 未验证 | 高：依赖三方 DOM 结构，版本升级即碎；弹窗焦点陷阱与卸载时机冲突；React 事件委托受容器位置约束 |
| 「设置里不显示」 | ✅ 天然达成（包自己不再注入管理页） | ❌ 仍需隐藏他人槽位，无官方钩子 | ❌ 同左 |
| 可逆性 | 好 | 好 | 差 |

## 4. 关键结论

需求的两半指向不同答案：**"独立显示" 可以我们侧解决（B），"设置里不显示" 实质上只有 A 能干净做到** —— 因为那些设置条目是各包自己注入的，我们既无官方过滤钩子，就只能靠 CSS/DOM 硬藏，属于脆弱补丁，与"专业级"验收标准不符。

## 5. 建议的推进顺序

1. **Spike（约半天，只读验证，不产出交付物）**：确认 `renderSlot("settings.section")` 能否按 entry id 只渲染指定组件。可行 → B 是主路径；不可行 → 只剩 A 或 C。
2. **无论 spike 结果如何，"设置里不显示" 走 A**：向 `dshmarket`、`dsh-skills-manager`、`dsh-agency-agents` 各提一个 PR，把管理界面注册到 `shell.overlay`，设置里只保留配置字段。这是官方规范做法，也符合知识库第 6 节"能力三层拆分"与第 10 节"新行为归属表"。
3. 过渡期表现：导航指向独立视图，设置里暂时仍保留一份入口（不隐藏）。等上游 PR 合入后再去掉。
