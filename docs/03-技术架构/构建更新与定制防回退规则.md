# 构建、独立更新与定制防回退规则

日期：2026-09-30。适用于 DSH 桌面壳、Harness 内核、本地插件、前端定制、便携数据布局及其构建、发布、更新和清理流程。

用户决定：以后任何功能更新或修改，都必须防止已经接受的功能、界面和配置恢复成原版。本规则是 DSH 手册中的长期执行约束，不代表本轮代码已经部署或生产验收通过。

当前状态（2026-10-01续做）：保护清单、校验模块、构建缓存、独立运行时发布契约和家园准备事务已经进入源码；当前统一类型检查、正式全量1066 pass/0 fail/26 skip、真实ZIP本地消费及手册Profile/Loader隔离验证通过。手册四份新来源尚未完成接受登记和离线同步，源码保护门禁正确报告SOURCE_DRIFT，不能继续使用旧候选来验收新源码。本轮用户仅授权本地功能/测试，暂不远程发布；安全内核激活方案仍待选择，现役保持不变。新组合的完整构建、冷启动、真实UI与数据恢复仍需完成，不得写“已自动更新”或“已生效”。本轮过程见 [实施与证据记录](../01-当前工作/20260930-构建独立更新与定制保护.md)。

## 1. 每个功能必须有持久归属

开发或修复前，先记录问题、复现证据、影响链和本次写入边界。与其他会话并行时先核对工作树、活动槽、任务和更新事务，不代替其他会话批准漂移。

每个接受的功能都必须登记以下内容；仅存在于现役 `Data` 文件里，不算完成源码归档。

| 登记项 | 必须回答的问题 |
|---|---|
| 稳定能力 ID | 这个功能叫什么、由谁维护？使用稳定 ID，不随版本或盘符改变。 |
| 持久源码 | 哪些 `src/`、`plugins/` 或 `customizations/` 文件是唯一维护入口？哪些文件是生成物？ |
| 构建和安装链 | 源码如何生成客户端/宿主载荷、如何进入安装包、如何进入实际 Profile 或桌面槽？ |
| 运行载荷 | 实际加载的包、导出、patch、客户端、样式及资源是什么？指向哪个本地 link 和活动家园？ |
| 配置与数据 | 配置、令牌、会话、数据库、用户文件分别保存在什么 `Data` 相对路径？是否需要迁移？ |
| 依赖与兼容 | 关联哪个官方接口、包版本和其他功能？跨版本授权由哪个经过审阅的契约提供？ |
| 验收与回滚 | 正向测试、故障反例、实际运行验证和恢复步骤在哪里？失败时保留什么证据？ |

插件新增、修改和下线同时遵守官方插件规范、稳定 patch ID 及“模型可见即已记录”规则。界面和侧栏还必须遵守 [UI 定制维护契约](UI定制维护契约.md)，不能用本规则替换既有 UI baseline。

清单入口为 `customizations/preservation.json`。新增定制必须更新能力 ID、必需插件和适用的源码映射，补测试和审阅记录；不得只编辑活动家园。桌面混合源码允许合法升级，不能要求 `src/main.ts` 等文件的整体哈希永远不变；其行为必须通过稳定能力契约和真实回归验证保留。

## 2. 保护实际加载，不只保护源码快照

`src/customization-preservation.ts` 提供以下门禁：

- `verifyCustomizationSources` 检查已经登记的持久源码与接受记录是否一致。
- `captureCustomizationState` 从明确的活动 Profile 捕获本地包声明、实际 link 目标、启用状态、包语义、稳定 patch 和运行文件，不能以“最新目录”代替实际加载位置。
- `verifyCustomizationPreserved` / `assertCustomizationPreserved` 检查候选是否仍完整保留该快照；丢失、禁用、链接指向旧家园、载荷替换、未批准新增/变更均阻止切换。
- `checkPreservationManifest` 检查远程桌面候选的 `resources/preservation.json`。缺少清单、能力 ID、必需插件或已接受来源记录时拒绝；较大的 revision 不代表自动批准哈希变化。

当前固定来源清单覆盖已归档的定制源组；动态快照还覆盖活动 Profile 中全部本地 link 包，不仅是固定来源清单里的包。现役核查捕获到 17 个本地插件，这只是当轮事实，不是以后可以漏登记新增插件的上限。

快照只记录相对路径和稳定载荷哈希，不收集令牌、会话内容、日志、缓存或 `ui-probe.json` 等动态输出。已经嵌入生成客户端的原始构建图片可显式标为 `runtime: false`，但原始源码仍需保护，不能以此排除实际运行资源。

合法变更必须先说明差异、归档源码、审阅影响、补正反向测试与真实验收，再形成接受记录。若使用显式 `approvedSnapshot`，只能批准完整且已经审阅的精确新快照；不得由更新器发现差异后自动生成批准，不得仅改哈希、删能力 ID 或删测试放行。

## 3. 数据留在便携盘，运行时保持不可变

应用可控的配置、会话、用户文件、缓存和环境路径继续由便携路径模块重定向到便携盘 `Data`。更新替换不可变桌面/运行时槽，不覆盖整份 `Data`，不重新初始化用户工作区、令牌或会话。

桌面槽位于 `Data/Updates/Desktop/slots/`；独立 Harness 槽位于 `Data/Runtime/Harness/slots/`。源码装配缓存属于 `Data/Development/build-cache/`，不是用户数据，也不是现役槽。

内核涉及数据格式和插件兼容，家园准备模块提供以下事务约束。它是已经进入源码的离线准备能力，不代表本轮允许真实自动切换：

1. 持有更新互斥并通过任务空闲门禁，真正停止旧 DSH 服务和相关 Profile 监听器后，才能传入 `sourceStopped: true`。参数不是绕过检查的占位值。
2. `prepareHarnessHome` 仅复制所传活动 Profile 对应的 `Data` 内 home。不能按最新 receipt 选来源，不能复用旧目标家园，否则会话可能倒退。
3. 每个事务使用全新 generation；内核二进制留在 canonical 槽，不再复制一整份运行时到 generation。
4. 内部链接改指新 home，本地插件 junction 改指新 home 内 `local`，官方运行时链接改指候选。未知外部链接、缺包或不明确的归属必须失败，不能静默跳过、摘掉 bundle 或删除用户文件。
5. 逐个启用 bundle 读取实际安装包的 peers，以候选运行时提供的 semver 检查；不能回落开发机的 semver。既有授权只认精确 `插件名@安装版本` 和目标内核版本。发布授权只能列本次目标版本，不能批量把旧授权改成新版本，不能修改 peer 范围。内核授权也不是任意第三方库依赖的豁免。
6. 完整复制、定制保留和兼容校验都成功后，最后才发布 schema 2 家园绑定：`runtimeVersion`、`generation`、相对根的 `runtimeRelativePath`。
7. 绑定失败关闭。回滚先停止候选服务，再恢复自己发布的绑定和旧运行时；发现绑定已属于其他事务时拒绝覆盖。失败现场留在本事务 `.incomplete-*` 目录，不删广域数据。

启动遇到未提交的事务，应同时选择旧运行时和对应旧家园，不允许“二进制回滚、数据仍用新版”。绑定损坏或配套不完整时不能假装成功并静默回落另一份旧数据。数据兼容组声明本身也不能代替真实迁移和回滚测试。

## 4. 桌面壳与内核独立发布、独立更新

复用已有组件 A/B 和健康提交机制，不另造第三套指针或并行更新状态机。

桌面更新只接受配置的便携项目发布源，保留定制、Data 和完整离线启动配套；官方原版桌面包不能当成便携定制更新直接覆盖。预发布是否参与发现由通道控制，不能只以版本字符串大小推断产品或制品身份。

内核由发布端预先装配完整成品，用户端只下载、校验、暂存和启动验证，不能在后台偷偷运行 pnpm/install 或长时间源码构建。缺少合格成品时明确提示阻止原因并保留现役；开发环境的显式装配路径不能成为生产更新失败后的隐式回退。

当前源码契约与发布入口：

- `src/harness-release-catalog.ts`：配置发布源、官方精确版本/标签、npm integrity、commit、Node/平台、包大小、包 SHA256、内容 SHA256、运行时指纹及精确 Profile 兼容授权。
- `src/harness-prebuilt-update.ts`：限制下载来源与重定向，检查空间，验证缓存和压缩包，拒绝路径穿越/链接/特殊文件，验证完整运行时后发布不可变槽。
- `.github/workflows/harness-runtime-release.yml` 和 `scripts/create-harness-release-contract.mjs`：制作独立内核包与配套契约。兼容授权必须经过审阅并提交；已发布版本的制品不得覆盖。
- `.github/workflows/desktop-package.yml`：便携桌面发布门禁与定制清单装入资源。

本地有这些文件不等于远程已有新 Release。发布源正确、制品可下载、精确版本/签名或来源证明匹配以及离线启动，均须真实核实并留证。

自动检查和下载不得打断正在运行或待审批的任务。桌面 `auto-on-exit` 只暂存候选，由用户下一次正常退出后的启动器/下次启动激活；不得后台自动重启。用户主动选择立即更新/重启是另外一次明确操作。

内核本轮必须在成品获取和无业务 shadow 验证后持久标为 blocked，在停止旧服务、发布家园绑定和修改活动指针之前阻止激活，不提供不安全放行开关。独立内核成品下载与静态家园准备能力已经实现，安全自动激活和真实验收尚未完成。

原因：实际官方类型尚未提供已查证的统一入站暂停接口。新 Profile 即使被 GUI 遮罩，MCP、IM 和定时任务仍可能投递业务；“界面不能点击”和短暂空闲并不证明入站已冻结。在能够阻止所有任务入口、证明队列清空并验证中断恢复之前，不能进行带真实业务的观察后回滚，也不能把 online 的冒烟写成数据安全验收。后续完成真实 barrier 或经过验证的正常退出/启动激活机制，才可重新审阅并解除阻止。

## 5. 构建提速靠验证复用，不靠跳过质量

`Build-DSH-Portable.ps1` 与 `src/build-cache.ts` / `scripts/prepare-runtime.ts` 负责依赖和装配复用。缓存命中要求输入指纹一致、成功记录完整、全部交付文件大小和 SHA256 一致；丢文件、多文件、损坏、工具版本或依赖输入变化必须失效。失败或中断的半成品不得提交为成功缓存。

构建使用互斥、已校验工具链和阶段计时；同一轮避免重复 install、重复 tsc 和重复打包。构建提速不改变全量类型、测试、官方基线、定制和 UI 门禁要求。`SkipTests` 等诊断入口不能用来制作已验收发布。

`Build-UI-Only.ps1` 也属于发布入口，不能成为旁路：共用构建锁，等长/同时间戳仍比较内容 SHA256；缺成功 receipt、dist 或资源保护清单时失败关闭。`-Force` 仅兼容旧调用参数，不能跳过保护，`SkipStage` 也必须在复制前检查。git dirty 和 mtime 仅辅助提示：即使工作区未提交，只要精确源码与成功 receipt 一致，也可做合法素材更新；反之源码已提交也不能让旧 asar 通过。

构建输入凭据由 `scripts/lib/build-input-receipt.mjs` 与对应 CLI 管理。先封存源码、清单、锁、工具和正式测试输入，tsc 后、测试前另封存编译产物；打包、暂存及最终提交重新比较。成功 receipt 绑定真实 asar、完整 dist 及不可变应用输出，不从失败/中断的产物补发成功记录。仅明确映射的可替换 assets 允许 UI-only 更新；嵌入 exe/安装器的图标等仍属完整构建输入。全量发布脚本拒绝 `-SkipTests`。

新本地候选必须在槽清单和指针携带 `local-build-receipt-v1` / transactionId。先持久化 intent、定制快照及 D 锁内真正的 prior pointer；全部比较完成后，在同一操作锁内形成事务 receipt 副本及 finalized proof。缺凭据、复制后完整载荷变化、同槽文件增删/篡改或身份不一致，均不得从 pending、直接健康提交或扫描恢复进入 current。失败撤销仅 CAS 自己的未激活事务，不回写锁外旧快照；最终校验前不回收被替换候选。current/previous/pending 对应的证明文件也是运行配套，不能提前清理。

源码缓存、装配产物、下载文件与活动槽必须分开识别。缓存缺失时重建缓存，不删现役“修缓存”。清理只能处理明确归属且未被 current/previous/pending、家园绑定、运行进程或未完成事务引用的对象；不能仅按时间、文件夹名字或“看起来是旧版”删除。

禁止构建/回收清理与候选激活并行。启动器持有构建/装配租约到健康提交或完整回退结束，不能仅探测一次后放开；Desktop 指针操作锁只在短 CAS 区使用，不能跨候选启动与健康等待持有而造成提交死锁。先等待既有回收清理完成，再做冷启动验收；不得把 I/O 竞争造成的启动失败误判成候选 UI 缺陷。receipt 的最终完整哈希校验耗时需要实测，不提前称其为短操作。

清理器继承安全环境，不清空删除守卫、不换 shell 绕过拒绝。有限失败后保留 `.failed` 诊断；普通已隔离诊断不是活跃队列，不能永久挡住候选。活跃队列/心跳、链接路径或枚举失败仍阻止激活。每轮 worker 重新核对回收根真实路径，不能将启动时检查当作以后任意删除的授权。

## 6. 每次变更与发布的必过门禁

按影响链确定共同修改范围，不按文件名猜。检查用户入口、前端事件/反馈、后端处理、公共 schema、安装/迁移链、调用方和失败恢复；若共享契约改变，所有消费者要一起适配并测试。无关业务功能和他人未提交修改保持原样。

开发和构建必须包含：官方兼容双基线核对；门禁 Node 下 tsc；新测试及受影响定点测试；使用新鲜编译产物的全量测试；源码保护检查；UI baseline；实际活动 Profile 定制快照与候选校验。官方或 UI 基线漂移先调查，禁止直接修改哈希通过。

远程候选还必须包含：发布源和精确产品身份、下载/解包完整性、资源保护清单、完整离线工具链/运行时、候选 Profile 组合、readiness、任务隔离、健康观察、事务恢复和回滚证据。只有所有适用门禁通过才能提交 current/健康状态。

哈希只能证明“这些文件一致”，不能证明“按钮能点击”或“功能已经加载”。UI 变更必须在实际启动链和活动 URL 上验证：新/旧会话、全屏/窄窗、缩放、左右卡片/面板、相关按钮与设置入口。插件必须通过实际 Profile + Loader 组合确认，不以手工挂载单测代替。

保护范围要正确：开发区尚未批准的改动阻止新候选，不应停掉健康现役的普通启动。切换发布通道后，旧 available/缓存结果不能作为自动下载或安装许可；限流保留的旧显示信息也不是新许可。busy/已准备/待激活事务不能悄悄换通道；跨进程已下载候选必须有安全重新核对路径，不能因为许可失效而永久卡死，且重核对不删除制品、家园或活动指针。

## 7. 必须有能拦住回退的负向测试

除正向成功外，至少覆盖适用的反例：

- 已安装插件保留名字，但客户端被原版替换；包声明消失、启用状态变成禁用、link 指向旧家园或外部目录。
- 远程桌面缺少保护清单、稳定能力 ID 或源码记录；revision 升高但未批准的哈希变化。
- 预构建包来源错误、契约错版本/Node、SHA 或内容指纹不符、路径穿越、未知链接、缺少官方包或 semver。
- peers 不满足且无目标版本精确授权；授权错插件版本、错误目标或批量迁移旧授权；缺失第三方必需 peer。
- 待审批/运行任务存在时不切换；缺少已查证的全入口暂停能力时即使 GUI 遮罩、短暂空闲也不激活；未停止源服务不能复制；旧目标家园有过时会话时也不能复用。
- 准备过程中 binding 被另一事务修改、发布后 rollback 试图覆盖其他事务；断电/异常退出留下 pending 时同时恢复旧运行时与旧家园。
- 构建输入变化、产物损坏/缺失/增加、中断或锁竞争时不能错误命中缓存或回收活动槽。

使用隔离 fixture 故障注入可以验证门禁是否阻止，但真正用户报告的 UI 故障还需旧制品复现与新制品真实对照。没有做的测试列为“未验”，不得改断言或删除失败测试伪装通过。

## 8. 交付记录与完成判定

每轮交付记录至少包含目标、源码/运行链、直接与间接影响、已验/未验、精确制品/活动家园、失败尝试、回滚步骤和下一步。输出状态区分“源码已实现”“门禁通过”“候选已就绪”“已激活”“已验收”。

只有候选实际启动、健康观察和真实组合验证完成，且原数据/接受定制未回退、回滚路径有证据，才能标记该更新闭环完成。未部署时必须明确说未部署；需要用户重启时说明影响并另行确认，不把一次旧授权重复当作无限重启许可。

本轮尚待完成：手册精确来源接受与活动离线同步、新组合完整构建和桌面实测、用户选定的内核安全激活范围、适用的启动中断/数据恢复验证及实际热构建耗时对照。当前全量源码测试已通过不代表发布门禁全通过；远程成品发布本轮明确排除。具体结果追加实施记录；本规则不提前填写PASS或改写历史证据。

补充安全边界：正常退出、exit0、进程离场和稳定Data哈希不能单独证明所有已接受消息已持久化。拟议的离线切换只能在验证源写入者离场后复制已持久Data，并在新业务开放前持久记录联合事务边界；边界后失败必须保留新家园并恢复新组合，禁止自动退回旧会话。该方案仍待用户选择和代码/真实故障测试，不能据此解除当前激活阻止。若要承诺所有已接受待办不丢，另须验证拒绝新入站、持久队列、producer drain和flush成功ACK，不以标志参数替代。
