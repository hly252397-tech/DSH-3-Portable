# 06 数据流 — 会话与插件交互

> 审计日期：2026-09，以实机产物为证据。官方运行时根：`App\dsh-runtime\node_modules\@deepseek-ai\dsh\node_modules\@deepseek-ai\`（下称 `<RT>`，全部 0.1.2-alpha.3，只读）。

---

## 1. 数据流①：用户发送消息 → 会话 → 模型调用 → 工具执行 → 回复渲染

**链路（每步均有类型/实现证据）：**

1. **入口与身份**：浏览器加载 DSH Web（`window.__DSH_BOOT__` 引导图由 `dsh-client-modules` Node 半侧合成——`<RT>\dsh-client-modules\lib\types\index.d.ts` 模块注释："scans the host Loader's entries for packages declaring `dsh.client`, composes the `window.__DSH_BOOT__` entry graph … serves one-or-more-plugin combo scripts"）。用户消息经 Web 前端进入宿主 HTTP 面（`dsh-host-webserver` 提供的 `ctx.webServer`，`<RT>\dsh-host-webserver\lib\types\index.d.ts`），由 `dsh-api-session-controller` / `dsh-api-gateway` 的控制器路由到目标 agent 会话。
2. **会话持久化（仅追加日志）**：会话事件写入 `ctx.sessions: SessionStore`（`<RT>\dsh-session\lib\types\index.d.ts`）；铁律 1"模型可见即已记录"由 `dsh-invariants` 保障（`dsh-base` 的 `invariant.d.ts` 导出 `base-bundle-invariant`，`apply: (ctx) => Promise<() => void>`）。
3. **Agent 循环**：`ctx.agentLoop: AgentLoop`（`<RT>\dsh-agent-loop\lib\types\index.d.ts`）驱动轮次流水线；请求发出前经过 `agent/request` 等 Cordis 事件（各包 Events 合并块），**模型调用**被 `llm/stream` waterfall 包裹（`<RT>\dsh-llm\lib\types\index.d.ts`："Waterfall around every streaming model call (retry, replay, routing) … call `next()` to reach the resolved adapter's stream"），最终落到已注册适配器（`dsh-llm-deepseek` / `dsh-llm-pi-ai`）。
4. **工具执行**：模型返回 tool-call 后由 `ctx.tools: ToolRuntime` 把关执行（`<RT>\dsh-tools\lib\types\index.d.ts` Events 注释："Allow, deny, or ask before dispatch. `next()` delegates to allow…" —— `tools/pre-execute` 类 waterfall 先过策略再放行；执行结果持久化为 `tool/call`/`tool/result` 会话事件）。
5. **回复渲染**：会话事件经投影（`<RT>\dsh-session-projection\lib\types\index.d.ts`，配缓存 `dsh-session-projection-cache`）折叠为界面表面（`dsh-session\lib\types\surface.d.ts` 的 fold/surface 函数族），再由 client-ui 渲染器消费：`<RT>\dsh-client-ui-renderer`、`dsh-client-ui-conversation\lib\types\client\contract\records.d.ts`（`ContextMessageNode` 等视图契约）。流式增量通过 host→browser 通道推给已连接页面。

**观察正确姿势**（铁律 10）：监听 `session/event` 后检查 `event.type`（`turn/*`、`step/*`、`tool/call`…，见 `dsh-session\lib\types\known-event-types.d.ts` 的 `KNOWN_SESSION_EVENT_TYPES`），不能 `ctx.on('tool/call', …)`。

## 2. 数据流②：插件客户端 UI 注入（slots.inject → 浏览器渲染）

真实本仓证据链：

1. **声明双端同构包**：插件 `package.json` 写 `dsh.client: {platform:'web', inject:[…client 包…]}` + `exports['./client']`。例：`Data\DSH\profiles\web\local\dsh-better-sidebar\package.json`（`dsh.client.inject` 列出 `dsh-client-ui-slots`、`dsh-client-locale`、`dsh-client-ui-conversation`、`dsh-client-modules`）。
2. **宿主发现**：`dsh-client-modules` Node 半侧扫描 Loader 条目，把声明的 client 包编入引导图，并"contributes the registration facade … to the webserver's index injection table"（同文件模块注释）；index 注入表由 `dsh-host-webserver\lib\types\injections.d.ts` 的 `IndexInjection` 定义，webserver 的 Events 注释："Collect the structured index injection table. Emitted on every index render and every worker boot-payload request"。
3. **浏览器半侧注册槽位**：client 模块拿到的 client ctx 有 `ctx.slots.inject(path, factory)`。运行时自用例：`<RT>\dsh-client-ui-cordis\lib\client.js`（`ctx.slots.inject("sidebar.footer.action", …)`、`ctx.slots.inject("tool.call.toolview", …)`）；本地插件实例：`local\dsh-black-hole\lib\client.js`：
   ```js
   ctx.slots.inject('conversation.input.dock', () => ctx.slots.register({
     name: 'conversation.input.dock', id: 'black-hole-capture', order: -80,
     locale: NS, inject: () => ({ ctx }) }, (props) => h('div', …)))
   ```
4. **渲染**：布局组件在对应槽位路径聚合所有注入面（`<RT>\dsh-client-ui-slots` 的 `InjectFace`/`HostObservable` 契约，被 `dsh-client-ui-cordis\lib\types\client\*.d.ts` 引用），注册经 `ctx.effect` 归还的撤销函数随 Fiber 处置自动回收，浏览器端由 cordis-client-runner 的 client timer/registry 支撑（`<RT>\dsh-cordis-client-runner\lib\types\client\index.d.ts`）。

注意：本仓 `dsh-restart-button` 是**不走 slots** 的反例——其 `lib/client.js` 直接 `window.__ModuleLoader__.load({id, factory})` 后操作 DOM 并调用外壳 `window.dshDesktopShell.action`，说明 client 模块系统只要求加载进引导图，UI 手段自选。

## 3. 数据流③：插件宿主半侧注册 → 实际被调用

两条实证：

- **webServer HTTP 路由**：`@michengai/dsh-im-connect`（`Data\DSH\profiles\web\node_modules\@michengai\dsh-im-connect\lib\*.js`）调用 `host.webServer.register({…})` 注册 prefix 路由；本地插件同样在宿主注册：`local\dsh-work-mode\lib\index.js`、`local\dsh-black-hole\lib\index.js`、`local\dsh-sidebar-spaces\lib\index.js`、`local\dsh-better-sidebar\lib\index.js` 均有 `webServer.register`（grep 实证）。调用链：浏览器/外部客户端 → webServer 绑定端口 → 注册的 handler → 插件宿主逻辑 →（可选）操作 `ctx.sessions`/`ctx.subagents` 等 → HTTP 响应。注销同样由 Fiber 处置自动完成。
- **tools 注册 → 模型调用**：插件在 apply 里 `ctx.tools.register(defineTool({…}))`；下次模型请求时工具清单进入系统提示，模型发起 tool-call → 数据流①第 4 步把关执行。命令形态则不经过模型：`@michengai/dsh-simplify` 实测调用 `ctx.commands.register({…})`，handler 里 `invocation.agent.followup(createUserMessage({…, source:{kind:'plugin', …}}))` 把**模型可见**消息注入当前会话（铁律 1：source 必带插件名）。
- **旁问子任务**：`@michengai/dsh-btw` 实测：`ctx.subagents.start("fork", {…})` + `ctx.extend({fiber: ctx.root.fiber}).tools.guard(createAnswerOnlyGuard(labels))` 只读护栏——独立于主会话轮次的完整小型数据流①。

## 4. host↔client 通信三通道（各自证据与适用场景）

| 通道 | 证据 | 适用场景 |
|---|---|---|
| **connection.rpc** | `ctx.connection: HostConnectionHandle`，`<RT>\dsh-client-connection\lib\types\rpc-host.d.ts`："Host registry and HTTP adapter for generic Connection RPC channels"、"Host Connection service whose channel registrations belong to the caller fiber"；浏览器对端在 client-runtime 内。宿主侧注册 `connection.rpc.handle('/通道名')`（社区八件套通用形态，AGENTS.md 实证表） | 页面↔宿主的**低延迟双向会话内调用**：UI 状态、按需读取宿主服务，随 Fiber 生命周期自动回收 |
| **webServer HTTP** | `ctx.webServer: WebServer`（`<RT>\dsh-host-webserver\lib\types\index.d.ts`）；实调用见 §3（im-connect、work-mode、black-hole、sidebar-spaces、better-sidebar） | **通用 HTTP API**：外部系统接入（IM webhook）、文件/流、跨页面共享资源；需插件自校验请求头，天然可被外部调用方消费 |
| **typert 远端** | 注册表 `ctx.typert`（`<RT>\dsh-typert-registry\lib\types\service.d.ts`；dsh-base patch `id: typert` + `typert-loader`/`typert-gateway` 三行）；协议 `<RT>\dsh-typert-protocol\lib\types\types.d.ts`（Context 合并块）；实例：`@michengai/dsh-agency-agents\cordis.patch.yml` 专门插入 `agency-agents-remote` 行（注释"让 api-gateway 从根服务表发现 agencyAgents Remote 路由"） | **强类型 RPC**：宿主服务以装饰器/远端接口暴露，客户端 `ctx.remote.$mount()` 调用，类型安全随包分发；适合插件对外提供结构化服务 API |

选择原则：页面内即时交互走 connection.rpc；要被浏览器之外的世界调用走 webServer；要跨插件共享强类型服务接口走 typert。三条通道的注册都经 `ctx`，卸载即自动撤销——与铁律 5 一致。

## 5. 小结

- 会话主链路是"HTTP 入口 → SessionStore 仅追加日志 → agentLoop → llm/stream waterfall → tools 把关执行 → session-projection → client-ui 渲染"，每一环都有对应的 .d.ts 或 lib 实现文件可查。
- 插件 UI = 双端同构包 + `dsh.client` 声明 + `slots.inject`；插件能力 = 宿主半侧 tools/commands/webServer/connection/typert 注册，全部随 Fiber 可逆。
- 本仓所有本地插件（restart-button 除外）宿主侧用 webServer、客户端侧用 slots/直调外壳桥，与官方三通道模型吻合。
