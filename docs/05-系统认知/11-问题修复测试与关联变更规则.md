# 11 — DSH 问题修复、测试与关联变更规则

版本：1.0；编写日期：2026-09-27（Asia/Shanghai）。适用于 DSH 桌面、插件、前端、服务、配置、构建与更新问题。

目的：修好用户遇到的问题，同时证明相关功能没有在已测范围内退化。**最小且完整的修复，不等于修改文件最少；有关联不等于全部都要改。** 不承诺任何修复“绝不会影响其他功能”，而是把影响分析、测试证据、未覆盖风险和回退办法交代清楚。

本章是供维护者与模型查阅的工作规则，不授予重启、删除数据、付费调用、发布或跨任务修改权限，不覆盖用户最新要求及上级指令。仅诊断请求不授权实施修复。

## 1. 先明确规则与事实的来源

本文路径均相对便携项目根目录，移盘后从实际根目录解析，不能固定使用旧盘符。

- 开发约束：根目录 `AGENTS.md` 及目标目录适用的下级规则。
- 中大型任务前后检查：`docs/05-系统认知/10-GlobalContextCheck与ImpactReview模板.md`，执行 GCC 12 项、GIR 10 项，不用本文简表替代。
- 前后端与 UI 三项对齐：`docs/01-当前工作/便携版3-变更与答复质量门禁.md` 第 6 节是唯一规则来源；本文只给执行方法，不另建一套验收口径。
- UI 修改：`docs/03-技术架构/UI定制维护契约.md`，包括实际修改和失败尝试的记录要求。
- 事实：当前加载代码、类型声明、配置和实际行为。历史截图、旧测试、旧手册与源码不能代替运行证据；源码和运行制品冲突时先调查，不直接覆盖其中一方。
- 版本、Profile、数据代际、工具与 API 每次现读。手册里的历史版本、路径、测试数量只是当时记录。

## 2. 修复流程与每一步的产物

| 步骤 | 必做动作 | 进入下一步的条件 |
|---|---|---|
| ① 确认范围 | 写清症状、用户预期、授权动作、并发任务与不改区域 | 知道改什么、不改什么，以及是否允许重启/发布 |
| ② 复现与定位 | 在真实入口复现，核实实际加载文件；记录旧版反例与根因 | 有证据区分根因、症状和环境干扰 |
| ③ 关联分析 | 正向追调用，反向找消费者，建立影响矩阵 | 每条关联都有依据、处理方式和测试 |
| ④ 最小完整修复 | 修改正确源码/配置，补失败回归用例，保留兼容与清理逻辑 | diff 未超授权；新发现的范围已重新评估 |
| ⑤ 分层验证 | 定点、契约/组合、相邻功能、适用全测及真实操作 | 各层结论和未测项明确，不用一层替代另一层 |
| ⑥ 受控交付 | 按项目门禁构建，审查候选差异，按授权激活并检查健康 | 实际运行的确是已验证候选，恢复路径可用 |
| ⑦ 记录与交接 | 保存成功/失败证据、修改清单、风险、手册和功能状态 | 报告结论与证据覆盖范围一致 |

纯文档修改可按现有规则豁免 GCC/GIR 与应用构建，但必须说明理由，验证内容、链接、检索和原有文档保护。文档中描述的规则不等于已经实现自动阻断。

## 3. 如何确定根因，而不是看到哪里异常就改哪里

### 3.1 修改前留下问题卡片

至少记录：时间、真实启动入口/URL、桌面与运行时版本、活动槽、Profile/家园绑定、窗口和缩放条件、复现步骤、预期与实际、日志/截图/错误栈位置、复现次数。

先形成可验证的一句话：

> 问题是___；证据是___；下一步是___。

尚未确定根因时明确标为“假设”，并写验证方法。截图只能证明可见现象，不能独自证明按钮事件、接口或状态错误在哪里。

### 3.2 确认改的是实际生效链

追踪“启动器 → 实际进程 → 桌面活动槽 → DSH 运行时/家园 → Profile/Loader → 客户端与服务端文件 → 用户入口”。记录源码到构建制品、制品到实际加载位置的对应关系。

- 区分源码、生成物、归档、旧家园、候选与现役；同名文件不代表同一实例。
- 依赖版本/图标/API 问题先核对活动运行时的声明、导出与实际使用方式；mock 必须符合该版本，不能保留已移除接口来制造通过。
- 检查日志和控制台，同时核对点击是否命中、事件是否触发、请求是否发出、状态是否提交、界面是否展示该状态。
- 调试端口失效、测试夹具不匹配、插件未就绪与业务故障分开记录。等待明确的就绪条件，不用任意加长 sleep、无限重试或吞异常掩盖竞态。

### 3.3 留下旧失败、新成功的对照

同一前置条件、相同操作与断言，旧实现应能复现失败，新实现应通过。自动回归尽可能先红后绿。

无法安全运行旧版时，使用保留的旧日志、隔离夹具或历史制品，说明局限；禁止为复现破坏真实会话或覆盖当前槽。偶发问题记录重复次数、负载/时序和观察时长，一次通过不等于修复。

## 4. 如何判断哪些关联功能必须一起修改

### 4.1 双向追踪，而不只搜索文件名

优先在相关目录用 `rg` 搜索符号、事件名、IPC/RPC/HTTP 路由、工具名、配置键、Schema 字段、CSS/slot 标识，再查看实现和注册关系。搜索无命中不是“没有关联”的证明，还要检查动态注册、反射、配置引用、生成器和运行时 Loader。

沿两条链核实：

1. 正向：用户入口 → 事件/组件 → 状态/服务 → 数据或系统动作 → 成功与失败反馈。
2. 反向：被改服务/数据/公共组件 → 全部消费者 → 菜单、快捷键、通知、弹窗、不同会话/面板和后台任务。

另外检查隐性关系：共享状态与缓存、生命周期挂载/卸载、事件订阅与清理、异步回包顺序、窗口合成与焦点、CSS 作用域、持久化与迁移、便携路径、源码与生成物、版本/代际配对、更新/回滚和权限边界。

### 4.2 关联变更判定表

| 分类 | 判定依据 | 行动 |
|---|---|---|
| **必须联动修改** | 不改消费者就会违反同一契约或状态不变量，例如返回字段变化、共享导航入口失效、保存结构与读取不一致、注册与清理不配对 | 在授权范围内完整修改契约两端、必要生成源/制品和测试；范围扩大时先复核 GCC，重大扩展须询问用户 |
| **只需回归，不先改代码** | 使用了共享能力，但公开契约与预期行为未变 | 列入影响矩阵，测试该入口；只有发现有因果证据的回归才修改 |
| **独立问题，另行处理** | 只是时间上同时出现、同目录或名称相近；根因不同，或需要重构/升级/新增功能 | 单独记录影响与复现，不顺手修；需扩展授权时询问用户 |
| **关系未知** | 动态调用、版本/加载路径不明，或缺少可验证环境 | 标记未确认，补调查；高风险链路未清楚前停止发布，不能写“无影响” |

“一起改”的必要条件：**能指出具体契约/不变量、真实调用证据，以及不联动会发生的错误**。只因“可能相关”不足以扩大修改。

### 4.3 每项关联都进入影响矩阵

| 受影响入口/功能 | 关联证据（文件、符号或运行记录） | 分类与原因 | 计划修改文件 | 回归用例/预期 | 结论与证据 |
|---|---|---|---|---|---|
| 示例：通知打开会话 | 与返回/前进共用会话打开 API | API 已移除，必须适配同一入口 | 桥接源码与测试 | 通知应打开正确会话；失败不得错误标记成功 | 待填，不预写 PASS |
| 示例：浏览器面板 | 同属外壳，导航修复未改变其几何契约 | 只回归 | 无 | 点击、缩放、切换/重载仍正常 | 待填 |

共享组件影响多个入口时可以选代表性组合，但必须说明选择依据和未测组合。用户要求“所有会话”的约束，应覆盖全部实现分支/会话类型及尺寸规则，不能用一个会话截图替代。

## 5. 如何避免影响其他功能

1. 改前保存 `git status`、目标文件原始差异和必要的可恢复快照；未跟踪文件也要保护。记录其他任务正在修改的边界，不能把脏工作区全部当成自己的改动。
2. 列出 Expected Files、Do Not Touch、必须保持的行为及候选允许变化文件。共享文件若发生并发变化，重读最新内容、局部合并并复验；无法安全合并就暂停协调。
3. 优先修复契约与根因，复用现有能力。不夹带重命名、大面积格式化、依赖升级、另一套状态机或无关重构。
4. 默认保持 API、数据格式、配置默认值、权限和用户习惯。确需改变时说明兼容策略、迁移、失败恢复及所有消费者。
5. 异步工作要防止旧回包覆盖新状态；取消、卸载、重载后不得留下监听器、计时器或重复注册；服务迟加载/重加载也要验证。
6. 不对冻结家园、历史版本、官方运行时或 `node_modules` 做机械全盘同步。活动版本和兼容目标分别确定，并保持源码/生成物可追溯。
7. 改后审查实际 diff 与计划差异；交付前再次检查并发变化和候选内容，确认没有覆盖别人的修改，也没有将其夹带发布。
8. 保留原有回滚目标和用户数据；测试使用隔离临时目录/夹具，不拿真实会话做删除测试。不因测试方便重置 Profile、清配置或杀掉所有同名进程。

## 6. 如何测试：每一层证明不同的事情

| 层级 | 核心检查 | 不能据此宣称 |
|---|---|---|
| 静态/类型 | API 是否存在、导入/契约一致、注册/清理成对、构建引用正确 | 用户已能操作 |
| 定点回归 | 根因用例旧失败新通过；正常、边界、异常与取消/时序路径 | 真实宿主一定兼容 |
| 集成/组合 | 实际版本的服务、Profile/Loader、前后端参数与结果、持久化 | 当前桌面已加载候选 |
| 相邻功能 | 影响矩阵中的共享消费者、旧兼容路径与关键用户行为 | 未测模块全无风险 |
| 全量门禁 | 当前规定的全量测试及适用构建，报告 pass/fail/skip | 跳过项通过或实机已验收 |
| 真实应用操作 | 实际启动入口、真实按钮/键盘、业务结果与错误反馈；适用刷新/重载/冷启动 | 用户本人已确认 |
| 交付后复验 | 活动指针/加载文件匹配候选，健康状态和关键链路通过 | 所有第三方模型与设备均兼容 |

### 6.1 必选与按风险选择

- 每个 bug：复现用例、修复用例、至少受影响的失败/边界路径，以及直接消费者回归。
- 导航/状态：正确目标、返回/前进、分支截断、目标失效、打开失败、异步切换与卸载。
- 保存/数据：读取与写入一致、重复提交、拒绝/冲突保留草稿、刷新后持久化、旧数据兼容；迁移用数据副本验证。
- 插件/工具：实际注册与作用域、参数、错误、权限、迟加载与卸载；有模型适配变化再测相关 native/PTC 链，不把模拟模型等同真实厂商验证。
- UI/外壳：窗口还原与最大化（需求含全屏时另测真正全屏）、窄宽尺寸、侧栏/面板开关、页面缩放和相关显示缩放；适用主题、焦点和遮挡。页面缩放与系统 DPI 分开记录。
- 截图只能辅助判断外观，必须结合真实点击后的目标 ID、正文/结果或状态断言。Electron 跨层点击问题在真实桌面测，不用独立网页替代。
- 截图类回归按契约至少重复独立重载；首开/空闲问题增加首次打开、闲置、关闭重开和面板切换。记录每轮条件与次数，不反复尝试直到偶然成功后只保留成功结果。
- 任何不适用项都给理由；缺账号、权限、设备、依赖或付费授权时标“未验证”，不得计入通过。

### 6.2 DSH 的执行入口

先读当前 `AGENTS.md` 与构建清单，核对门禁 Node 版本/哈希。**门禁解释器必须与 `package.json` 的 `config.bundledNodeSha256` 一致**，因此命令一律经 `scripts/gate-node-run.mjs` 转发（它会 re-exec 到哈希命中的那个 Node）：2026-09-29 实测清单已是 `v26.10.0`，而 `Tools/node/node.exe` 停在 `v24.21.0` 不命中清单——裸跑就是在错版运行时上取绿灯。未来入口变化后以当前规范为准：

```powershell
# 在便携项目根目录执行；本章展示命令，不授权自动运行构建或重启。
# 不确定当前该用哪个 Node：node -e "import('./scripts/lib/gate-node.mjs').then(m=>console.log(m.GATE_NODE))"
& '.\Tools\node\node.exe' '.\scripts\gate-node-run.mjs' '.\node_modules\typescript\bin\tsc'
& '.\Tools\node\node.exe' '.\scripts\gate-node-run.mjs' '.\scripts\run-tests.mjs'
```

通过现有隔离测试运行器使用独立临时目录和锁，定点参数按脚本当前实现核对。涉及 `src/` 的改动仍须完成项目要求的完整构建与候选门禁；不能因为定点测试通过就省掉。共享构建/暂存不得与另一任务抢占；重启前确认构建和回收阶段均结束。

### 6.3 测试失败怎样处理

- 产品缺陷：修实现，并加能捕获根因的回归用例。
- 测试契约过时：先用实际版本/API 证明，再修夹具/断言；保留原要保护的用户行为，不能只把期望改成实际输出。
- 环境或并发问题：保留失败日志，修环境隔离/就绪条件，重跑原用例与相关组；不得计作产品已修复。
- 基线漂移：逐文件审查变化归属和语义；合法 UI 变化完成真实验证、记录证据后，才按维护契约追加不可变基线。
- 无关既有失败：列出原始证据、归属和影响；不能删测、加 skip、改哈希或把异常吞掉来全绿，也不能将失败门禁说成通过。若既有失败阻塞项目强制交付门禁，应报告阻塞并请求处理方向。

## 7. 如何交付与恢复

源码修好、构建成功、候选暂存、实际激活、真实验证、用户确认是六个不同状态，分别登记。

- 审查候选与当前版本的文件清单/哈希差异，变化必须能逐项解释。发现源码与现役不一致、混入其他任务或丢失已验修复时，停止激活并重新分析范围。
- 按现有不可变候选与 A/B 流程交付；不原地覆盖活动 App/运行时槽。不在客户端加载代码中安排自动重启/退出。
- 重启/更新可能中断任务时先协调授权，检查事务归属、进行中的构建、回收与其他任务；不能替换他人的 pending 候选。
- 授权激活后核对真实加载位置、健康标记、启动错误和关键功能；失败则按受支持机制回退，保留诊断证据，避免无限重试。
- 应用回滚不等于数据回滚。涉及 Schema/数据迁移时，在变更前准备备份、兼容读取和恢复验证；不得假设换回二进制能恢复已迁移数据。
- 发现无法明确影响范围、数据安全风险、强制门禁失败、非预期制品变化或无有效恢复方案时，停止高风险交付，说明阻塞与所需决定。

特殊收口方案必须有范围复核、完整构建证据、独立候选差异证明与恢复路径，不作为日常手改生成物的许可。源码/运行制品长期分叉应单独治理。

## 8. 本次导航修复给出的实例，而不是永远有效的结论

以下为 2026-09-27 历史案例，详细事实以 `docs/01-当前工作/20260927-导航兼容与三项测试修复.md` 为准：

- 返回/前进失效的根因是桥接依赖旧会话导航 API。真实 rc.2 用 `uiWorkspace.openSession` 与 `retainedBy.mainView`；不仅按钮路径，通知打开也使用同一能力，因此需要联动适配，并测试状态切换的瞬态。
- 侧聊兼容测试把旧家园源码与新运行时混验。正确处理是确认活动版本/家园配对并验证真实导出，不是修改所有历史副本。
- 两处既有 UI 基线变化逐项审核并完成真实空间/浏览器回归后才追加基线，不把登记哈希当成修复本身。
- 完整候选包含其他工作，并可能覆盖现役未回写源码的窗口修复，因此未直接激活；重新分析后采用独立受控候选并证明只有两份同模块文件改变。这个历史例外不意味着可以跳过构建或直接改现役槽。
- 当时全测为 687 通过、0 失败、26 跳过；导航两轮真实操作通过。这不等于 26 个跳过项已验证，也不等于全部功能、厂商模型和用户本人确认通过。
- 隐藏窗口黑图、过早点击、未选中预期会话均记录为失败/不足证据；另见的启动器重复启动问题未混入本次导航修复。

## 9. 每次修复记录模板

复制到当前任务记录；中大型任务同时完成第 1 节引用的 GCC/GIR，不能只填本模板。


## 10. 模型如何找到、使用和维护本规则

手册章节 ID：`notes/dsh-bugfix-testing-impact-rules`。当前手册根目录由实际 DSH home 与插件 `manualDirectory` 配置确定，不假定一定是旧 `Data/DSH/manual`。

存在可用手册工具时，使用当轮真实工具 Schema：

```json
{"operation":"search","query":"问题修复","limit":10}
```

这是 `dsh_manual` 的参数示例；从返回结果取得 ID，再 `read`。读取分页未完时继续读取，禁止用截断正文覆盖全文。工具未暴露时先通过当轮可用的能力发现入口核实，不虚构工具名；有授权文件访问时可读本章或实际 home 下的 Markdown。

维护方式：

1. 仓库本章是已整理的版本化规则；手册 `notes/` 是可编辑工作副本，不是 `generated/` 自动章节。手册笔记默认 draft，不能伪造“已验证”身份或认为模型建议自动成为批准规则。
2. 编辑前读取当前 revision；通过手册编辑通道传 `expectedRevision`，新建用 null。冲突时重新读取合并，禁止覆盖他人修订。使用 `history/restore` 追溯；不直接改元数据或历史。
3. 在正文记录变更理由、证据、日期和适用版本。认可的规则变更再同步回仓库本章与索引；再次发布前读取最新手册 revision，比对并保留后续补充。两份文档不保证自动双向同步。
4. 规则/API/流程改变时更新本章和关联索引，并验证 list/search/read、正文一致性及修订历史。自动来源同步不会覆盖 notes，但也不会自动更新这份工作副本。
5. “存储层可查”“插件已注册”“本轮模型工具可调用”“真实 UI 已打开”分别验收；仅写文件不代表所有模型已自动获知，也不代表已建立自动执行门禁。
