## 二、AI 容易失去大局观的原因（结合本仓库真实情况）

**R-1 构建产物与源码并存，且都不在 git 里（D-30）。** 仓库同时存在源码 `src/`、脚本、`App/resources/**` 装配产物、`Data/` 下真实运行实例（profile、运行时槽、更新槽）。AI 读到 `App/resources/` 里的旧代码或 `Data/DSH/profiles/web/node_modules/` 里的物化拷贝，会误当作"当前真相"改起来——link 迁移前"改 local 源不生效"正是这个认知陷阱的实锤（`docs/03-技术架构/评估-目录链接替代插件双拷贝.md` §痛点与根因）。

**R-2 双基线 + 多 dist-tag，"最新"不等于"可用"。** 实现基线钉**活动运行时槽**（2026-09-26 为 `0.1.7-rc.2`；撰写本节时为 `0.1.2-rc.1`）、审查基线是官方 HEAD、受信清单另有裁决（`docs/03-技术架构/DeepSeek-Harness-官方兼容基线.md` 当前基线表）。AI 天然假设"官方文档=可调 API"，于是会调用内置运行时不存在的新接口；dsh-agency-agents 的 settings-compat 双代桥接说明连社区插件作者都会掉进去。

**R-3 坑只存在于散文式 AGENTS.md，一条坑平均埋没在 1.2 万字里。** 16 条坑无编号无索引，触发条件（"跑 profile 内 pnpm 前""在 Git Bash 调 PowerShell""新写 ps1"）与坑条目之间没有机器可查的映射。长上下文任务里，AI 在第 3 步读过 AGENTS.md，到第 15 步做 profile install 时早已"知道过但想不起来"——2026-09-11 specifier 物化事故（AGENTS.md 坑清单）正是"流程知识没有在触发点出现"的代价。

**R-4 同一事实在 3–4 处文档各说一遍，且会过期不同步。** 例如 0.1.5-rc.2 升级修复同时写在：AGENTS.md 两条坑、兼容基线 2026-09-11 节 5 小条、功能清单 #45b 一大段、I025 迭代总览。**本条在 2026-09-26 被再次实证**：桌面版本同时出现在 `02-当前状态.md`、`01-产品全貌`、`02-代码地图`、`07-功能清单`、`04-迭代路线图`，同一轮审核里各文件的旧值互不相同（`1.0.65+build.8` / `1.0.76` / `v1.0.13`）。**对策不是"记得一起改"，而是把易漂移字段改成指向事实源**（`package.json` / `bundled-plugins.ts` / 槽指针），只在必要处保留数字并标注读数日期。AI 引用了任何一份旧副本都会得出过期结论，且无法判断哪份是权威。

**R-5 双基线 + 认祖式上游同步，历史线性假设失效。** git 历史交替出现上游提交（英文、官方口径）与便携提交（中文、便携口径），`merge -s ours` 让"看 log 判断功能是否保留"不可靠（git `e68d364`、`fbe34a2`）；标签 `v1.0.53` 指向便携发布而非上游同名标签（AGENTS.md 认祖坑）。不了解该决策的 AI 会试图"补上上游内容"或"修复标签冲突"，恰好破坏既定契约。

**R-6 验证环境的四重分裂：`node --test` 绿 ≠ 用户可用 ≠ CI 绿 ≠ 双击可用。** tar 探测（GNU vs bsdtar）、实机 Data 产物（CI ENOENT）、ps1 BOM（PowerShell 5.1）、非 win32 用例（git `1d367b6`）各是一个"测试通过但真实环境失败"的维度。AI 习惯把"全绿"当完成态，而本仓库的完成态定义是四层验证叠加（`docs/03-技术架构/00-桌面启动器架构基线.md` §7）。

**R-7 A/B 槽与"不可变制品"心智模型反直觉。** 直觉是"直接改正在运行的文件最快"；本仓库的正确路径永远是"建候选→验证→切指针→可回滚"。AI 想走捷径（原地安装、绕过退避闸门、在指纹槽补文件）时，每一个都是历史真实事故（D-01、D-06、D-07）。

**R-8 多插件、多本地定制并存，改一处可能波及自愈系统。** profile 有 20 项 bundles、4 个本地 link 插件、npm 社区插件矩阵；改 schemastery 依赖或主题变量会触发 DSH 自愈摘除 bundles、设置页样式回退等链式反应（D-09）。没有"影响面地图"，AI 只见单点不见链条。

**R-9 文档入口与任务路由断裂。** 00-交接入口导航未索引 26 个迭代；`docs/05-系统认知/` 此前为空；排障类任务（为什么启动失败/为什么更新被阻止）在文档树上没有入口，AI 只能靠全文搜索碰运气。

## 三、建议：认知基建补强方案（本阶段只提方案，不改流程文件）

### 3.1 哪些信息可以脚本自动生成

| 可生成物 | 建议脚本 | 数据源 |
|---|---|---|
| 基线快照（内置版本/受信清单/官方 HEAD 漂移状态） | 已有 `scripts/verify-dsh-official-baseline.mjs`，增加 `--json` 落盘到 `docs/03-技术架构/DeepSeek-Harness-官方兼容基线.json` | npm + git |
| 测试→守卫映射表 | 扫描 `test/*.test.ts` 的 describe/注释关键词，生成 `docs/05-系统认知/test-guard-map.json` | test/ |
| 功能清单与 src 文件的一致性校验 | 检查功能清单引用的 `src/*.ts` 是否存在、是否未被登记的新文件 | `docs/00-交接入口/07-功能清单.md` + src/ |
| 插件矩阵快照（profile package.json specifier vs node_modules 实装 vs bundled-plugins 声明） | diff 脚本，输出三者不一致告警（正是 D-09 地雷的探测器） | `Data/DSH/profiles/web/` |
| 槽/指针/状态健康摘要（当前槽、pending 候选、deploymentFailures、events.jsonl 尾部） | 只读脚本，供会话开始时快速建立"机器现在什么状态"的认知 | `Data/Updates/Desktop/`、`Data/Runtime/Harness/` |
| git 状态摘要（上游标签冲突预期、最近认祖点、未发布提交） | 包装 `git log/tag` 的只读脚本 | git |
| ps1 BOM / tar 探测环境自检 | 静态扫描 `*.ps1` 前 3 字节 + `tar --version` 探测结果 | 仓库脚本 |

原则：**状态类**（现在是什么版本、什么在跑、哪里不一致）全部可脚本化；生成物统一落 `docs/05-系统认知/generated/` 并标注生成时间，与人工文档物理分离，避免互相污染。

### 3.2 哪些必须人工维护

- **决策的 why 与否决记录**（07 号文的 Decision/Reason）：机器只能证明"门禁红了"，不能替代"为什么这么裁"（如 0.1.5-alpha.1 除名裁决、rc.1 保留受信的理由）。
- **坑条目的触发条件与守卫位置**：新坑发生后由人归纳"下次在什么动作前必须想起它"，并可结合 07 号文更新对应 D 条目。
- **官方变化的审阅结论**（兼容基线逐日审阅记录）：AGENTS.md 已明确禁止脚本自动接受。
- **三项对齐的真实 UI 验收证据**：截图/实测记录无法自动生成。
- **迭代总览与交接入口的状态叙述**：哪些待办真正阻塞、哪些历史结论作废。

### 3.4 Global Context Check（任务前置 12 项）与 Global Impact Review（任务后 10 项）的固化方案

**落点一：AGENTS.md 新增两节（建议放在「强制流程」章之后）。** 前置 12 项按任务类型分组，全部改写为可勾选、可证实的动作（避免空泛自问）：

前置 12 项（草案）：
1. 跑 `verify-dsh-official-baseline.mjs --online`（或声明离线降级，不得宣称符合官方最新）。
2. 读 `docs/05-系统认知/00-系统认知总览.md`，确认本任务命中的决策 D-xx 与坑索引条目。
3. 判断行为归属（桌面宿主 / 插件 / Profile / 运行时 / 数据迁移），写进任务说明首行。
4. 若改 `src/`、profile、App/resources、scripts、package.json：通读规范知识库 + 按审查清单逐条自问（现有 10 项并入此处）。
5. 若在 profile 内跑任何 pnpm 命令：先 diff specifier vs 实装（D-09）。
6. 若写/改 ps1：确认 UTF-8 BOM + 5.1 可解析（D-11）。
7. 若涉及归档/解包：确认 tar 探测逻辑未绕过，计划含双击启动器路径验证（D-10）。
8. 若改更新/部署/槽链路：确认不绕过退避闸门、不原地写活动槽、不动指纹槽不变式（D-01/06/07）。
9. 若改 UI/插件客户端：确认 slots 注入 + locale 字典 + 主题层归属（D-25），并登记功能清单（D-24）。
10. 若新增测试：确认 existsSync 守卫 + 无模块级实机读取（D-12）。
11. 确认验证计划覆盖四层（tsc/node --test、Build、A/B 部署、真实入口实测）。
12. 跑 3.1 的状态快照脚本，记录"动手前机器状态"作为 Impact Review 的对照基线。

后置 10 项（草案）：
1. tsc + node --test 全绿（0 fail，以实际发现数为准）。
2. `src/` 改动已重打包 + 暂存候选，未覆盖活动 `App/`。
3. 候选经双击启动器实测：清单哈希、readiness、`state.json → completed`、startup-error 无新增。
4. 触碰的每个 D-xx 决策守卫测试均通过且未被删除/弱化。
5. 部署失败点（若新增）已记 deploymentFailures；提交成功已清除版本记录（D-06）。
6. 测试改动通过干净克隆复验（D-12）。
7. 功能清单三项对齐已登记 + 证据链接（D-24）。
8. 新坑已写入 AGENTS.md + 09 号索引 + 对应 07 号 D 条目；受影响文档（基线/功能清单/评估）已同步，无过期副本。
9. 对照前置第 12 项的基线快照，说明机器状态差异（版本/槽/插件矩阵无意外漂移）。
10. 声明剩余风险与未验证范围，不使用"已完成/符合官方最新"等未证实表述。

**落点二：`dsh-dev-spec` 技能。** 把两份清单做成技能的强制检查表段（前置清单在"读规范"与"写代码"之间执行，后置清单在"类型与测试门禁"之后执行），技能输出要求逐项勾选并给证据路径。

**落点三：门禁文档。** `docs/01-当前工作/便携版3-变更与答复质量门禁.md` 增补第 7 节「Global Context / Impact 双清单」，作为唯一事实源，AGENTS.md 与技能以链接引用（避免三处正文漂移——正是 R-4 的教训）。

**落点四：模板化。** 在 `docs/00-交接入口/06-文档编写规范.md` 增加「迭代任务书模板」：任务书必须含前置 12 项勾选区，实施记录必须含后置 10 项勾选区，使 I0xx 系列迭代天然携带双清单痕迹。

### 3.5 优先级建议

1. **先建 09 号「坑与触发条件索引」**（成本最低、直接缓解 R-3）。
2. **再做 profile 矩阵 diff 与状态快照脚本**（探测器先行，防 D-09 类事故复发）。
3. **然后把双清单固化进门禁文档与 dsh-dev-spec**（需人工审阅措辞，故放后）。
4. 最后补测试→守卫映射与功能清单一致性校验。
