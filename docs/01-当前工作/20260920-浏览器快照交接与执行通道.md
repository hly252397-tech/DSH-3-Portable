## 一、浏览器标签在 `+` 菜单打开时变白 —— 快照交接（I007 协议）补齐

**现象**：右侧面板「浏览器」标签激活时打开 `+` 菜单，浏览器区域整片变白。

**根因**（源码取证，非推测）：
- 浏览器内容由 Electron `WebContentsView` 承载，**原生层永远在任何 HTML 之上**，CSS `z-index` 无效。
- `portable/browser-view.js` 检测到 HTML 浮层（`[role=menu]` 等）与浏览器区域重叠后，**直接**调用 `bridge.setOccluded(true)` → 外壳隐藏原生层 → 白屏。
- 外壳侧的快照基础设施其实**一直存在**：`main.ts` 的 `captureBrowserPanelSnapshot()`（L1639）、IPC `browserPanelPrepareOcclusion`（L2491）、preload 暴露的 `bridge.prepareOcclusion()`（`dsh-view-preload.cts` L342）。**缺的只是客户端「先铺快照再隐藏」这一步。**

**修法**（对齐仓库既有 I007 协议，见 `docs/01-当前工作/I007-浏览器原生层遮挡修复/实施与验证记录.md`）：

```
菜单打开：bridge.prepareOcclusion() → 铺 <img> 快照(chrome+page) → await decode()
        → await 2×rAF → bridge.setOccluded(true)
菜单关闭：bridge.setOccluded(false) → await 1×rAF → 移除快照 <img>
```

**健壮性**：
- `occlusionRevision` 版本号丢弃过期异步结果（快速开关菜单不串状态）。
- `prepareOcclusion` 不存在时**回退旧的同步路径**（测试环境/旧外壳）。
- 快照失败时**不隐藏原生层**（宁可菜单被盖住，也不要白屏）。
- 快照 `<img>` 内联 `filter:none;opacity:1;max-width:none;max-height:none`，避开 I007 记录的「通用 `.browser img` 把快照压成 14px」的坑。
- dispose 时清快照 + 递增版本号，且对 mock 元素做了 `querySelectorAll` 存在性判断。

**验收**：用户真机确认「可以了」（菜单打开不再白屏）。

## 二、自定义空间输入框打字丢字/重复 —— 受控输入竞态

**现象**：重命名空间时，快速输入（或输入法拼音中间态）会把名字写坏，例如 `ho'jianho'jian'yuho'jian'yu'g'nhojianyugn`。

**取证（运行实例内探针，非推测）**：

| 输入速度 | 目标串 | 输入框实际值 |
|---|---|---|
| 180ms/键 | `TEST-ABCDEFGHIJ` | 完全一致 ✅ |
| **25ms/键** | `FASTABCDEFGHIJ` | **`TEA`** → 静置后 `TEAB` ❌ |

**根因**：输入框 `value` 直接绑异步设置快照，且**每敲一键就写一次盘**（`onChange → scope.set`）。打字快过「写盘→回读」一个来回时，旧值回写覆盖新输入。

**修法**：本地草稿 + 400ms debounce 落盘 —— 输入只改 `draft`（画面即时），停 400ms 才写一次；写成功才交回快照（`setDraft(null)`）。

**修复后同一测试**：25ms/键 → `FASTABCDEFGHIJ` **完全一致** ✅（对照复现成立）

**连带修掉的真 bug**：落盘被拒（不可写）时原先直接 `return`，**草稿滞留**；等 scope 恢复可写后再编辑会基于过期草稿拼接（单测抓到「多写一条」）。改为**不可写时丢弃草稿**回退远端值；写失败仍保留草稿（那是用户未保存的内容）。

## 五、标签堆积的根因与「先查再开」协议（2026-09-21 用户令）

**现象**：用户截图显示侧边栏浏览器的标签条堆了 2×Example Domain + 3×ChatGPT。用户令：「以后打开之前检查一下是否有，没有在新建，有就是用现成的，不要打开太多。」

**根因（源码级）**：`src/main.ts` 的 `browserPanelShow` handler 调 `openBrowser(request.url, true)`，而

```js
function openBrowser(url?, newTab = false) {
  let tab = getActiveBrowserTab()
  if (tab === null || newTab) tab = createBrowserTab(url || homepage)   // newTab=true ⇒ 必新建
  else if (url) void tab.view.webContents.loadURL(...)                  // false 才就地导航
```

⇒ **每一次带 `url` 的 `show`/`openTab` 都必新建一个标签**。我此前每轮探针都调一次，于是堆积。

**协议（已落 `宏建云系统/AGENTS.md`，并由代码强制）**：`window.__dshAgentBrowser`（dsh-hj-workbench 客户端提供）：

| 方法 | 语义 |
|---|---|
| `ensure(url)` | **两级查重**：① `browserPanel.tabs({action:'list'})` 全清单（含后台标签）命中 → 激活它 → `reused`（不动页面）；② 活动标签是别的页 → `location.href=` 就地导航 → `navigated`；③ 一个标签都没有 → `sidecard.openTab` → `created`；异常 → `failed` |
| `exec(code)` | 在活动标签页面里执行 JS（转发 `browserPanel.executeJs`） |
| `tabs()` / `activate(id)` / `close(id)` | 标签清单 / 激活 / 关闭（新通道 `browserPanelTabs`） |

**实测（第一版，仅活动标签查重）**：`ensure(当前 URL)` → `action = "reused"`，调用前后 `location.href` 不变（未新建、未导航）。

**为什么关标签必须走宿主侧**（2026-09-21 查证）：`createBrowserTab` 建的页面视图 **webPreferences 里没有 preload**（只有 partition/sandbox）⇒ 页面 JS 调不到关标签 API；渲染 × 按钮的 chrome 视图（`browser-panel.html`，其 preload 有 `dshShell.browser.closeTab`）不在本通道可达范围。`Ctrl+W` 只在 `before-input-event`（真实键盘输入）触发，合成 DOM 事件无效。故新增 `browserPanelTabs`（list/activate/close）。

**标签不跨重启**：`loadBrowserWorkspace()` 在 `main.ts` 里**定义但从未被调用**（死代码）⇒ 重启后 `browserTabs` 归零，不会恢复历史标签。

**结论**：智能体可在侧边栏浏览器里自开页面 → 读 DOM → 填输入框 → 点按钮 → **发消息并读回回答**，并能**列出/激活/关闭标签**（先查再开，不再堆积）。「以后只用侧边栏浏览器」具备完整可执行通道；需要外部意见时可自行咨询并依据回复执行。

## 六、侧边栏全板块操作入口（2026-09-21 用户令「操作右侧侧边栏里所有板块功能」）

**架构事实**：13 个已注册板块里，**只有 `browser` 是原生 `WebContentsView`**，其余 12 个（editor/git/subagent/sidechat/terminal/diff/hj-workbench-tab/space-black-hole/space-knowledge/space-database/space-inventor-2027/space-automation）**都在 DSH 页面里渲染 HTML** ⇒ 探针可直接读写。

**统一入口 `window.__dshAgentSidebar`**（dsh-hj-workbench 客户端提供，免重启）：

| 层 | 方法 |
|---|---|
| 服务层（板块/标签生命周期） | `types()` `state()` `openTabs()` `open(seed)` `activate(id)` `close(id)` `update(id,patch)` `openFile(path)` `show(bool)` |
| DOM 层（内容操作，**作用域=活动标签内容**） | `pane()` `text()` `q(sel)` `qa(sel)` `click(sel)` `type(sel,value)` `read(sel)` `findByText(text,tag)` `clickText(text,tag)` |

**作用域定位的踩坑（务必照此实现）**：不能取「最后一个可见 `[data-dsh-pane]`」——**隐藏的底部面板 `pane:3` 也满足 `getClientRects().length > 0`**，会读到空内容。正解：① 优先选「含可见 `[class*="paneTab"]`」的 pane；② 否则按面积最大者；③ 再取其中可见的标签内容 → 内容容器 → 面板本身。

**新增板块是否自动纳管 —— 已实测（双向动态）**：临时注册 `agent-ext-probe` → `types()` 13→14、能 `open`、能读到内容、选择器命中、能 `close`、注销后自动消失；探针代码与注册均已移除。

**三层边界（新板块需注意）**：
1. **原生视图类板块**（如 `browser`）：DOM 层够不到，必须像 browser 那样单独加宿主侧通道。
2. **`q/qa` 走 `querySelector`，不穿透 shadow root / iframe**：新板块若把内容渲染进 shadow DOM 或 iframe，需先加固（遍历 `shadowRoot` / `contentDocument`）。
3. **canvas 类内容**（xterm 终端、PDF/图片查看器）：可点、可滚，但 `text()` 读不到文本（terminal 的 `textLen=0` 属此类）。

**未验证边界**：

- 快照交接在「连续快速开关菜单」下的表现由 `occlusionRevision` 保障，但未做真机压力复现；用户确认的是常规开合。
- `executeJs` 权限面：仅 DSH 视图（`mayManageBrowserPanel`）可调用；未做越权尝试的真机验证（策略代码已读，属实现边界内的保守设计）。
- 写操作只用 `execCommand('insertText')` 验证过 contenteditable；`<input>/<textarea>` 的原生 setter 路径未取到真机数据（当时页面无输入框）。

## 七、修「重启那一瞬间左下角乱一下」（2026-09-21，用户令「想修启动那一下」）

**现象**：重启瞬间，侧栏左下角的自定义空间入口与计费卡挤在一起，名字被拆成三行、页脚明显变高。

**定位（DOM 量化，不是看图猜）**：

| 状态 | `.dcs-group` | `.dcs-item` | `.dcs-name` |
|---|---|---|---|
| 稳态·展开 | 262×78 | 254×42 | **200×18**，`display:block`（一行正常） |
| 稳态·紧凑 | 38×45 | 36×36 | 被 `.dcu-compact .dcs-name{display:none}` 隐藏 |
| **异常帧**（窄盒 + 展开规则） | **40×294** | 32×194 | **0×180**，`display:block` ← 零宽竖排 |

**机制**：`dcu-root` / `dcu-compact` 是 **codex-ui（第三方 npm）** 的类；`dsh-custom-spaces` 用 `.dcu-root:not(.dcu-compact) …` 挂展开态样式。**启动时「类还没加上、列已经变窄」的那一帧**里，展开规则被套进几十像素的窄盒 ⇒ `.dcs-name` 宽度归零 ⇒ 文字逐字竖排 ⇒ 页脚被撑到 294px。

**修法（一处，按实际宽度兜底，不依赖第三方的类）**：`dsh-custom-spaces` 样式表里给 `.dcs-group` 加 `container-type:inline-size`，并新增 `@container (max-width:64px){ … }` —— 盒子窄到放不下文字时，直接按紧凑形态渲染。选择器与展开规则**同形**（特异性持平、次序在后 ⇒ 胜出），**不使用 `!important`**。

**对照复现（受控：把 `.dcs-group` 宽度强制成 40px 制造同一几何）**：

| | `.dcs-group` 高 | `.dcs-name` |
|---|---|---|
| 修前 | **294** | 0×180，`display:block`（竖排） |
| 修后 | **50** | `display:none` ✅ |

**回归**：正常展开态未受影响（`.dcs-name` 仍为 200×18、单行；`.dcs-item` 254×42）。

**边界更正（自查记一笔）**：首轮探针把 `0×180` 当作"真实现场"贴出，其实那是我**自己实验造成**的状态（在移除 `dcu-compact` 之后才测名字，而列宽仍锁在 54px）。后改为「两态都量」才拿到可对照的结论 —— **拿自己造出来的现场当证据，比结论错更该防**。

### 七·补 · 第二次更正：阈值定错了（2026-09-21，用户再次贴图）

**用户反馈**：修完后截图显示**仍然折三行**，且这次是**稳态**而不是启动一瞬。

**我的错**：第一版把阈值定为 `max-width:64px`，而我复现用的是自己选的几何（把 `.dcs-group` 强制成 40px）。**用户实际撞到的几何是「侧栏偏窄但仍算展开」(约 120~180px)，远高于 64px ⇒ 兜底规则根本没触发。**

**改法：宽度扫描定阈值**（同一条路径，把 `.dcs-group` 依次设成 120/150/180/200/220/250/280/320px，量名字行数）：

| 容器宽度 | 修前（阈值 64px） | 修后（阈值 190px） |
|---|---|---|
| 120px | 名字 **3 行**，group 高 104 | 名字 `display:none`，item 36×36，group 高 **50** ✅ |
| 150px | 2 行，group 86 | `display:none`，group 50 ✅ |
| 180px | 2 行，group 86 | `display:none`，group 50 ✅ |
| 200 / 220 / 250 / 280 / 320px | 1 行 ✅ | 1 行 ✅（**未回归**，名字 138~258px 宽） |

**分界线实测在 180~200px 之间** ⇒ 阈值取 **190px**：低于此按紧凑形态渲染（只显图标），到 200px 起恢复展开态单行标签。

**教训（比第一次更正更贵）**：**"我能复现"不等于"我复现的是用户那个几何"。** 第一次我用自己挑的 40px 做对照，结论通过、用户却依旧看到故障 —— 对照复现必须复现**用户实际的条件**，或者像这次一样**扫一遍区间**，把阈值建在数据上而不是我的假设上。

### 七·定稿 · 咨询 ChatGPT 后改为「默认安全态 + opt-in 展开」（2026-09-21）

**做法**：把问题（含现状、阈值来源、约束）通过侧边栏浏览器发给 ChatGPT（`__dshAgentBrowser.ensure` + `exec` 打字/发送/读回复），取回 3,254 字回答。

**回答要点**：
1. `container-type: inline-size` **不只是开启查询能力**，它会启用 inline-size containment 并建立独立格式化上下文 ⇒ 容器的横向 intrinsic size **不再依赖子内容**；放在承担复杂 flex 行为的节点上有 intrinsic sizing 风险。**最稳是另包一层专做 query container。**
2. **容器查询改不了容器自己，只能影响后代**（想改自身布局必须靠 wrapper）。
3. **关键建议：把逻辑反过来 —— 默认走安全窄态，只有容器实测够宽才进入展开态**（`@container (min-width:…)` 展开），而不是"先展开、窄了再 max-width 覆盖回来"。这样第三方 class 早一帧晚一帧都影响不到布局。
4. 190/200px 这类阈值**不是永久常数**（字体、Electron zoom、125%/150% DPI、文案长度、国际化都会挪动折行点）。
5. 若侧栏有动画/拖拽，可在 190~200px 附近加 `ResizeObserver` + **滞回**（进 205 / 出 185）防抖。

**据此实施的改动**（`dsh-custom-spaces` 样式表）：
- `.dcs-group{container:dcs-group / inline-size}`（具名容器；容器查询只影响其**后代** `.dcs-item/.dcs-name/.dcs-icon/.dcs-title`，正好合适）
- **基础样式改为安全窄态**（标题/名称默认 `display:none`，条目默认 36×36）——不再依赖 `.dcu-compact` 类与挂载时序
- **展开态改为 opt-in**：`@container dcs-group (min-width:200px){ … }` 才恢复名称/整宽条目/26×26 图标

## 八、`ensure()` 的「假复用」与带锚点的重复标签（2026-09-21，用户问「这是怎么回事」）

**用户看到**：右侧侧边栏浏览器打开 `http://127.0.0.1:8765/`（宏建云操作手册）时整块是白的；
再点一下变成"新建标签"占位 + 转圈。

**先排除服务端（一手数字）**：`Invoke-WebRequest` 得到 **HTTP 200 / 930,120 字节 / text/html**，
监听进程是 `build_manual_html.py --serve`（pid 24500，22:06:37 起）。**服务是好的。**

**再排除"页面没加载"（探针读活动标签的真实文档）**：
`{"href":"http://127.0.0.1:8765/","rs":"complete","title":"宏建云 ERP 操作手册 · 网页主版","textLen":281224}`
⇒ **页面也是好的**。所以白的是"原生视图没挂上去"，而卡片自己的容器底色就是白
（`portable/browser-view.js` 的 host div `background: var(--dsw-alias-bg-base,#fff)`）。
`PrintWindow` 抓图复核：本次实测该面板**正正经经显示着手册全文**（目录 + 第 0 章）。

**根因（两条，都是查重口径问题）**：

1. **「假复用」= URL 对、页面是死的**。`ensure()` 旧逻辑只比 URL，命中就直接返回 `reused`、什么都不做。
   而手册服务是**后台任务**，随应用重启/作业回收一起死（本轮实录：22:03 应用重启杀掉 8765 服务，
   22:06:37 才重启回来）。服务死时那个标签的 `tab.url` **仍然是 `http://127.0.0.1:8765/`**，
   于是服务恢复后**没有任何一环会去重载它** ⇒ 白屏一直挂着。
2. **带锚点的 URL 逐字符不等 ⇒ 每次 `show` 都新建标签**。实测标签清单里同时存在
   `http://127.0.0.1:8765/` 与 `http://127.0.0.1:8765/#apx-h`（一度共 **3 个手册标签**，其中两个 `#apx-h`）。
   外壳 `browserPanelShow` 的查重是 `tab.url === target || tab.url === request.url`（**逐字符**），
   路径只要带 `#锚点` 就命中不了 ⇒ 多开。

**改法（本轮已落，客户端侧即时生效、无需重启）**：`local/dsh-hj-workbench/lib/client.js` 的 `ensure()`

- 同一文档判据改为**忽略 `#锚点` 与结尾斜杠**：`key(u) = u.split('#')[0].replace(/\/+$/,'')`；
- 新增**内容活性探针**：命中标签后读它自己的 `{href, readyState, body 文本长度}`；活着才算 `reused`；
  死了就 `location.reload()` 并**轮询到真正加载出来**再回报 ⇒ 新动作 `reloaded`；
- 就地导航那条路同样改成"导航后回读确认"，不再把 `nav.ok` 当成"加载成功"。

**对照实测（同一页面、同一标签）**：

| 调用 | 结果 |
|---|---|
| `ensure('http://127.0.0.1:8765/#apx-h')` | `reused`，命中已存在标签，读回正文 **209,705 字** |
| `ensure('http://127.0.0.1:8765')` | `reused`，命中**同一个**标签 |
| 标签数 | **3 → 3（没多开）** |

顺手清掉 1 个重复的 `#apx-h` 标签（`close` 返回 ok）；门禁 `tsc` 0 / 全量 559-538-0-21 通过 / `ui-baseline` PASS。

**未决项（如实登记）**：

1. **外壳侧 `browserPanelShow` 仍是逐字符查重**（`src/main.ts` L2477）⇒ 官方卡片
   `show({owner, url:'…#apx-h'})` 仍会新建标签。修这条属 `src/` 改动，**要构建 + 重启**；
   且需顺带定语义：命中同一文档后，是否把 `#锚点` 在复用的标签里落地（否则点锚点链接不会跳过去）。
2. **手册服务的生命周期**：它是后台任务，随应用重启/作业回收一起死。要长期稳定应改为脱离进程树的常驻服务
   （或需要时由智能体重启），而不是靠"挂了再重启"这条被动路径。
