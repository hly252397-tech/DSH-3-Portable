# 2026-09-30 ESC 关不掉 DSH 设置页 —— 「标志位说没开、DOM 明明开着」

## 现象

顶栏「设置」按钮点开 DSH 网页内设置页后，按 ESC **关不掉**（点「返回应用」可以关）。上一轮刚修好的开→关→开循环在 ESC 这条路上仍然是坏的。

## 诊断先行

> 问题是 ESC 路由读的那个进程内标志位，在设置页明明开着的时候是 `false`；
> 证据是同一次会话里 `F11` 能把窗口切全屏、`Ctrl+B` 能把边栏从 240px 收到 56px ——
> 这两条都只能由 `mainWindow.webContents` 的 `before-input-event` 触发，且都要先过
> `input.type === 'keyDown'` 守卫；而 ESC 时 DOM 照常收到 `keydown:Escape`，
> 说明同一个 handler 走了 `escapeRoute` 的 `pass-through` 分支、**没有** `preventDefault`。
> 下一步是让 ESC 不再依赖这个标志位，改成以 DSH 页面 DOM 为准。

## 证据链（全部实机，CDP 受信输入）

| # | 观测 | 说明什么 |
|---|---|---|
| 1 | 现役槽 `app.asar` 内含 `dshSettingsDialogVisible = outcome === 'closed' \|\| outcome === 'opened'` | 上一轮的 `'opened'` 笔误修复**确实在运行产物里**，不是没打进去 |
| 2 | 三个 profile（`Data/DSH/profiles/web`、`v4-rc2b`、`v5-020rc1`）全量静态 grep `dsh-shell:dsh-settings-visibility` / `dshSettingsVisibility` → **零命中** | 标志位唯一的自动校准通道确实无发送方，注释里的说法成立 |
| 3 | 给 DSH 页 `history.pushState` / `replaceState` / `popstate` / `hashchange` 打桩，开关设置页全程 `nav` 为空、URL 不变 | 排除「SPA 同文档导航触发 `did-start-navigation` 把标志位清掉」 |
| 4 | `Ctrl+B`：壳页 DOM **零事件**（`keydown`/`keyup` 都没收到） | `before-input-event` 装在 mainWindow 上，且 `preventDefault()` 生效、事件被吞 |
| 5 | `Escape`：壳页 DOM 收到 `keydown:Escape` | 同一个 handler **放行**了 ESC ⇒ `escapeRoute` 判 `pass-through` |
| 6 | `F11`：窗口 (592,246) 1376×908 → (0,0) 2560×1440，再按恢复 | 再次确认 CDP 派发能走通 `shellActionForShortcut` → `executeShellAction` 全链路 |

4、5 两组对照是决定性的：**不是** CDP 输入到不了主进程，**不是** `rawKeyDown` 被 `keyDown` 守卫早退（`F11`/`Ctrl+B` 同样是无文本键、走同一条守卫）。唯一的差别就是 `escapeRoute` 的 `isDshSettingsDialogVisible` 读到了 `false`。

## 为什么标志位不可靠

`dshSettingsDialogVisible` 是主进程里的一个模块级 `let`，进程内有 4 条写入路径：

| 位置 | 场景 |
|---|---|
| `src/main.ts:3261` | 顶栏「设置」toggle 后的回写（`'opened'` 分支，**唯一**把它置 true 的地方之一）|
| `src/main.ts:655` | `isDshSettingsPageOpen()` 以 DOM 为准的校准 |
| `src/main.ts:645` | `exitDshSettingsPage()` 点完「返回应用」后置 false |
| `src/main.ts:2051` | `did-start-navigation` 无条件置 false |
| `src/main.ts:2104` | 窗口清理 |
| `src/main.ts:3030` | `dsh-shell:dsh-settings-visibility` 上报（**已确认无发送方**）|

2026-09-30 逐条排查后，`did-start-navigation` 与上报通道都被证据 2、3 排除，**具体是哪条路径把它改回 `false` 仍未锁定**。这不影响修复方向：一个只能靠多方写入维持、且唯一自动校准通道已消失的标志位，不该是 ESC 的唯一闸门。

## 修法

`src/main.ts` 新增 `dismissDshSettingsDialogWhenOpen()`：先 `await isDshSettingsPageOpen()`（以 DOM 为准）判断，没开就空转，开了才 `dismissDshSettingsDialog()`。接到两处：

1. `route === 'dismiss-dsh-settings'` 分支 —— 标志位恰好为 true 时的快路径；
2. **无条件的兜底** —— 主壳上按 ESC 且当前不是辅助窗口时直接补一次 DOM 判定，覆盖标志位为 false 的情形（这才是真正修好问题的那一条）。

两个分支都**刻意不 `preventDefault`**：ESC 照常透传给 DSH 页面，壳只在旁边补一次关闭。这样设置页没开时，DSH 自身的 ESC 语义（关浮层、退输入态）完全不受影响——比无条件吞掉 ESC 安全得多。

对任何尚未识别的标志位写入者都免疫，这是选它而不是「继续追谁写的」的理由。

## 回归测试

`test/shell-settings-toggle.test.ts` 追加「ESC 关设置页以 DOM 为准，不能只信进程内标志位」，锁三件事：

- 兜底函数必须先问 DOM 再关，没开就空转；
- 兜底必须挂在标志位分支**之外**（否则 flag=false 时根本没机会跑，等于没修）；
- 关闭动作不得 `preventDefault`（只查真实调用，注释里出现该词不算）。

## 影响面

- 只影响主壳上 ESC 的行为；辅助窗口（快捷键/关于/功能面板/桌面设置）的 `close-auxiliary` 路径未动。
- 新增行为是「ESC 到达 DOM 为准的关闭」，对用户可见且只在设置页开着时生效。
- 已知副作用：设置页开着时 ESC 会**同时**透传给 DSH 页面。若 DSH 自身对 ESC 有响应，可能出现"设置页关了 + 某个浮层也关了"。相比"ESC 完全失效"可接受，且是刻意选的保守方向。

## 两次自我纠错（记录以免重犯）

1. **窗口几何会翻转**：应用恢复的是**保存过的非最大化尺寸** 1376×908 @ (592,246)，不是最大化。同一轮里两次采样分别读到 2576×1408 @ (-8,-8) 和 1376×908 @ (592,246)。点击坐标必须由 `list_windows` 的 hwnd rect + 视口 `getBoundingClientRect()` 推出，不能假设。
2. **不能只发 `rawKeyDown` 就下结论**：一开始怀疑「无文本键发 `rawKeyDown` 被 `keyDown` 守卫早退」，用 `F11` 做对照才发现守卫其实是通的。若当时据 `rawKeyDown` 现象直接改守卫，会修一个不存在的问题、并真的弄坏 Ctrl+B 等所有无文本快捷键。
