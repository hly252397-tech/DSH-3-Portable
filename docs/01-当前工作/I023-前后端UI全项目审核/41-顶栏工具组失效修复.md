# 40 · 顶栏工具组失效修复（一个缺失的 DOM id 让整条外壳脚本中断）

- 轮次：2026-09-13（20:30~21:0x）
- 用户入口：用户截图（顶栏条，2411×52）→ 用户原话「这些功能现在都没办法使用」
- 触发版本：活动槽 `Data/Updates/Desktop/slots/1.0.66-local-536047aaadd3f01a`（20:10:14 由启动器切换）
- 关联上一轮：[39 · 外壳顶栏改版](39-外壳顶栏改版.md)（顶栏从 `display:none` 恢复显示）

## 1. 实际问题与根因

用户截图里顶栏**长出来了但按不动**：`文件/编辑/视图/帮助` 菜单区空白，返回/前进、搜索胶囊、重启、搜索、桌面设置、检查更新全部点击无反应。

根因是**一个缺失的 DOM id 让整条外壳内联脚本在第一个语句上就中断**：

| 环节 | 事实 |
|---|---|
| `assets/browser-workspace.js` | 20:01 的改动新增 `menuExternal: byId('browser-menu-external')`，并在 `create()` 里**无条件**执行 `elements.menuExternal.addEventListener(...)` |
| 该 id 是否存在 | 只存在于 `assets/browser-panel.html`（独立浏览器面板文档），**`assets/shell.html` 里没有** |
| 谁把 `create()` 放在顶层 | `shell.html` 第 227 行 `const fullBrowser=window.DshBrowserWorkspace.create(api,{getState:()=>state})`；此处抛错 ⇒ 后面所有 `addEventListener`（菜单填充、返回/前进、搜索胶囊、重启两步确认、齿轮、更新）**一行都没执行** |
| 为什么顶栏还看得见 | HTML/CSS 与 `<head>` 里的主题脚本照常执行（用户截图是浅色=主题脚本跑过），只有 `<body>` 末尾那段交互脚本死了 |
| 为什么"现在"才坏 | 39 号改版的 `shell.html`(32502ef4) 在 17:26/19:15/19:49 进槽；19:45 又用界面快通道把带 `menuExternal` 绑定的 `browser-workspace.js` 单独铺进同一槽，20:10 切换后才生效 |

离屏实机复核（`artifacts/shell-topbar-fix-20260913/results.json`，同一 harness 跑两组对照）：

- 旧组合（活动槽 536047 的 `resources/`）：`pageErrors=["Cannot read properties of null (reading 'addEventListener')"]`、`menusCount=0`、点返回键**零 action**——与用户截图逐项一致。
- 修复后（仓库 `assets/`）：`pageErrors=[]`、`menusCount=4`、六个控件都发出正确 action。

## 2. 原行为 → 新行为

| 项 | 原行为 | 新行为 |
|---|---|---|
| 外壳交互脚本 | `create()` 抛 `TypeError`，顶栏整条哑火 | `create()` 正常返回，菜单与全部监听器就位 |
| `shell.html` 浏览器「更多」菜单 | 缺 `在系统浏览器打开` | 补齐该入口（与 `browser-panel.html` 对齐） |
| 单个 id 缺失的后果 | 整条顶栏失效 | `elements.menuExternal?.` 空安全跳过；并由回归用例兜住同类问题 |

## 3. 修改位置与关键选择

1. `assets/shell.html`：在 `#browser-overflow` 的「浏览器资料与设置」与「清除 Cookie…」之间补
   `<button id="browser-menu-external" type="button">在系统浏览器打开</button>`（文案与 `browser-panel.html` 同字）。
2. `assets/browser-workspace.js`：`elements.menuExternal.addEventListener` → `elements.menuExternal?.addEventListener`
   （同一 `byId` 契约同时服务 `shell.html` 与 `browser-panel.html`，缺一个不该拖垮另一个；空安全是保险，真正的护栏是下面第 3 条）。
3. `test/main-safety.test.ts` 新增用例「浏览器工作区脚本引用的元素在它加载的每个文档里都存在」：
   解析 `browser-workspace.js` 全部 `byId('…')`，逐个断言在 `shell.html` 与 `browser-panel.html` 中都存在。
   扫描结果：62 个 id，`browser-panel.html` 缺 0 个，`shell.html` 此前缺 1 个（即本故障），修后 0 个。

不取代任何既有要求：39 号确定的顶栏布局（两段分组、居中定宽 320 胶囊、自绘电源图标、重启两步确认）全部保留。

## 7. 失败尝试记录（不要重复）

0. 本记录初次落盘时命名为 `40-顶栏工具组失效修复.md`（未注意该目录已有两个 `40-`），随后改名 `41-` 并重记基线。
   因此历史里 `customizations/ui/history/2026-09-13T12-50-08-539Z.json` 的 `note` 指向旧文件名（该名字已不存在）；
   受保护资产内容两次记录完全一致，不是资产漂移，无需处理。
1. `cmd /c 'Build-UI-Only.cmd -DryRun'` 从 pwsh 调用时引号被拆坏（`Build-UI-Only.ps1" -DryRun` 被当成命令），
   实际门禁已跑并返回 3；**直接用 `powershell -File Build-UI-Only.ps1` 调用**即可。
2. 一开始按"混血槽"方向排查（界面素材比 `app.asar` 新 ⇒ 新界面调旧主进程）——**证伪**：
   活动槽 `app.asar` 内的 `dist/src/main.js`/`shell-preload.cjs` 与仓库 `dist/` 逐字节一致，
   界面调用的 24 个 `dshShell` 方法在 preload 里一个不缺。真正断点是 DOM 层，不是 IPC 契约层。
3. 该故障不是 `installWindowSurfaceGuard`（未提交的窗口切换改动）引起的：那条路径只影响
   `dshView.browserPanelView` 的显隐与 bounds，不会让 `shell.html` 的顶层脚本中断。
4. **基线登记范围一度出错并已纠正**：20:50:08 首次 `--record` 正好落在另一会话重建
   `dsh-sidebar-spaces` 之后 3 秒，`recordBaseline` 会把「登记时刻的全部受保护文件」写进基线，
   于是把对方那两个在途文件也背书了。用 `artifacts/shell-topbar-fix-20260913/trim-external-drift.mjs`
   把那两项恢复为上一版基线的哈希与快照（**方向是把不该绿的恢复为红，不是为变绿改哈希**），
   新基线 `2026-09-13T12-52-19-972Z.json` 只背书 `assets/shell.html`。
   教训：`--record` 前应先逐文件比对「本次改动清单 vs 受保护文件清单」，发现登记窗口内有别的会话
   在写受保护文件时，**先确认再登记**。
5. 同一次全量里曾出现 10 项 `activityDays is not defined`（侧栏插件测试组）：该用例按文本替换把
   `activityDays` 注入插件 `client.src.js` 的 `exports.model`，而对方改造中途的临时构建里还没有这个符号，
   与其完成后复跑即转绿。**非本轮引入**，但说明「实机插件 + 文本注入」的测试会在别人改插件时连带变红。
