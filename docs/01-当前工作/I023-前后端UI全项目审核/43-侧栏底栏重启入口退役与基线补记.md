# 43 - 侧栏底栏重启入口退役与 UI 基线补记

## 背景

2026-09-14 的改动注销了 `dsh-restart-button` 客户端半侧注入到 DSH 侧栏底部的那一行「● DSH 工作台 ⚙」。
理由（摘自 `Data/DSH/profiles/web/local/dsh-restart-button/lib/client.js` 头部注释，原文未改）：

1. 齿轮的 `onClick` 走 `bridge.action("desktop-settings")`，与外壳顶栏齿轮（`assets/shell.html:109`）触发**同一个动作、同一个窗口**——上下两处功能完全相同；
2. 「DSH 工作台」字样与顶栏 `workspace-label`（`shell.html:101 / 233`）同文；
3. 左侧圆点使用固定色 `--dcu-sidebar-primary`，不绑定任何连接或运行状态，是**假状态指示**。

重启本身已于 I023-39「外壳顶栏改版」移到顶栏 `#restart-btn`（`power.svg` + 两步确认 + 5s 超时），
底栏不再承担重启职责；I023-34 的「重启 / 连接 / 设置」三列排版随之作废。
宿主半侧 `lib/index.js` 的受令牌保护重启端点（`POST /api/dsh-restart-button/restart`）**未改动**。

## 本轮补的是什么（两处未收尾）

改动落在实机 `Data/` 下的本地插件文件上，但两处收尾没有做，导致全量门禁出现 2 项失败：

| # | 失败项 | 原因 |
|---|---|---|
| 1 | `test/main-safety.test.ts`「重启按钮不会把未完成的重启伪装成已完成」 | 该用例钉的是**已退役控件**的字符串（`RESTART_TIMEOUT_MS = 15_000`、`setState("starting")` 等）。控件退役后字符串消失，断言必然失败。按设计决策 **D-27**「文案/控件随版本退役要连测试一起退役」处理——**退役该断言，改为钉住新契约**（见下），不是删掉了事 |
| 2 | `test/ui-baseline.test.ts` UI 基线漂移 | `Data/DSH/profiles/web/local/dsh-restart-button/lib/client.js` 已变，但受保护基线未重新登记。按 `docs/03-技术架构/UI定制维护契约.md`，**漂移必须调查 + 完成实际 UI 验证后才可 `--record` 追加新基线**，禁止直接改哈希放行 |

## 新增测试钉住的新契约

`test/main-safety.test.ts` 的该用例改为「侧栏底部不再重复注入重启/设置入口」：

- 客户端半侧**不得**再出现任何底部注入痕迹（`RESTART_TIMEOUT_MS`、`setState("starting"|"failed")`、`sidebar.footer.action`）；
- 模块形态必须保持（`function apply() {}` 与 `inject: ["locale", "slots"]` 仍在）——因为宿主 `cordis.patch.yml` 仍按 id 加载它，形态坏了会变成解析失败而非「什么都不做」。

**没有丢覆盖**（已在别处钉住，逐一核对过）：

- 「全壳唯一一个重启入口 + 紧凑图标态 + 两步确认与拒绝文案」→ `test/main-safety.test.ts:157`（含 `id="restart-btn"` 全壳只出现 1 次）；
- 「复用既有优雅重启实现、不允许第二条硬杀路径」→ 同文件「运行时可通过 IPC 请求优雅重启」；
- 「宿主半侧受令牌保护的本机重启端点」→ 同文件「重启按钮宿主半侧提供受令牌保护的本机重启端点」。

## 实际 UI 验证（本记录的证据来源）

用仓库既有做法：把**真模块源码**放进**盘内真 Chrome**（离屏 harness 页面）里执行，而不是手抄或静态比对。

- 脚本：`artifacts/restart-button-retired-20260914/verify.cjs`
- 结果：`artifacts/restart-button-retired-20260914/results.json`
- 做法与 `artifacts/home-activity-removed-20260913/verify.cjs` 一致（同为「真实模块 + 真实浏览器」离屏验证）。
- **含反向对照**：同时加载**退役前**的版本（取自受保护快照 `customizations/ui/sources/f6aea1b1…txt`）与当前运行件。
  退役前版本必须被检测器判为「有注入」，当前件必须判为「零注入」——否则说明检测器是空跑，证据无效。
- 另核对：profile 实际加载的文件与本次检验的文件是同一份（junction 解析一致），避免"验的不是运行件"。
