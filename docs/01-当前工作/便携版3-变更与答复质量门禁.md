# 便携版 3：变更与答复质量门禁

本文件是便携版 3 的强制验收标准。涉及启动、插件、更新、数据路径的方案，未满足下列门禁时只能标为“临时诊断”，不得称为正式方案或推荐给用户。所有用户功能的新增、修改与下线，还必须满足第 6 节前后端与 UI 三项对齐门禁，包括仅前端或 UI 的变更。

## 0. “专业级”与“企业级”的强制定义

“专业级”和“企业级”是可验收等级，不是修饰词。答复、设计或实现不得在缺少对应证据时使用这两个称谓。

### 0.1 专业级

必须同时满足：

1. **事实准确**：先核对当前版本、源码、日志、发布通道和运行状态；时效性事实使用官方一手来源并标明核对时间。
2. **边界正确**：明确桌面宿主、DSH 子服务、插件、运行时、用户数据和源码更新的不同生命周期。
3. **方案完整**：同时覆盖正常路径、失败路径、数据保护、兼容性、验证方法和用户可见结果。
4. **可实施**：给出明确组件、状态、输入输出、文件位置和验收条件，不能只给原则或口号。
5. **可验证**：结论必须由静态检查、自动化测试、故障注入或真实环境验证支撑，并明确尚未验证的部分。
6. **不夸大**：临时恢复、设计方案、已实现、已测试、已部署必须分别陈述，禁止把计划写成完成状态。

任一项不满足，只能称为“建议”或“草案”，不得称为专业级。

### 0.2 企业级

企业级必须先满足全部专业级要求，并额外同时满足：

1. **供应链安全**：只信任允许列表中的 HTTPS 来源；固定不可变版本和制品哈希/完整性；校验发布身份、包名、版本、大小、依赖闭包与签名或可验证证明。
2. **策略治理**：具备发布通道、维护窗口、暂停/恢复、跳过版本、最低桌面版本、强制/可选更新和灰度策略；预发布版本默认不得静默强切。
3. **事务与幂等**：下载、解包、安装和验证在独立暂存区完成；提交使用原子指针或同卷改名；重复执行不会破坏状态。
4. **A/B 与自动回滚**：旧版本在新版本通过观察期前保持可启动；启动失败、崩溃循环、健康超时或兼容门禁失败时自动回到上一已知良好版本。
5. **最小中断**：等待任务空闲或维护窗口，只重启必要组件；运行时/插件更新只回收 DSH 子服务，桌面二进制更新才重启桌面宿主。
6. **数据与迁移安全**：更新前识别破坏性变更和数据格式迁移；迁移必须可备份、可验证、可恢复；用户数据不得作为更新清理对象。
7. **可观测与审计**：记录检测、决策、下载、哈希、安装、切换、验证、提交和回滚事件；日志带关联 ID、版本、时间、耗时和脱敏错误，且全部落在便携盘。
8. **受控发布**：至少经过候选运行时静态验证、隔离启动验证、真实 Profile 兼容检查和切换后观察期；支持逐步放量与撤回。
9. **故障预算与恢复目标**：定义检查/下载/启动超时、最大重试次数、崩溃阈值、回滚时限和保留版本数，禁止无限重试或失败后继续覆盖。
10. **独立验收**：类型检查、单元测试、集成测试、故障注入、离线/断网/磁盘满/断电边界测试、真实打包冒烟和回滚演练全部通过后才能启用全自动策略。

任一企业级项尚未实现或验证时，必须明确标为“企业级目标方案”或“候选实现”，不得声称已经企业级投产。

## 1. 先确认生命周期边界

- `DSH Codex Desktop`：Electron 桌面宿主，维护窗口、托盘和便携路径。
- `dsh --profile web`：由桌面宿主管理的子服务。
- 插件安装、升级、启用、禁用：桌面宿主保持运行，只回收 DSH 子服务。
- 桌面程序自身升级或替换 `App/`：必须从托盘彻底退出，再进行原子部署。

任何答复在提出“退出/重启”前，必须先说明重启对象，并从源码、运行日志或可复现测试确认必要性。

## 1.1 官方规范与版本门禁

1. 每个功能开始前必须运行 `App/resources/node/node.exe scripts/verify-dsh-official-baseline.mjs --online`，并完整阅读官方兼容基线与插件开发规范知识库。
2. 实现以实际内置 DSH 版本的导出和类型声明为准；官方最新 HEAD 是审查与迁移基线，不得把新版本接口直接写进旧运行时。
3. 官方 HEAD 变化时必须先人工审阅官方 `AGENTS.md`、架构、测试规范和受影响子系统，再更新基线；禁止自动改写基线后视为通过。
4. 官方网络不可用时只能继续诊断或标记候选实现，不得声称符合官方最新要求。
5. DSH 内部新能力必须走官方扩展点；Electron 桌面宿主仅拥有窗口、进程、便携路径和桌面 A/B 部署，二者边界不得混淆。
6. 产品可见插件必须有真实 Profile/Loader 组合测试；用户可见状态只能在事务提交点后发布。

## 2. 正式方案的必备证据

1. **根因证据**：错误日志、缺失文件或调用链能对应到同一个故障点。
2. **数据边界**：配置、凭据、对话、缓存、运行时仍位于便携盘；不得无提示写回系统用户目录。
3. **事务性**：先暂存和校验，再提交；中途失败恢复旧文件和旧清单。
4. **可恢复性**：损坏社区插件只从启用列表隔离，保留依赖和文件；清单备份与原因写入审计日志。
5. **可观测性**：用户可以从 `.dsh-recovery/quarantined-bundles.json` 和 `manifest-backups/` 查到时间、来源、原因和备份。
6. **最小中断**：插件变更仅热重载 DSH 子服务；只有 App 更新才退出桌面。
7. **兼容与安全**：拒绝非法包名和路径越界；打包资源包含新增模块的完整依赖闭包。
8. **验证**：类型检查、单元测试、故障注入、独立打包目录导入、打包后启动冒烟必须通过。
9. **单一更新入口**：桌面 Release、本地源码构建、官方运行时和社区插件必须由明确的唯一协调器管理；不得保留可绕过清单验证与回滚的同级脚本。
10. **可视进度一致性**：更新图标、设置页阶段条、持久化状态和审计事件必须使用同一状态机；用户看到的“完成”只能发生在健康验证提交之后。

## 3. 启动故障的标准处置

1. 启动前检查每个社区 bundle 的 `package.json`、`main`/根 `exports`、patch 入口及直接依赖清单。
2. 发现损坏时，原子备份 Profile 清单，只从 `dsh.profile.bundles` 隔离该插件，不删除依赖和插件目录。
3. 将插件名、指纹、故障阶段和原因写入便携盘内的恢复审计日志；审计写入失败则回滚清单。
4. 继续启动 DSH；若加载阶段仍报告具体社区插件，再隔离并在有限次数内重试。
5. 插件文件被修复且健康指纹发生变化后，自动解除旧隔离；正常的清单协调流程可重新启用它。
6. 官方 bundle 不做自动隔离，避免把运行时损坏伪装成社区插件问题；此类错误应明确失败并进入运行时修复流程。

## 4. 答复分级

- **正式方案**：满足上述全部门禁，并给出验证结果。
- **临时恢复**：用于立即恢复可用性，必须明确风险、影响和后续正式修复，不能冒充长期流程。
- **诊断建议**：只用于收集证据，不应修改用户数据或要求不必要的退出。

禁止在未核对现有实现的情况下，把删除插件、删除 Profile、清空用户数据或“完全退出桌面”作为通用建议。

## 5. 最近功能的回归门禁

- 更新入口必须显示检测、下载、验证、构建、部署、完成六阶段及总进度；活动阶段、可更新、待部署、完成和失败状态应在工具栏图标上可辨识。
- 社区插件和 Harness 更新不得退出 Electron；仅回收由桌面创建的 DSH 子服务，并等待运行/审批任务空闲。
- 桌面二进制更新必须由用户确认后正常关闭宿主，再由外部启动器切换 A/B 槽；不得用全局进程名强杀。
- 内置浏览器宽度调整必须限定 DSH 与浏览器最小可用宽度，最大化/恢复状态必须可持久化且键盘可操作。
- 会话路径修复只能在完整备份后移动经会话头精确证明为错位的目录；禁止改写会话日志内容或用模糊匹配批量移动。
- Electron 内校验 `app.asar` 必须读取物理归档字节，禁止使用会把 `.asar` 当虚拟目录的补丁版 `node:fs`；需由 Electron `original-fs` 冒烟证明。
- PowerShell 启动器在严格模式下读取 `pending`、`previous` 等可选字段必须先检查属性；失败回滚必须先原子撤销 pending，再清理候选进程。
- 桌面候选必须在当前桌面仍可使用时完成共享运行环境预热并通过逻辑内容摘要门禁，之后才能写入 pending；正常重启路径只允许执行桌面槽切换、启动和健康提交。启动时解压仅作为断电、缓存缺失或损坏后的自愈路径，不得作为每次更新的正常流程。

## 6. 前后端与 UI 三项对齐强制门禁

生效日期：2026-09-08（Asia/Shanghai）。适用项目：`G:\DSH-3-Portable`。本节为三项对齐规则的唯一事实源；开发入口、功能清单及迭代记录引用本节，不另行复制完整规则。

### 6.1 完成定义与适用边界

一个用户功能必须同时满足以下三项，才可以标记验收通过：

1. **后端能力可用**：实际接口、IPC、RPC 或插件服务已接通，入参、响应、错误、权限与持久化行为明确且经过验证。
2. **前端操作闭环**：用户能找到入口，操作触发真实业务行为，结果反映到相关视图，刷新或重启后符合预期。
3. **UI 界面可用**：主页面及弹窗、标签页、二级页面等关联界面布局正确，适用的加载、成功、失败、空数据、禁用状态完整，交互经过运行验证。

代码存在、编译通过、接口返回成功或截图外观正确，均不能单独证明三项对齐。历史功能清单中的“✅ / 已实现”不是三项对齐验收结论。

- 面向用户的后端能力必须有可达的前端入口；分期开放的能力须记录产品范围、未开放原因和状态，不能按已交付功能验收。
- 内部服务、维护接口及后台任务的内部步骤不强制生成独立页面，但须记录用途、调用方与无需入口的理由；面向用户的后台任务仍需有适用的入口及状态反馈。
- 纯前端交互可标记“无需后端”，仍需验证实际行为；任何不适用项都必须写明理由。
- 未开放功能应隐藏或禁用并说明原因。禁止将占位按钮、空事件处理、模拟成功或失效链接作为可用功能交付。

### 6.2 开发前与变更同步

1. 先确认真实启动链、当前加载的页面来源、Profile 与运行版本；区分源码、构建产物、候选槽和实际运行槽。
2. 检查未提交修改及并行工作的文件边界，保留无关改动，遵守本仓库官方兼容性与插件归属规范。
3. 从用户入口正查事件、调用、后端处理和结果反馈，再从受影响的后端能力反查前端入口；覆盖菜单、快捷操作、弹窗及嵌套界面。
4. 修改前明确契约、调用方、交互状态和验收步骤；新增、修改、下线都要同步对齐记录，不能只改其中一端。
5. 下线时同步入口、路由、调用方和数据兼容处理，不遗留死链接或可操作的失效控件。
6. 当前 Profile 缺少某插件时，必须对照用户原有界面、历史配置和功能记录确认是否属于回归，不能直接标为“不适用”。名称相似不代表能力互相替代：例如 `dsh-codex-ui` 的左侧导航与 `dsh-better-sidebar` 的右侧/底部卡片工作台是不同能力，应验证共存。可选服务的扩展注册必须覆盖稍后加载、卸载及重新加载，不能只在首次挂载时查询一次。

### 6.3 契约与交互实现要求

- 接口字段、枚举、空值、分页、错误码或版本发生变化时，同步所有受影响调用方，优先复用项目已有共享类型与契约机制。
- 异步操作必须显示可感知的进行中状态；按实际能力处理超时、取消或重试，不吞掉错误、不无限加载、不显示虚假成功。
- 写入操作防止重复提交；成功后更新相关视图，失败后保持可恢复状态；有持久化要求的功能验证刷新或重启后的数据。用户可见成功只能在相应事务提交后发布。
- 空数据、无权限、离线、服务不可用等适用场景必须给出准确反馈和可行的恢复操作。
- 验证弹窗及子界面的打开、关闭、返回、切换、滚动、焦点、键盘操作，不能只有外层页面正常。
- 复用现有组件、主题与文案体系；在支持的窗口尺寸、显示缩放、明暗主题下检查遮挡、溢出和内容可达性。
- 需要在第三方插件更新后保留的便携版外观约束应归本项目主题层，不以修改注册表安装包作为持久方案。使用实际更新后的插件验证样式后加载、重载和主题切换；不靠回写旧插件或禁止正常更新来维持颜色。见 [插件更新后主题保持](I023-前后端UI全项目审核/07-插件更新后主题保持.md)。
- 首页活动分布与输入框必须共用内容列、尺寸比例和间距规则，禁止分别设置相互冲突的宽度或横向留白。变更后组合验证窗口大小、侧栏开关和界面缩放；输入内容允许自然增高，不能通过裁剪维持比例。当前尺寸约束和实测证据见 [首页卡片尺寸对齐](I023-前后端UI全项目审核/06-首页卡片尺寸对齐.md)。
- Electron 外壳与 DSH `WebContentsView` 跨层界面必须实测合成层、点击区域和焦点；不能只依据浏览器预览或增加 `z-index` 判断通过。
- 产品可见插件遵守真实 Profile/Loader 组合验证要求，确认宿主实际加载的客户端与服务端产物一致；模拟响应不能作为真实业务链路通过证据。
- 本地候选的内容标识必须覆盖主程序和额外打包的 HTML、CSS、JS 等资源；只改 UI 也必须生成包含新资源的候选，不能仅按 `app.asar` 摘要复用旧槽。发布前核对源码、构建目录和候选槽中受影响文件的一致性，并保留 UI 单独变更的回归用例。

### 6.4 对齐记录与证据归属

功能索引统一维护在 [功能清单](../00-交接入口/07-功能清单.md)。每个受影响功能登记三项对齐状态，并链接到当前迭代中的实际检查或验收记录；详细证据只保存一份。尚无实际检查内容时不得创建空验收文档。

记录必须包含：

- 功能名称或稳定标识、变更范围、真实入口与关联子界面。
- 前端事件和调用位置、后端接口或处理位置；无需后端或入口的理由。
- 请求、响应、错误、权限和适用 UI 状态；涉及持久化时记录读写及恢复预期。
- 验证环境、版本或槽位、检查时间、操作步骤、预期与实际结果、测试输出或截图等证据路径。
- 后端、前端、UI 各自的结论，以及总体验收结论；结论使用“通过 / 失败 / 未验证 / 不适用（理由）”。
- 未解决问题、影响、复验步骤及对应待办链接；原有功能被修改后，受影响部分须重新验收，不能沿用旧通过状态。

### 6.5 验证顺序与阻断条件

在执行本仓库已有类型、测试、打包与部署门禁的基础上，按变更风险完成以下适用检查；本节不减免已有强制门禁，也不要求为简单样式变更堆砌无意义测试：

1. **静态对应检查**：确认入口、事件、调用、处理器和契约对应，没有空处理、失效路由或遗漏调用方。
2. **接口与集成验证**：验证真实请求、错误处理及数据读写；覆盖变更影响的契约和共享组件。
3. **真实操作验证**：从用户实际使用的启动入口进入，完成核心操作，检查结果和适用的异常、空数据、权限、重复点击场景。
4. **UI 验证**：检查主页面及关联子界面的布局、主题、状态和交互，保存可复查证据。
5. **相邻功能回归**：覆盖共享组件、契约或数据变化影响到的其他入口；持久化功能检查刷新或重启后的结果。

出现以下任一情况，受影响功能不得标记验收通过或作为已完成交付：

- 用户能力缺少可达入口且无明确范围说明。
- 点击无反应、虚假成功、失效跳转、错误隐藏或持续卡住。
- 主页面或子界面遮挡关键内容、无法操作、状态与实际结果不一致。
- 缺少真实运行证据，却将静态检查、单元测试、模拟数据或截图单独当成端到端通过。

缺少账号、设备或外部依赖时，标记“未验证”并写明原因和复验步骤，不得计入已通过项。源码验证、打包验证、候选暂存、部署完成与实际运行验证分别记录，候选存在不代表正在运行该版本。

### 6.6 后续开发与交付固定流程

更新功能索引与对齐记录 → 明确契约和 UI 状态 → 同步实现 → 完成适用验证与回归 → 保存证据 → 更新验收状态。

每次功能交付必须说明：受影响功能、前后端与 UI 的对应关系、验证范围和结果、实际运行版本、遗留问题。未验证范围须保留，禁止用“全部完成”覆盖。自动检查只能证明其实际覆盖范围，不能替代真实交互与 UI 验收。

本节是开发与验收的文档门禁；规则写入不代表全项目已完成对齐检查，也不代表已安装自动化阻断机制。
