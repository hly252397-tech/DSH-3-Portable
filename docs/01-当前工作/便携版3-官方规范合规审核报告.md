## 一、总体结论

**代码质量对规范主线是高符合度的**：插件扩展点、`ctx` 注册、事务提交点、A/B 回滚、供应链校验（integrity + commit + registry 签名 + 资产域白名单）、Electron 安全基线（`contextIsolation`/`sandbox`/`nodeIntegration=false` + 导航拦截）都真实落地，`src/` 里没有 `as any` / `@ts-ignore` 这类官方新规范明令禁止的写法。

**主要问题不在代码，而在"规范自我一致性"与"程序化门禁的覆盖范围"**：

- 两份被指定为"改动前必读"的权威文本（兼容基线 MD、插件规范知识库）**仍把实现基线写成一个已过期的版本**（`0.1.6-alpha.2`），而当前声明与实装都是 `0.1.7-rc.2`。这违反基线文档自己第 52 行"非平凡变更必须留下决策与证据"的可读性要求，且现有门禁测试**测不到**这两份 MD。
- 官方基线脚本**不校验活动运行时槽**，所以"实现基线 = 活动槽"这句规范里的关键等价关系**没有机器兜底**：活动槽可以在不被任何门禁发现的情况下偏离声明。
- 三项对齐门禁（§6）是文档门禁，**未系统落实**：规则生效后新增的功能条目仍按旧的 `✅`/单行描述登记，没有后端/前端/UI 三态结论。
- 可移植性硬约束（Junction + pnpm 硬链接）**没有任何卷类型前置检查**，而产品定位明确支持 U 盘/移动硬盘。
- **"吸收上游前必读"的那份同步基线自己已过期**（F-27）：快照仍写 `1.0.66 / 0.1.6-alpha.2 / ddefc45f`、矩阵"16 项 / Codex UI 1.1.14"，实况是 `1.0.76 / 0.1.7-rc.2 / 477b4f42`、15 项 / `1.1.18`；同一份 B 档文件里 `dsh-better-sidebar` 的注释（锁 0.18.0）与矩阵值（0.21.1）也互相打架（F-28）。这正是该文件自己警告过的"会产生漂移的副本"。
- **工具链本身有个假阴性陷阱**（F-20）：`grep`/ripgrep 跳过 `.gitignore` 覆盖的目录，而 `Data/` 整体在忽略列表里 ⇒ **任何"对 `Data/**` 目录级搜索后说没有 X"的结论都不可信**（本轮已用对照实验证实）。这条影响的是审核与开发两边的取证可靠性，不只是本报告。

**建议处置顺序**：先修"文档判据漂移 + 活动槽无门禁 + `Data/**` 搜索假阴性"这三件结构性问题（都低成本、都能防复发），再谈三项对齐的批量回填与插件侧小缺陷。
