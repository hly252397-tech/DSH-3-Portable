## 一、结论先行

**版本与制品这一层是自洽的、可信的；不合规集中在"文档事实源"和"门禁覆盖不全"两类，而不是实现本身。**

- **但有 6 条真问题**，其中 2 条会实际误导后续开发或让"假绿灯"通过；另有 1 组企业级门禁本来就如实标着"未满足"，审核确认它们**至今仍未闭环**。

## 二、发现（按严重度）

### 🔴 H1　两份强制必读文档的实现基线是错的（0.1.2-rc.1 / 0.1.6-alpha.2 vs 实际 0.1.7-rc.2）

**违反**：`AGENTS.md`「官方兼容性双基线」——"以便携版实际内置的 `@deepseek-ai/dsh` 版本、导出和类型声明为准"。

**证据**

- `docs/03-技术架构/DeepSeek-Harness-插件开发规范知识库.md:6`：「实现适用版本：`@deepseek-ai/dsh 0.1.2-rc.1`（本便携版内置运行时）。官方最新审查版本为 `0.1.5-alpha.1`」——**落后实现基线 4 个版本、落后审查基线 2 代**，且这是 `AGENTS.md` 要求"改动前必读"的第 2 位文档。
- 同文件 `:25` 又写"即使内置运行时已到 `0.1.6-alpha.2`"——**同一份必读文档内部有三个互不一致的版本号**。
- `docs/03-技术架构/DeepSeek-Harness-官方兼容基线.md:46`「代码必须以**已内置** `0.1.6-alpha.2` 的实际导出和类型声明为准」——被本文档自己的表头（`:9` 实现基线 `0.1.7-rc.2`）和 `:11` 审查版本取代，但正文未同步。
- 对照组：该文档自身的过期处理规则是"按日审阅记录一律保持原样不改写，过期判断以当前节为准"（`:91`）——`:46` 属于"现行判定条款"而非历史记录，不在豁免范围内，且它正是审查者会照着读的那一行。

**为什么是真问题**：这三处是**给开发者的判据**，不是历史账。照 `知识库:6` 写的"实现适用版本 0.1.2-rc.1"去核对 API，会把 0.1.7-rc.2 已存在的接口误判成"不存在"，或反过来把旧写法当合规。本仓已因同类"文档过期判据"吃过一次亏：`官方兼容基线.md:90` 记载 2026-09-13 的 I024 迭代就是被过期表述误导（以为实现基线是 `0.1.2-rc.1`）。

**为什么没被拦住**：`test/quality-gate.test.ts` 的版本一致性用例只覆盖三处——基线 JSON ↔ `package.json`（`:42`）、`OFFICIAL_DSH_VERSION` ↔ 测试常量（`test/bundled-plugins.test.ts:75`）、基线 MD 的章节词（`:47-49`）；**知识库与基线 MD 的版本表格没有任何机器校验**，所以它们可以随意漂移。

**建议**：把"文档声明的实现基线版本"纳入机器门禁（例如新增断言：知识库首段版本号 === `OFFICIAL_DSH_VERSION`、基线 MD 表格两行 === 同一常量），并同步修正上述三处；历史审阅记录保持不改写。

### 🔴 H2　官方基线校验脚本不校验活动运行时槽，"实际实现基线"没有任何门禁

**违反**：`AGENTS.md`「官方兼容性双基线」把"实际内置版本"定为判定依据；`质量门禁 §1.1 第 1 条`要求每个功能开工前跑该脚本。

**证据**

- `scripts/verify-dsh-official-baseline.mjs:9` 读的是 `Data/Runtime/dsh-runtime/...`（**历史回退目录**），`:11` 读了 `Data/Runtime/Harness/current.json` 却**只用来判断"存在活动槽就放过回退目录落后"**（`:83-92`），从不读取活动槽里的 `package.json` 版本。
- 文档自己也承认："该脚本**不检查活动运行时槽**——活动槽以 `current.json` 为准"（`官方兼容基线.md:37`）。

**后果**：用户可以处在一个"脚本 PASS / 声明 0.1.7-rc.2 / **实际跑的是别的版本**"的状态而无人发现——正是 `AGENTS.md` 坑清单里"清单 `0.1.5-rc.2` + `node_modules` `0.1.2-rc.1`"那类坏槽要防的事（那次靠 `reconcileOfficialRuntimeManifest` 兜底，但兜底只在工具被调用时发生）。当前实机是好的（`current.json` = `0.1.7-rc.2`），**缺的是"保持它好"的检查**。

**建议**：在脚本里新增一步——读 `Data/Runtime/Harness/current.json` → 拼活动槽根 → 校验槽内 `node_modules/@deepseek-ai/dsh/package.json` 的 `name`/`version` 等于 `baseline.bundled.dshVersion`；不一致即红灯。这属于"门禁补强"，不是新功能。

### 🟠 M1　供应链：registry 签名只记录不验证（企业级门禁第 1 条未达标）

**证据**：`src/harness-update.ts:402-403` 只做 `const signatureKeyIds = …; if (signatureKeyIds.length === 0) throw`，随后 `:436/:448` 把 keyid **存进候选记录**，全程没有对 `dist.signatures[].sig` 做任何密码学验证，也没有钉住允许的签名公钥。真正的完整性依据是 `:396` 的 `sha512-` integrity 与 `:425` 与受信清单的比对。
**自认**：同文件 `:106` 注释"后续 CI 应把该数据替换为 Ed25519 签名的外部运行时清单"。
**判定**：`质量门禁 §0.2 第 1 条`要求"校验发布身份、包名、版本、大小、依赖闭包与**签名或可验证证明**"。当前满足"固定不可变版本 + 哈希 + 允许列表来源"，**不满足**"签名验证"。文档状态已如实标注"企业级候选实现；尚未宣称企业级投产"（`企业级自动更新方案.md:3`），因此不构成虚假声明，但**不得**据此宣称供应链安全达标。
**建议**：要么把 keyid 与公钥白名单绑死并真正验签，要么把该限制明确写进企业级门禁的"未满足"清单（第 3 节已列 3 项，此项建议补成第 4 项）。

### 🟠 M2　官方审查基线已落后于本轮人工复核（联网门禁无法执行，禁止宣称"符合官方最新要求"）

**违反**：`AGENTS.md`「上游同步与便携保护基线」——保护文件三档清单是"吸收上游前必读"的保护网。

### ⚪ L1　`AGENTS.md` 点名的入口技能不存在，退回手工流程无痕迹

`AGENTS.md` 首段要求"先加载 `dsh-dev-spec` 技能"，实测该技能不可用（工具返回 unknown/不再可用）。手册里写了"技能未注册时才按本文件手工执行"，因此不是错误，但没有证据表明手工路径被实际执行；建议要么注册该技能，要么把『手工执行』的留痕要求写进门禁（例如 GCC 记录必须引用本次跑过的基线命令输出）。

### ⚪ L2　空 `catch` 未点名吞掉的错误（官方写作铁律）

官方 `AGENTS.md`（2026-09-19 审阅记录 `官方兼容基线.md:59`）要求"空 `catch` 必须点名吞掉的错误"。实测 `src/` 内有 3 处空 catch：

- `src/main.ts:829`：`try { unlinkSync(handoffReadyFile) } catch { }` —— 交接文件清理失败被静默吞掉，**没有任何注释说明吞的是什么**。
- `src/main.ts:846`：`appendFileSync(restartAuditPath, …)` 失败被吞（有"降级"上下文，但未点名错误类型）。
- `src/plugin-seed.ts:321`：`JSON.parse(key)` 失败被吞（同目录 JSON 解析惯用法，风险最低）。

建议按"要么点名错误，要么写出为什么可以吞"的写法补齐；L2 级别，不阻塞。

### ⚪ L3　重启交接只用超时兜底，失败无诊断

`src/main.ts:811-819` 用 `cmd /c start` 拉起 PowerShell 启动器且 `stdio: 'ignore'`，`:824-828` 只靠 10 s 轮询 `handoffReadyFile` 超时抛错。启动器若在 `Publish-HandoffReady` 之前失败，日志里**只有一句"等待便携启动器接管超时"**，没有启动器侧的失败原因（`restart-handoff.log` 只在 `scheduleAppRelaunch` 的 catch 里写，`:844-846`）。建议在超时分支补一条提示指向 `Data\Updates\Desktop\launcher.log`，或在 spawn 前预写意图记录。
