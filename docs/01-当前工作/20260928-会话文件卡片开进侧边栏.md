# 2026-09-28 会话文件卡片开进侧边栏（fileLink 拦截）

## 现象（用户报告 + 亲测复现）

会话消息里点击文件路径卡片（官方 ToolRow 的 `<hash>_fileLink` 按钮，如 `20260928-Data-Temp 只读盘点.md`），弹出一个**独立 OS 窗口**（Windows 默认程序打开 .md，带最小化/最大化/关闭按钮的文档查看器）——不是右侧定制工作台（better-sidebar）的编辑器卡片。

用户同时指出交付纪律问题：上一轮外链修复只做了合成探针验证（拦截判定层），未亲自模拟用户操作方式做端到端验证。本轮全程按"真实点击 + 窗口对比"验证。

## 根因（动态取证链）

- better-sidebar 既有 `workspaces.openPath` wrap（`registerOpenPathInterception`）注释声称它是"聊天侧文件打开的唯一漏斗"（tool-row path links / produced-files row / prose mentions）——**在 0.1.7-rc.2 上不再成立**。
- 亲测取证（hj broker 注入，Data/Temp/attachment-click-probe.mjs v1–v7）：
  1. 真实 `.click()` 点击 `.md` fileLink → **页内无浮层、无新 tab、URL 不变**；
  2. `window.open` 未被调用；`fetch` 仅 pua 轮询噪声；**WebSocket 出站为零**；
  3. prefs 全默认（两家园 settings 无显式记录：`interceptOpenPath=true`、editor 卡启用、未 suspended）。
- 结论：官方聊天视图的 file opener（web-frontend 注入 ChatView 的 `openFile` prop）**绕过 `workspaces.openPath`**，直接把文件交给 Host OS 打开（openFile 实现被压进 `dsh-web-frontend/dist/assets/index-*.js`，无 openPath 调用可寻）。

## 修改（双家园 src + bundle 双层）

better-sidebar 新增 `registerFileLinkInterception`（`src/client/link-intercept.ts` + `lib/client.js`，注册于 `src/client/index.tsx` apply 的 `file-link interception` effect）：

- **DOM 捕获拦截**（document capture click，与既有 link-intercept 同款模式）：命中 `button[class*="fileLink"]`（css-module 哈希前缀随官方构建变化，`fileLink` 后缀稳定）且按钮文本是绝对路径（Windows 盘符 `/^[A-Za-z]:[\\/]/` 或 POSIX `/^\/[^/]/`）→ `preventDefault + stopPropagation`（React root 委托拿不到事件，官方 Host-OS 打开完全被替代）→ `openSidebarFile(ctx, store, sessionId, path)` 开进编辑器卡片（路径解析/去重/浏览器互斥收层由既有实现承担）。
- **门控**与 openPath wrap 同款：`!suspended && interceptOpenPath !== false && tabsEnabled['editor'] !== false`；**Ctrl/Cmd+点击始终绕过**（`isPlainLeftClick`，官方 OS 打开保留可达）。
- 旧家园三文件同步（link-intercept.ts / index.tsx / client.js，md5 一致，`--check` 通过）。

## 亲测验证（真实用户操作方式）

探针 `Data/Temp/verify-filelink.mjs`（真实 `.click()`）+ desktop-control 顶层窗口对比 + 证据 `customizations/ui/evidence/filelink-intercept-20260928.json`：

## v2（同日用户复测仍弹官方窗口 → 两处补修）

**用户实测打脸 v1**（合成验证通过但真实点击不生效），按"亲自模拟用户操作方式"重测，两处独立问题被逐层剥出：

1. **测试方法缺陷（我的）**：v1 的 OS 级点击坐标被 **ZCode 自身窗口遮挡**（点击点落在 ZCode 上，事件从未到 DSH），且 DSH 窗口在测试间被移动（旧坐标失效）。修正方法论：**每次点击前实时取窗口 rect + 遮挡检查**；事件追踪探针（capture/bubble 记录器 + `dispatchEvent` 返回值）证明点击到达与拦截与否。
2. **功能缺陷（真因）**：官方 `fileLink` 类按钮有**两种形态**——ToolRow 路径按钮（textContent=完整路径，v1 已拦）与 **fileMention 短名 chip（textContent=纯文件名如 `20260928-xxx.md`，完整路径在 `title` 属性、正斜杠）**。v1 的 `isFilePathText` 只认绝对路径文本 → 短名 chip 全部放行（用户点的正是这种）。修复：`filePathOf(button)`——**title 优先**（绝对路径判定），textContent 兜底；路径交给既有 `openSidebarFile`（内部 resolveSidebarPath 处理）。

**终验证据**（`customizations/ui/evidence/filelink-intercept-20260928.json` v2）：
- 合成点击 3/3 被拦（含 2 个短名 chip），md tab 开卡；
- **OS 级真实鼠标点击**短名 chip（事件 `trusted:true`、target=`_fileMention_1ypvv_85 _fileLink_1ypvv_59`）：capture 阶段 `prevented:true`（bubble 被 stopPropagation 阻断=官方 Host-OS 打开完全被替代），**activeTab=该文档编辑器卡**；
- 点击前后顶层窗口清单一致（无系统文档程序弹出）。

附带修正：src/client/link-intercept.ts v1 的 heredoc 转义坑（`[\/]` 丢反斜杠）在 v2 重写时一并修复。
