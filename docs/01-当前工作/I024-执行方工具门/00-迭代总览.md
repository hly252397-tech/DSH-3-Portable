## 0. 需求与方案选择

用户先要求"写进 DSH 底层"，已先完成两层**文本约束**（同批改动，见 §5）：

1. `$DSH_HOME/AGENTS.md`（用户全局指令，官方 `dsh-agent-instructions` 的全局加载位，覆盖本机全部会话）
2. 仓库根 `AGENTS.md` 增加「智能体行为边界」一节

但文本指令是**软约束**（长会话与压缩会稀释）。用户确认追加**工具层硬门**——本迭代实现。

### 为什么门禁真的咬得住（实测依据，不是推测）

活动槽 `Data/Runtime/Harness/slots/0.1.5-rc.2-fd316e6b895e48c1` 实读
`node_modules/@deepseek-ai/dsh-tool-ask-user/lib/index.js` L18–L65：

- `questions` 是 required 数组，但 **`options` 是可选字段**（无 `required`、无 `minItems`）；
- `questions` **没有数量上限**；
- 官方 README 对推荐标注只是"建议"（"If you recommend one, put it first and append `(Recommended)`"）。

→ 现有 schema 允许模型合法地抛出「你看怎么办？」式开放式问题、单选项假选择、或挤牙膏式连问。
这正是用户要禁止的"指挥用户"，门禁非冗余。

## 2. 实现

**策略（全部可配，见 `Config`）**：

| 规则 | 默认 | 目的 |
|---|---|---|
| `gatedTools` | `['ask_user_question']` | 门禁对象 |
| `minOptions` | `2` | 禁止开放式甩问 |
| `maxQuestions` | `4` | 一次问全，不挤牙膏 |
| `requireRecommendedOption` | `true` | 必须给建议（推荐项放第一 + `(Recommended)`） |
| `recommendedMarkers` | `(Recommended)`/`（推荐）`/`推荐`/`Recommended` | 标注识别 |
| `exemptPatterns` | 密码/验证码/登录/扫码/password/captcha… | **正当豁免**：凭据/身份类提问按用户全局规则允许找用户 |

**流水线纪律**：`const decision = await next()` → 上游非 `allow` 原样返回 → 仅对 `allow` 且命中 `gatedTools` 的调用做校验 → 不合规返回 `{kind:'deny', reason}`。
上游 `deny`/`ask` **单调不可逆**（测试覆盖）。

**铁律 1 论证**：本插件不新增模型可见输入。`deny` 由注册表物化为该次调用的 error 结果
（`dsh-tools/lib/types/index.d.ts` L413–L415「`deny` materializes an error」），随既有 `tool/result`
会话事件落盘，可从会话日志重建 → **无需扩展 `SessionEventMap`**。

**挂载**：沿用 house pattern（与另外 6 个本地插件一致）——`link:local\dsh-agent-boundary` 依赖
+ `dsh.profile.bundles` 条目 + `node_modules` junction（不跑 pnpm，避免触发 AGENTS.md 记录的物化地雷）。
未采用 profile 级 `cordis.patch.yml` 绝对路径方案：该文件被 `ensureDesktopBridgePatch`
（`src/desktop-host.ts:348-353`）在每次启动做文本级重写，虽然会保留外来内容，但把门禁挂到会被改写的文件上不如 bundle 层稳。

### 红灯 2：官方基线脚本 —— 两段误判，均已纠正

**误判 ①（我的报告有错）**：最初报的是"打包回退槽缺 `@deepseek-ai/dsh`（tar 退出码 null）"，并据此说打包制品可能坏了。
真相：当时 DSH 文件策略为 `workspace-write`，受限沙箱不允许子进程管道 stdio，脚本里 `spawnSync('tar', …)`
直接起不来（`status=null`），被脚本渲染成"缺少官方包"。策略放开后**离线检查立即 PASS**：
`打包回退运行时版本 0.1.2-rc.1 与桌面清单一致`——即**打包制品没有问题，是我的运行环境造成的假红灯**。

**误判 ②（真红灯但性质判断需修正）**：策略放开后仍失败两次，报 `无法核对官方 HEAD：timeout / fetch failed`。
定位过程：复刻同参请求 3/3 成功（0.1–1.1s）→ 逐字复制脚本加 `error.cause` 后仍超时且 `cause=n/a`（即
`AbortSignal` 到点中断）→ 跳过 tar 段与放宽到 60s 的两个二分副本**均 PASS**，60s 副本实测 HEAD 仅 **654ms**。
结论：`api.github.com` 在本机存在**间歇性卡顿**，撞上脚本 15s 硬超时即误报红灯（当时连 3 次误报，随后连 4 次全绿）。

**处置（唯一一处代码改动）**：把 `scripts/verify-dsh-official-baseline.mjs` 的两处联网超时
从 `15_000` 提为共享常量 `onlineTimeoutMs = 30_000`，并在代码注释里写明上述实测依据。
`test/quality-gate.test.ts` 只钉住"脚本必须请求官方 API 与 raw 地址"（L50–L51），未钉超时值，改动不破坏契约。
加固后 `--online` 连跑 3 次 **PASS / online=verified**。
