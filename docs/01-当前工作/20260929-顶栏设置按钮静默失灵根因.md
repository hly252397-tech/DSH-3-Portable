# 顶栏「设置」按钮静默失灵——真因是本轮菜单去重的自伤（2026-09-29）

配套：[20260929-顶栏菜单去重.md](20260929-顶栏菜单去重.md) §9 是本次事故在原文档里的更正条目。本文是完整取证记录。

## 1. 现象

1.0.77 候选槽激活（`launcher.log` 10:12:23 启动候选、10:14:07 验证通过，`pointer.json` current=1.0.77）后，
用户报「顶栏『设置』点了没反应」。CDP 在实机上稳定复现。

## 2. 根因

`src/main.ts` 的动作准入白名单是从**菜单表**推出来的：

```ts
const shellActionIds = new Set<string>(SHELL_ACTIONS.map(action => action.id))
```

而 `ipcMain.handle(SHELL_IPC.action)` 的第一行就是：

```ts
if (typeof id !== 'string' || !shellActionIds.has(id)) return
```

**不抛错、不记日志、不写任何东西，直接返回。**

菜单去重把 `settings` / `desktop-settings` / `check-updates` / `whats-new` / `feedback` / `reload`
六个 id 从 `SHELL_ACTIONS` 里删掉，白名单随之从 33 项缩到 27 项。顶栏 `#settings-btn` 的
`data-action="settings"` 于是被静默丢弃：**控件在、`executeShellAction` 的分支在、唯独进不去。**

**这是 2026-09-29 菜单去重那一轮自己引入的回归，与内核 0.2.0-rc.1 无关。**
去重文档 §4 写的「下线条目不等于删除能力……若连带删了 id，`main.ts` 的分支会立刻编译不过」
只对**分发分支**成立，对**运行时准入白名单**不成立——后者是运行时数据，编译期完全看不见。

## 3. 排除过程

逐层二分，每层都有可复现证据。目的是避免把锅甩给内核、再花几小时做无效的跨版本对照。

| 假设 | 证伪方式 | 结果 |
|---|---|---|
| 客户端不监听 `dsh-action` 的 settings 分支 | 改走「壳直接驱动 DSH 页面」后仍无反应 | 假设不成立（但该改动本身是对的，予以保留） |
| 合成 `.click()` 被 `-webkit-app-region:drag` 吞掉 | 改用 CDP `Input.dispatchMouseEvent` 发**可信**点击 | 事件确实到达按钮：`bar-pd:IMG, pointerdown, mousedown, mouseup, click` |
| `executeJavaScript(TOGGLE_…)` 抛错被 `.catch(()=>'unavailable')` 吞掉 | 按主进程同构方式重建脚本文本，在 DSH 页内联执行 | 返回 `'opened'`，设置页正常打开（19 个导航项） |
| 主进程 IPC 整体断了 | 同一页调 `dshShell.action('find')` | 设置页被正常关闭 ⇒ IPC 通、`dshView` 活、`executeJavaScript` 可用 |
| 动作 id 不在准入白名单 | 读 `SHELL_ACTIONS` 实际内容 | **6 个 id 全不在表里** ⇒ 命中 |

**决定性对照**：`action('find')` 能关设置页、`action('settings')` 不能。同一个 IPC 通道、
同一个 `executeShellAction`、同一个 `dshView`，唯一差别是分支——而分叉点在分支**之前**的准入检查。
这一条就把范围锁死在「id 白名单」，无需再碰内核。

补充证据：给 `.dcu-settings-trigger` 的 `click` 打包装探针后从外壳发 `action('settings')`，
探针**一次都没被触发**，证明脚本根本没走到 `trigger.click()`（而不是 click 了但 React 没响应）。

## 4. 顺带查明的一个独立缺陷（本轮不修，只登记）

codex-ui 1.1.18 的设置页关闭逻辑：

```js
const close = useCallback(() => {
  if (exitAnimation.current !== null) return          // 闩锁
  const finish = () => { exitAnimation.current = null; setOpen(false); setQuery('') }
  const animation = element.animate([...], { duration: 140, fill: 'forwards' })
  exitAnimation.current = animation
  animation.onfinish = finish                          // 只在正常结束才清闩锁
}, [])
```

**窗口最小化时** Chromium 挂起渲染生命周期：实测 `document.visibilityState === 'hidden'`、
3 秒内 **0 次 rAF**，动画 `playState` 变成 `finished` 但 `onfinish` **永不派发** ⇒ 闩锁永久锁死
⇒ 设置页再也关不掉，只能刷新页面。窗口恢复（`visible`、rAF 稳定 16ms）后同一路径一切正常。

这是第三方包（npm `@michengai/dsh-codex-ui`）的实现问题。按「内核/插件解耦、桥梁式连接」方针，
不直接改包，只登记；将来升级 codex-ui 时复查是否已修。

**取证纪律插曲**：本轮一度把"最小化导致的 onfinish 不派发"当成根因写进了结论，
差点把一个自造的伪 bug 当成内核问题继续追。判据是 `document.visibilityState`——
任何 rAF / 动画 / 渲染类断言之前必须先确认页面可见，且实机窗口的最小化状态要与
`list_windows` 的 `minimized` 字段对齐。

## 5. 修法

1. `src/shell-actions.ts` 新增 `SHELL_ACTION_IDS`——与菜单表**分开维护**的完整可分发 id 白名单，
   注释写明事故来龙去脉。
2. `src/main.ts:126` 改用 `SHELL_ACTION_IDS`（同时移除已无用的 `SHELL_ACTIONS` import）。
3. 菜单表的文档注释补一句警告：下线条目仍要过 `SHELL_ACTION_IDS` 白名单，"不查菜单表"≠"不受菜单表影响"。

## 7. 教训

**「菜单表」「可分发动作表」「快捷键表」是三件事。**

凡是"有 UI 入口的动作"，其 id 必须登记在**与 UI 呈现解耦**的注册表里。用呈现层的清单当准入白名单，
去重时就会连带静默杀掉入口——而且**不会报任何错**，因为白名单检查本身的语义就是"静默丢弃"。

护栏测试断言一个恒真的常量，是这类事故最常见的共犯：它让人以为自己覆盖了那条路径。
