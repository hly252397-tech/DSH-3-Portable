## 缺陷一：`test-build-freshness` 是**假失败**（机器负载敏感）

`test/test-build-freshness.test.ts` 原来这样构造"陈旧"场景：

```ts
await put('src/value.ts', 'export const value=1', 5000)     // 5 秒前
await put('dist/test/example.test.js', 'export {}')
assert.throws(() => assertFreshTestBuild(root), /missing/)
await put('dist/src/value.js', 'export const value=1', 8000) // 8 秒前 → 期望判定为"陈旧"
assert.throws(() => assertFreshTestBuild(root), /stale/)    // ← 这里挂
```

而 `assertFreshTestBuild` 判陈旧用的是**绝对 mtime 比较**：

```js
else if (statSync(output).mtimeMs < Math.max(statSync(input).mtimeMs, configTime)) problems.push(`stale: …`)
```

于是断言成立的前提是：**从写 `src/value.ts` 到写 `dist/src/value.js` 之间，真实耗时 < 3 秒**。
而这中间夹着一次 `assertFreshTestBuild`，它内部 `spawnSync` 了一个真实的
`tsc --showConfig` 子进程。

**实测**：机器负载高时该子进程超过 3 秒（800 用例并发 + 杀软扫盘），后写的 `dist`
反而比先写的 `src` 更新 → 判定翻转 → `assert.throws` 报 `Missing expected exception`。
单独跑该文件时子进程很快，所以**单跑全绿、全量跑偶发红**——典型的负载型 flake。

**修法**：年龄差从「5s / 8s（差 3 秒）」改成「2h / 4h（差 2 小时）」量级。
任何子进程耗时都不可能反转比较结果，从根上消除对机器负载的敏感。

> 教训：凡是用 **mtime 差值**构造测试场景、又在中途跑真实子进程的断言，
> 余量必须远大于最坏情况的子进程耗时，否则它测的是机器负载而不是被测逻辑。

## 缺陷二：测试污染实机状态（这才是那个自旋清理器的来源）

追查"谁在 10:53:51 启动了一个回收清理器"时发现：**是本会话自己跑的全量测试**。

`test/prepare-runtime.test.ts` 有一条用例调用**真实的** `removePreparedPath`，
而目标与回收区都硬编码在项目内：

```ts
const recycleRoot = join(projectRoot, 'Data', 'Temp', 'prepare-recycle')   // 硬编码
const probe = join(projectRoot, 'Data', 'Temp', `recycle-probe-${Date.now()}`)
```

`recyclePreparedPath` 成功后 `startRecycleSweeper()` 会 `spawn(process.execPath, ['-e', …], {detached: true}).unref()`
——**脱离进程树**的清理器比测试进程活得久。测试跑完、临时目录消失，清理器却还在对着
**实机** `Data\Temp\prepare-recycle\` 干活。

这违反 AGENTS.md「测试禁止读取/写入实机 `Data/` 产物」（CI 是全新检出，本机绿、CI 挂的那类问题）。

**修法**：
1. `recycleRoot` 改为**惰性函数**并支持 `DSH_RECYCLE_ROOT` 覆盖。
   （必须是函数不是模块级 const：测试是在模块已被 import 之后才设这个环境变量的，
   加载时求值的话测试设了也来不及生效。）
2. `recyclePreparedPath` 的"只回收项目内路径"守卫，在 `DSH_RECYCLE_ROOT` 显式指定时放行——
   否则测试把回收区指到 `tmpdir`(C:) 而目标在 G:，跨卷 `rename` 必失败、那条用例永远红。
3. 用例改为在 `mkdtemp` 出来的沙箱里回收，沙箱随用例销毁，清理器失去回收根后自行退出。
4. 加 `assert.match(source, /DSH_RECYCLE_ROOT/)` 护栏，防止有人把可覆盖性删回去。

**验证**：修后跑该用例，实机 `Data/Temp/prepare-recycle/` **不再出现新心跳**
（修复前 6 分钟内必有 `.sweeping`）。

## 缺陷三：P2 死结的真正根因——②和③互相拆台

`RECYCLE_CLEANER` 里那"两处修复"是矛盾的：

```js
c.on('exit', code => { if (code !== 0) pending = null });                    // ②
setTimeout(() => { if (pending && existsSync(…)) { if (++failCount >= 3) {   // ③
  renameSync(…, '.failed'); pending = null; failCount = 0 } } }, 15000)
```

③ 想做的是"同一桶连续失败 3 次就改名 `.failed` 隔离出队列"，但：
被第三方杀软持句柄锁的 PE 文件（如 `node.exe`）让 `rmSync` **瞬间**抛错退出
⇒ ② 立刻把 `pending` 清空 ⇒ 15 秒后 ③ 的 `if (pending && …)` 判假
⇒ `failCount` 永远归不了 1 ⇒ **桶永远进不了 `.failed`**
⇒ 每 5 秒 tick 一次、重新 `spawn` 一次 `rmSync` 去打同一个锁死的文件。

**表现**：心跳一直新鲜、删除量恒为 0、两小时零删除。这就是 AGENTS.md 里记的
「心跳在跳、两小时零删除」现象的**代码层真因**——此前 2026-09-29 那次"修复"只补了 ①，
②③ 互相抵消，等于没修。

**本次现场证据**：
- PID 9044（sweeper，PPID 62976 已退出）命令行逐字复现上述缺陷；
- PID 82260 是它反复 spawn 的 `rmSync` 子进程，目标 `…\prepare-recycle\zz-locked-node-exe`；
- `.sweeping` 心跳 10:53→10:57 持续刷新，桶始终删不掉；
- 该桶内容是 100 MB 的 `node.exe.xxx`（2026-09-21），改名后删除报 EPERM = **锁跟文件走**。

**修法**：把失败计数搬到 `exit` 回调里当场完成，按桶名累计，成功即清零：

```js
c.on('exit', code => {
  const b = pending; pending = null;
  if (code === 0) { failName = ''; failCount = 0; return }
  if (!b) return;
  if (b === failName) { if (++failCount >= 3) { try { renameSync(root/b, root/b+'.failed') } catch {}
                                          failName = ''; failCount = 0 } }
  else { failName = b; failCount = 1 }
});
```

②「不等 2 小时」与 ③「失败隔离」不再互相拆台。**根治仍需在杀软面板给 `Data\Temp\`
加信任/排除**——代码侧只保证不被无限重试。

**护栏**（`test/prepare-runtime.test.ts` 新增用例）断言四条结构性事实：
失败计数不在延迟计时器里、计数发生在 `exit` 回调、连续 3 次改名 `.failed`、成功即清零。

## 与止损纪律的关系

AGENTS.md 止损纪律第 7 条要求"构建与候选激活不并发，先让 `Data/Temp/prepare-recycle/` 排空"。
本篇正是那条规则**第一次真正被执行**的场景：自旋的清理器若与构建并发，会让候选槽冷启动
撞上持续盘 I/O，症状与"候选槽损坏"几乎一样。清理顺序：杀 sweeper → 改名隔离锁死桶 →
删 `.sweeping` → 确认 `DSH_RECYCLE_HEARTBEAT` 进程数为 0 → 才允许开始构建。
