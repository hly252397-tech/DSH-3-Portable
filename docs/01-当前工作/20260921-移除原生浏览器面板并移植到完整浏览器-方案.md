# 移除原生浏览器面板 · 移植到完整浏览器 —— 方案（2026-09-21）

> 用户原话：「选择彻底移除，并把功能移植到我加入的完整浏览器上，先给我方案。」
> 本文件是**方案**，不是执行记录；执行后按仓库规矩追加「改法 / 证据 / 门禁」并把本方案标为已实施。

## 0. 目标与非目标

**目标**：产品里**不再有原生浏览器面板**（Electron `WebContentsView` 那一层），因此"白面板 / 幽灵面板 / 状态不同步"这一整类故障**从根上消失**；侧栏浏览能力与智能体操作网页的能力**移植到完整浏览器**上。

**非目标**：不改 ERP 系统本身；不动「物料录入工作台」「宏建云」等业务功能；不改官方插件之外的运行时。

## 2. 硬约束（实测，不是推断）

1. **ERP 永远不能内嵌**：`login.hongjian.com` 下发
   `X-Frame-Options: ALLOW-FROM *.hongjian.com http://5t7.net` 且
   `Content-Security-Policy: frame-ancestors *.hongjian.com http://5t7.net`。
   DSH 页面来源是 `http://127.0.0.1:<port>` ⇒ 不在白名单 ⇒ **任何 iframe 方案都显示不了 ERP**。
   （本地手册 8765 无相关响应头 ⇒ 可内嵌；注意它的 `HEAD` 返回 501，探测必须用 `GET`。）
2. **无法给"已经在跑的 Chrome"接 CDP**：Chrome 必须带 `--remote-debugging-port` 启动才能被驱动；
   因此完整浏览器要么用**盘内 Chrome（独立 profile，登录一次持久）**，要么用带调试开关重新启动的 Edge。
3. **跨源 iframe 不可脚本化**：若把外部站点放在 iframe 里，DSH 页面**读不到**它的 DOM（无法再像现在这样"注入 JS 操作网页"）。
   本地站点可通过"同源化"解决（见 P4）。

## 3. 目标架构（三通道，按站点能力自动分流）

```
点击/打开链接
   │
   ├─ ① 本地/可内嵌  → 侧栏卡片内 <iframe>（P4 同源化后可脚本化）
   │                    无原生层 ⇒ 无白面板；智能体可直接读写 DOM
   │
   ├─ ② 禁止内嵌（ERP 等） → 盘内完整 Chrome（CDP 常驻，独立 profile）
   │                    侧栏卡片变成"控制台"：标签清单 / 地址 / 截图 / 切到前台
   │                    智能体走 CDP（Runtime.evaluate…），接口名与现在保持一致
   │
   └─ ③ 兜底 → 系统浏览器（既有 openExternal 不动）
```

## 4. 分阶段实施（每阶段独立生效、独立回滚）

### P1 · 页面侧：切到 iframe，禁嵌站点外派（本地插件，**无需构建、改盘即生效**）
- `local/dsh-better-sidebar`：
  - 把卡片渲染从"原生宿主 div"改为 **iframe**；用已存在的 `embeddabilityOf()` + `browser.probe` 决定；
  - `blocked` 分支不再创建原生视图，而是**调 P2 的宿主服务在完整浏览器打开**，卡片显示控制台（标签/地址/截图/切前台）；
  - 删掉 `portable/browser-view.js` 的原生路径（保留文件与说明，改为不挂载）。
- 回滚点：还原该插件文件（junction，秒级）。
- 验收：手册在侧栏 iframe 内正常显示；ERP 卡片显示"已在外派浏览器打开 + 截图"；**全程无原生视图**（可用 `[data-native-browser-card]` 不存在来判定）。

### P2 · 宿主侧：完整浏览器服务（CDP）
- 新增宿主侧能力（放在 `local/dsh-hj-workbench` 宿主半侧或独立插件，端口沿用本机回环 + 仅本机可达）：
  `POST /api/browser/{open,activate,list,close,screenshot,exec}` → 内部走 CDP 到盘内 Chrome。
- Chrome 由服务按需拉起：`--remote-debugging-port=<固定> --user-data-dir=<便携盘>\Data\Browser\profile`（登录一次持久、**不碰用户其它浏览器 profile**）。
- **智能体通道保持接口不变**：`__dshAgentBrowser.exec/ensure/tabs` 换成走本服务（`ensure` 保留 2026-09-21 的"忽略 #锚点 + 内容活性检查"两条修法）。
- 验收：`ensure('http://127.0.0.1:8765/')` → `reused` 且能读到正文长度；ERP 页面能被打开、能读到标题；Chrome 进程被服务正确托管（不残留、不重复）。

### P3 · 外壳侧：拆掉原生面板（`src/` 改动，**需构建 + 重启**）
- 删除：`browserPanelView`、每标签 `WebContentsView`、7 个 `browserPanel*` IPC、`browser-panel-layout.ts`、preload 的 `browserPanel` 块、`shell-contract.ts` 对应项、`layoutDshView` 里浏览器相关分支、`saveBrowserWorkspace`/`restoreBrowserWorkspace`。
- 同步：`test/shell-ipc-contract.test.ts`、`ui-baseline`（better-sidebar / shell-contract 属受保护路径，需 `--record --note --evidence`）。
- 保留：`openExternal`（系统浏览器兜底）、`assets/browser-panel.html` 与 `browser-workspace.js`（**它是"完整浏览器"的外壳实现，本轮保留**；是否也退役另议）。
- 回滚点：候选槽 A/B（失败自动回滚）。
- 验收：应用启动无 `startup-error.log` 新增；侧栏卡片、链接点击、手册/ERP 两条路径全部走通。

### P4 · 本地站点同源化（可选但推荐，让"侧栏里能操作网页"保住）
- 由我的插件宿主半侧把本地站点（手册 `build_manual_html.py --serve` 的 8765、工作台 8975、导出的 HTML）**以 `/hj-browser/...` 前缀挂在 DSH 自己的 origin 下**；
- 好处：同源 iframe ⇒ 侧栏能内嵌显示，**且智能体可直接读写其 DOM**（跨源做不到），比现在的原生通道更强、更稳；
- 验收：侧栏 iframe 显示手册，且 `iframe.contentDocument` 可读到「宏建云 ERP 操作手册」标题与正文长度。

## 6. 风险与代价（说清楚再动手）

1. **UX 变化（不可消除）**：ERP 这类禁嵌站点，在侧栏里**只能看截图 + 控制**，交互必须在完整浏览器窗口里做 —— 这是站点 `frame-ancestors` 决定的。
2. **多一个常驻进程**：盘内 Chrome 常驻约 300~500 MB 内存；需明确"何时启动/何时回收"。
3. **我的通道要迁移**：`exec` 从 Electron IPC 换到 CDP，需重跑我历史上写过的浏览器操作脚本（接口名不变，行为要复验）。
4. **保护路径多**：better-sidebar 与 shell-contract 都在 `ui-baseline` 受保护清单里，改动必须走 `--record`，否则门禁红。
5. **工作量**：P1+P2 一轮（插件为主，改盘即生效）；P3+P4 一轮（构建 + 重启验证）；期间原生面板**先保留可用**，不一次性拆断。

## 7. 明确不做

- 不动 ERP 系统、不改 hongjian 域名下的任何配置；
- 不碰用户其它浏览器 profile（新开便携盘内独立 profile）；
- 不为了"少改"而保留"原生面板只在某些条件下启用"这种半吊子状态（那正是白面板的成因）。

## 9. Codex 评审结论（2026-09-21，经侧边栏浏览器咨询，回答 12,510 字）

**结论：不建议为了修生命周期 bug 而把 `WebContentsView` 整层删掉。**

关键理由（按重要性）：

1. **`frame-ancestors` 管不到 `WebContentsView`**：它不是 DOM iframe，而是主进程创建的独立 WebContents（等同顶层页面）。
   所以 ERP 在原生层里**本来就能用**——"ERP 不能内嵌"只约束 iframe 路线。
   把 ERP 迁到外部 Chrome，等于用「Chrome 进程 + CDP 会话 + profile 管理」一整套系统，去替换一个几十行状态机就能修的问题。
2. **A（把站点挂到应用自身 origin）是本方案最大风险**：同源 iframe 能碰 `parent.*`、`localStorage`、cookie，
   以及经 contextBridge 暴露的任何 Electron 能力 ⇒ 把"网页内容"升级成"应用权限主体"；
   通用反代还会背上 Cookie / 重定向 / Service Worker / WebSocket / Range / CORS / CSP 等一长串维护债。
   若要做，只能迁**可信本地静态内容**，并**分源**（独立 scheme 或独立端口）+ 显式 `postMessage` 能力白名单。
   （另：`X-Frame-Options: ALLOW-FROM` 已被现代 Chromium 忽略，真正起作用的只有 CSP `frame-ancestors`；
   Electron 理论上可用 `onHeadersReceived` 改响应头绕过，但 Codex 明确不建议动这条安全边界。）
3. **三个真 bug 都能在原生架构内根治**：
   - owner **lease + ACK 屏障**（hide/show 带 `revision`，Main 只接受最新 revision）⇒ 治白面板，**包括"收起瞬间一帧白"**；
   - **WebContents 健康状态机**（`did-fail-load`/`render-process-gone`/`unresponsive`/`destroyed`…）⇒
     治"URL 相同就复用"这个逻辑错误（应改为先验 tab/view/webContents 存活 + 健康态，再决定复用）；
   - **tab identity ≠ URL**：匹配用 `origin + pathname + search`（忽略 hash），导航保留完整 hash；
     hash-only 变化属 in-page navigation ⇒ 复用并导航，不新建。
4. 其他要点：不要用 `<webview>`（官方不推荐）；生命周期要区分「tab（WebContents 保留）」与「视图挂载（lease 释放）」——
   收起侧栏只释放视图，保留登录态、滚动位置与页面 JS 状态；若做 Chrome+CDP，要写成独立 `ChromeSupervisor`，
   单实例 + 独立 `--user-data-dir`（Chrome ≥136 对默认 profile 禁用 CDP）、`--remote-debugging-port=0` 并读 `DevToolsActivePort`、
   CDP `targetId` 不可当业务 tabId、崩溃恢复**不得自动重放提交类动作**、不要 `execSync`。
5. Codex 建议的终态 Router：**可信本地内容 → iframe；普通/受限网站（含 ERP）→ WebContentsView；
   只有必须真 Chrome 时 → Chrome/CDP；最后系统浏览器兜底。**

## 10. 用户新发现（2026-09-21）：浏览器不跟会话走

实测 + 代码证据：

- `src/main.ts` L243 `const browserTabs: BrowserTab[] = []` 是**主进程全局数组**；`sessionId` 全文件只用于通知，**从不参与浏览器标签**；
- 工作区持久化是**单份** `userData/shell/browser-workspace.json`；
- 而拥有它的卡片是**按会话**的 ⇒ 切会话时原生标签不切，页面会**串到另一个会话显示**；新会话若没有浏览器卡片，
  外壳仍按旧的 `browserVisible` 画面板 ⇒ 白 / 幽灵面板；
- 页面重载还会触发工作区恢复，把之后打开的标签清掉（本轮实测：ChatGPT 标签被清，只剩手册与其重复标签）。

**因此新增硬需求**：浏览器状态必须**按会话隔离**（至少 `Map<sessionId, Tabs>` + 每会话各自的活动标签；
视图租约绑定"当前会话的卡片实例"）。**这条无论最终走哪条路线都要做。**

## 11. 修正后的推荐路线（取代本文件第 4 节的 P1–P4）

- **R1 Router 接线**：把仓库里**已有但没接线**的"能否 iframe"判定接上（本地/可信静态 → iframe，其余 → 原生），
  并支持"明确站点 policy + 响应头探测 + 运行时失败回退"三级判定；一次 HEAD/GET 的探测结果**不作绝对真理**。
- **R2 原生层三修 + 会话隔离**（**推荐先做**；改动集中在 `src/main.ts` + 卡片插件；不迁 Chrome、不破坏 Electron 安全边界）：
  lease+ACK / 健康状态机 / hash 复用 / `Map<sessionId, …>`。
- **R3 外部 Chrome/CDP 作为独立模块**（仅当确有必要）：`ChromeSupervisor` + 第 9 节列的 CDP 纪律。
- **原 P1–P4（彻底移除原生层）降级为备选**：若 R2 完成后仍不满足，再在此 Router 基础上迁移，成本显著更低。

**Codex 原话（结论段）**：「我认为这是比'彻底移除原生层'风险小一个数量级的路线。」

## 12. 第二轮 Codex 评审（2026-09-21，经侧边栏浏览器咨询，回答 7,792 字）

**结论：不要继续扩页面侧 1.5s 对账；该收口的是主进程的 BrowserPanel 生命周期。**

优先级（Codex 原表）：

| 优先级 | 方案 | 可靠性 | 定位 |
|---|---|---|---|
| P0 | ⑤ 主进程 **Session-scoped lease + 状态机 + renderer 生命周期撤销** | ★★★★★ | 根治 |
| P0 | ③ **显式 visible + bounds 协议**，ACK 后再做收起动画 | ★★★★★ | 正常生命周期主协议 |
| P1 | ② 独立 heartbeat + TTL（1s / 3.5~5s） | ★★★★☆ | 异常兜底（保险丝，不是电源开关） |
| P1/P2 | ① raw bounds 几何判据（**先判交集再 clamp**） | ★★★☆☆ | 漏报兜底 |
| P3 | ④ 只读 IPC 暴露 owner 给页面对账 | ★★☆☆☆ | 临时补丁，不建议长期保留 |

**P0 ⑤ 的核心 invariant**：*没有一个当前活跃 session 的有效 lease，WebContentsView 就绝不允许 visible。*
（而不是现在的"没人告诉我 hide，所以我继续 visible"——**这是整个 bug 的根**。）

- 把 `browserVisible / browserPanelOwner / browserPanelBounds` 合成一个 presentation state：
  `{sessionId, owner, generation, visible, bounds, lastHeartbeatAt, seq}`，外加主进程的 `activeSessionId`；
- 只有 `sessionId === activeSessionId && owner === currentOwner && generation === currentGeneration && visible && bounds 有效` 才允许上屏；
- **会话切换**：`onActiveSessionChanged` 立即 hide + revoke owner + 清 bounds + `generation++`，等新会话重新 CLAIM/SHOW
  （**旧会话的 `visible=true` 绝不能带进新会话**）；
- **renderer 生命周期撤销**：`reload` / `navigation` / `render-process-gone` / `webContents destroyed` → 立即 `revoke(owner) + hide()`。
  reload 比心跳更强——页面 reload 已经说明原 renderer 生命周期结束，不必再等几秒判断。

**P0 ③ 声明协议与顺序**：页面是"期望状态"的权威，主进程是"已执行状态"的权威（主进程仍要存实际状态，否则控不住原生 View）；
但**不能再有"页面以为 hidden、主进程自己以为 visible"的双状态机**。

- 统一命令 `setBrowserPanelState({sessionId, owner, generation, seq, visible, bounds})`；
- **show**：卡片拿到稳定 bounds → SET_STATE → 主进程校验 → **先 setBounds 再 setVisible** → ACK；
- **hide**：`REQUEST HIDE → 原生层先隐藏 → ACK → 页面再 panelHidden/translateX`。顺序反过来就直接消灭"收起一帧白"。

**P1 ② 心跳**：不要拿 `reportBounds` 当心跳（页面静止时 bounds 不变，几分钟都不发）。
独立 `browserPanelHeartbeat({sessionId, owner, generation})`，1s 一次、TTL 3.5~5s；主进程超时 → hide + revoke。
它擅长兜住"renderer 卡死 / React 异常 / IPC 生命周期没执行 / 没正常 unmount"，但**最多多活 TTL 秒**，所以是保险丝不是开关。

**P1/P2 ① 几何判据的坑（重要）**：**必须先算 `rawBounds ∩ viewport` 再判可见，最后才 clamp**。
反例：raw `x=2589, width=1000, viewport=2560` → 交集为 0，应判不可见；若先 clamp
（`x = min(2589, 2560-1000) = 1560`）就变成"完整落在视口内"——**clamp 会把"已经飞出屏幕"的证据销毁**。
建议同时保留 `rawBounds` 与 `effectiveBounds` 两个概念。

**会话维度**：①②③④都不能单独作为"切会话"的主解决方案（① 没有新 bounds 输入；④ 新会话可能根本没有卡片执行 guard）。
必须显式加 `onActiveSessionChanged` 的 revoke+hide。
另外：**`browserTabs` 可以继续全局**（内容状态 ≠ 面板 presentation 生命周期）；只有 owner/visible/bounds 必须绑 session。
若将来要"每会话各自标签"，再上 `browserTabsBySession`。

**对本仓库的决定（本轮）**：
