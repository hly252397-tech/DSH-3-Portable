# 2026-09-30 内核 0.2.0-rc.2 候选装配失败：真因与失败原因误报

## 一句话

候选装配失败的真因是**按发布时间解析撞上 pnpm 成熟期门槛**，而记录下来的「失败原因」是一行与故障无关的 pnpm WARN——两个独立缺陷叠加，让自动升级连续两天卡在同一个查不出的原因上。

## 现象

`Data/Updates/Harness/state.json` 记录 rc.2 连续 2 次部署失败，退避闸门把自动升级暂停到 2026-10-01，失败原因记为：

```
[WARN] The "pnpm" field in package.json is no longer read by pnpm. The following keys were ignored: "pnpm.onlyBuiltDependencies", "pnpm.allowBuilds", "pnpm.overrides". See https://pnpm.io/settings for
```

这行 WARN 只是 pnpm 12 提示 `package.json` 的 `pnpm` 字段不再被读取，与任何失败都无关。

## 缺陷一：失败原因取到了错误的行

`runPnpm`（`src/harness-runtime-candidate.ts`）只保留输出尾部 12 000 字符，调用方 `deployHarnessCandidate`（`src/main.ts`）再截到 200 字符。pnpm 输出尾部常以 WARN 收尾，于是那 200 字符里装的是 WARN，真正的错误行被截断吃掉。

**后果**：自动升级的失败记录不可信，退避闸门（`maxAutomaticDeployAttempts: 2`）据此判成「已重试耗尽」，排查只能手工绕过记录层重跑一遍。

**修法**：新增导出的 `pnpmFailureDetail(output, code)`，按「像错误」筛行（`ERR_PNPM_` / `Error:` / `ERROR:` 优先），退回第一条非 WARN 行，全空才用退出码兜底。回归测试 `test/harness-runtime-candidate.test.ts` 用事故原始输出形态验证「经过 200 字符截断后仍能看到真因」。

## 缺陷二：成熟期门槛（真正的失败原因）

真错误是：

```
ERR_PNPM_NO_MATURE_MATCHING_VERSION
  × installing dependencies
  ╰─▶ 1 version does not meet the minimumReleaseAge constraint:
        @deepseek-ai/dsh-client-ui-settings-account@0.2.0-rc.2 was published
      at 2026-09-29T11:17:03.848Z, within the minimumReleaseAge cutoff (2026-09-29T10:56:27.792Z)
```

链路：`pnpmWorkspaceYaml()` 为官方家族写 `resolutionMode: time-based`（`AGENTS.md` 钉版要求，防止 `^<同元组预发布>` 被最高版语义拆成混用家族）→ pnpm 改按发布时间解析 → 同一个 rc 版本内各包发布时间并不一致 → 比 cutoff 晚发布的那一个被判不成熟 → 整次安装收场。

**已排除的假设**（都实测过，不是推测）：

| 假设 | 实测结果 |
|---|---|
| `minimumReleaseAge` 没关 | 错。`officialRuntimeInstallArgs` 一直传 `--config.minimumReleaseAge=0`，并被 `preparePnpmInvocation` 翻译成 `PNPM_CONFIG_MINIMUM_RELEASE_AGE=0`；**设了它仍然失败** |
| 探针绕过了翻译层 | 自纠过一次。绕过后命中的是 pnpm 默认门槛，那不是真实部署路径的行为，结论是假的 |
| pnpm 版本不对 | 自纠过一次。`App/resources/node/pnpm-package` 是 11.24.0，活动槽里是 12.7.0（`bin/pnpm.mjs`）；11.24 报的 `ERR_PNPM_RESOLUTION_POLICY_VIOLATIONS_UNHANDLED` 是 12.x API，采信它就会修错东西 |
| registry（镜像 vs npmjs） | 错。两边都实测过，都能装成功 |
| 时间过去窗口自然消失 | 错。cutoff 是 `2026-09-29T10:56` 这个**固定值**，不是「当前时间减 N」；相隔 4 小时的重跑报同一个 cutoff |

**修法**：`pnpmWorkspaceYaml()` 在官方运行时变体里输出 `minimumReleaseAgeExclude: ["@deepseek-ai/*"]`（pnpm 自己在 help 里给的出口）。

按命名空间整体豁免而不是逐包列举：家族包随版本增删，硬编码清单下个版本就得改代码，与「新版本自动拉取升级」的要求直接冲突。官方家族本身已由受信版本表 + npm integrity + 家族对齐门禁把住，成熟期门槛在这里是纯粹的误伤。

## 缺陷三：既有目录永远补不上

`ensureRuntimeResolutionMode` 只在「文件不存在时」写完整模板，对**已存在的** `pnpm-workspace.yaml` 只补 `resolutionMode` 一行。现役槽与全部历史槽都是在加豁免规则之前生成的 —— 只改生成分支的话，升级会继续以同样原因失败。

这正是 `AGENTS.md` 记过的「已存在目录永远补不上」陷阱。

**修法**：改名 `ensureOfficialRuntimeResolutionPolicy(runtimeDir)`，对两项策略各走「有则改写、无则追加」的幂等路径，只动这两处、不碰其他设置；内容相同则不落盘（候选槽是不可变制品）。陈旧的逐包钉版条目被**就地替换**而不是并存 —— 留着会让下个版本继续失败。

配套把 `pnpmWorkspaceYaml` 的两个调用点与 ensure 统一到单一事实源 `OFFICIAL_RUNTIME_RESOLUTION_POLICY`，避免出现「新建的槽有豁免、历史槽没有」这种只在升级时才暴露的分裂。

## 验证

1:1 复现台 `Data/Temp/repro-exact.mjs` 用真实函数生成清单与参数、真实活动槽 pnpm 12.7.0、真实 store、npmjs 源：

| 条件 | 结果 |
|---|---|
| 修复前（`{ resolutionMode }`） | `exit 1`，`ERR_PNPM_NO_MATURE_MATCHING_VERSION` |
| 修复后（`OFFICIAL_RUNTIME_RESOLUTION_POLICY`） | `exit 0`，530 包，`@deepseek-ai/dsh 0.2.0-rc.2` 全家族装齐 |

门禁：tsc 干净；全量测试 `779 pass / 0 fail / 26 skipped`（新增 3 个回归用例）；`scripts/ui-baseline.mjs` PASS（零 UI 改动零漂移）。

## 留下的规矩

- **自动升级场景下，失败记录的准确性是功能的一部分。** 一个记着误导性原因、还据此耗尽重试次数的失败记录，比没有记录更糟：它会让人以为已经排查过了。
- `resolutionMode: time-based` 与成熟期门槛必须成对考虑。只要按发布时间解析，就要同时准备成熟期豁免，否则同版本内最后一个发布的包必然装不上。
- 探针必须走真实函数与真实参数。绕过 `preparePnpmInvocation`、用错 pnpm 版本、或用字面选项代替策略常量，都会产出**看起来合理但与产品无关**的结论 —— 本次三处都踩了。

## 复现台（留在 Data/Temp，CI 不入库）

- `repro-exact.mjs` —— 1:1 复现候选装配，逐字节同真实路径
- `probe-harness-build.mjs` —— 绕过记录层，打印 pnpm 完整输出
- `verify-detail.mjs` —— 用事故原始输出验证失败原因提取
