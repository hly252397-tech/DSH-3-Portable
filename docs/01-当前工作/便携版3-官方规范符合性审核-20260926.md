## 二、findings（按严重度）

### 🔴 F1 规范知识库的"实现适用版本"严重过期，且是必读文档
`docs/03-技术架构/DeepSeek-Harness-插件开发规范知识库.md:6`：

> 实现适用版本：`@deepseek-ai/dsh 0.1.2-rc.1`（本便携版内置运行时）… 官方最新审查版本为 `0.1.5-alpha.1`

而真实实现基线是 **`0.1.7-rc.2`**（`DeepSeek-Harness-官方兼容基线.md:9`），官方审查版本也是 `0.1.7-rc.2`（同文件表第 11 行）。同一文件 `:25` 又写"即使内置运行时已到 `0.1.6-alpha.2`"——**一份必读文档里同时出现三个互相矛盾的版本**，而门禁第 1.1 条要求"每个功能开始前完整阅读官方兼容基线与插件开发规范知识库"。
**危害**：审核者是按"0.1.2-rc.1 的 API 面"来判合规的，等于用落后三代的边界去审新代码。
**同源问题**：`DeepSeek-Harness-官方兼容基线.md:46` 的「官方兼容性判定」第 2 条仍写"代码必须以**已内置** `0.1.6-alpha.2` 的实际导出和类型声明为准"，与同文件顶部表格（`0.1.7-rc.2`）冲突。该文件自述"历史按日审阅记录不改写"（:91），但 `:46` 属**长期条款**而非某日记录，不改就是活的错误指导。

### 🔴 F2 质量门禁测试只锁 JSON，文档正文无人管
`test/quality-gate.test.ts:36-52` 只断言：JSON 基线 `bundled.dshVersion` == `package.json` 的 `config.bundledDshVersion`、commit 是 40 位 hex、仓库 URL、policy 两项、以及兼容基线 MD 里出现过"实现基线/审查基线"等**关键字**。
`test/bundled-plugins.test.ts:75` 另把 `OFFICIAL_DSH_VERSION` 钉在 `0.1.7-rc.2`。
**结论**：F1 那两处过期**结构上不可能被门禁发现**——门禁读的是 JSON 与关键字，不是"文档正文里的版本数字"。这正是仓库反复吃过的"文档漂移"（见今日可移植性报告同源问题）的机制性根因。
**建议**：给 `quality-gate.test.ts` 增加一条"文档正文里的版本号必须等于 `OFFICIAL_DSH_VERSION`"的断言（或把两个 MD 的版本行改为从 JSON 渲染/校验）。

### 🟠 F3 本地插件导出形态越出规范白名单，且注释与代码矛盾
`Data/DSH/profiles/web/local/dsh-agent-bridge/lib/index.js:20` = `export async function* apply(ctx, config)`（async generator，靠 `yield` 给 disposer），模块级 `inject = ['sessionController']`（`:9`）。
但其 `cordis.patch.yml:1-5` 写"**命名导出形态，模块级 inject / Config 即生效**"，条目里**没有 `inject:` 字段**。
AGENTS.md 只承认三种形态（命名导出 / default 类带 static inject / default 函数且 inject 写在 patch）。本插件是第四种：**注释声称是形态①，代码事实上不是**。
**风险**：若 loader 按"default 函数"口径处理，`sessionController` 注入缺失即抛 `cannot get property sessionController without inject` → 整条 Agent 桥接通道失效。
**建议**：把该形态写进知识库（附实证），或在插件里改成明确形态；至少修掉那句错误注释。**需真实 Loader 验证后才能定级为故障**（本轮只能证明矛盾，不能证明失败）。

### 🟠 F4 重启端点共享密钥明文固化
`Data/DSH/profiles/web/local/dsh-restart-button/cordis.patch.yml:4-5` 写死 `agentToken: '5630e422…ff47'`；`lib/index.js:38` 仅比对请求头。token 随 profile 被复制/备份/上传，等于长期有效的明文口令；注释所称"仅本机 webServer 可达"挡不住**本机任意进程**（读得到该文件即可 POST 触发外壳重启）。
**建议**：启动时随机生成、随进程存活；或至少 0600 文件 + 每次启动轮换。属性上这与"客户端 bundle 禁止重启动作"铁律是**同一类风险的运输通道**（都是"能触发重启的凭据"），建议一并纳入护栏。

### 🟠 F5 `dsh-black-hole` apply 校验分支矛盾、错误被吞
`local/dsh-black-hole/lib/index.js:66-68`：外层已要求 `dataDirectory` 非空且 `isAbsolute && existsSync`，内层却在 `!isAbsolute` 时才抛错 ⇒ **"绝对路径但目录不存在"静默通过**，用户最终看到存储路由 503 而不是"目录不存在"。
**建议**：拆成两条独立校验并分别报错。

### 🟠 F6 `dsh-agent-bridge` 的发现文件处理
`lib/index.js:209-213`：disposer 里 `JSON.parse(readFileSync(descriptor))` 失败时只在 `code !== 'ENOENT'` 才 warn ⇒ **JSON 损坏（无 `code`）时不警告、不清理**，`.dsh/agent-bridge.json` 留过期 token。`:25` 用 `process.env.DSH_HOME || process.cwd()`，DSH_HOME 缺失时会写到工作目录而非盘内数据目录。

### ⚪ F7 官方写作铁律"空 catch 必须点名错误"仍有多处未达标
`src/main.ts:829`（`unlinkSync` 无说明、无点名）、`src/main.ts:846`（重启审计写盘）、`src/plugin-seed.ts:321`，以及插件侧 `dsh-p3-tiny-watch/lib/index.js:124/133/282/297`。多数带注释解释"失败不影响功能"，但按官方铁律仍应点名吞掉的错误类型。

### ⚪ F8 受信清单的 `runtimeMigration` 块仍是 2026-09-11 快照
`DeepSeek-Harness-官方兼容基线.json:19-27` 的 `trustedTargets: ["0.1.5-rc.1","0.1.5-rc.2"]`、`migrationTarget: "0.1.5-rc.2"` 已落后；块内 `supersededNote` 已声明"此后三次前移"，且指向 `src/harness-update.ts` 的 `BUILTIN_TRUSTED_HARNESS_RELEASES` 才是事实源（实测确含 `0.1.7-rc.2`/commit `477b4f42`）。属**已标注的过期块**，但机器可读 JSON 里放过期值仍有被误读风险，建议只留指针不留值。
