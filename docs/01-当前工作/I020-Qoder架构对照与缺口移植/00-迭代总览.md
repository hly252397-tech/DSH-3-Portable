## 1. 目标

1. 判定外部"从零复刻 Qoder"架构方案中，哪些能力本便携版**已经具备**、以何机制具备，形成可复核的复用清单，避免重复建设与"第二套系统"。
2. 把方案中真正缺失的部分收敛成**归属正确**的工作包：每个缺口映射到官方扩展机制（`ctx.tools` / `ctx.llm` / `agent/*` 事件 / `ctx.commands` / `ctx.jobs` / Client Slot）与 PRD 需求编号。
3. 输出一批**验收用例**：若干条目实际是"能力已在、验收未做"，其交付物是测试证据而非代码。

**明确不做什么**：不替换 Harness Agent 内核，不新增第二套会话库、更新器、调度器或浏览器（PRD §2.2）；不因本文宣称任何功能已实现或已验收。

## 2. 结论摘要

对照结果与方案撰写时的预期**相反**：该方案假设从零构建工具循环、权限、压缩与多提供方适配，而这四层在 DSH 官方运行时中已作为可逆插件存在，且在沙箱与压缩两处比方案的设计更完整。方案中真正未被覆盖的产品级空白只有一处（分层长期记忆与检索注入回路），其余多为"已实现待验收"或"待决策"。

因此本迭代的移植方式是：**方案降级为参照清单，产出物改为缺口→插件映射**，而不是施工蓝图。

## 6. 禁区（本仓库已付出代价的规矩）

- 不改 Harness 内核、不碰 `App/resources/app.asar` 与 `Data/Updates/Desktop/slots/` 不可变候选；部署只走 `Build-DSH-Portable.ps1` + 启动器切换与自动回滚，禁止恢复原地覆盖脚本。
- 社区插件不得复制进 DSH 安装 `node_modules`；在线安装走 `dsh plugin --profile web add`。
- `web/local/<插件>` 与 `profiles/web/node_modules/<插件>` 是**两份拷贝**，宿主读后者，两处必须同步（含 `cordis.patch.yml`）。
- 类型与测试门禁只用 `App/resources/node/node.exe`（v24.20.0），系统 Node 属版本门禁违例；测试环境（Git Bash）与用户双击环境的 tar 实现不同，**测试通过 ≠ 用户可用**。
- `.ps1` 必须带 UTF-8 BOM。
- `docs/` 经 `.git\info\exclude` 仅本地保留，**禁止提交**，也不提议将其纳入跟踪。
- `宏建云系统/` 与 `工作空间/` 是独立业务项目与插件源码镜像，不并入本产品方案；`Customize/App-Overlay/` 是历史素材库，**不是**新功能落点。
