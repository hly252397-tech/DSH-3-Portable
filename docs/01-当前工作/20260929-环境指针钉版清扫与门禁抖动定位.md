## 4. 🔴 新定位：门禁本身在抖（约 50%），比门禁红更糟

本轮跑门禁时全量出现 1–2 个红，且**隔离复跑结果不一致**。定位结论：

```
隔离跑 dist/test/{test-build-freshness,test-runner-lock}.test.js 共 4 轮
  # pass / # fail 依次为： 0/2 → 1/1 → 1/1 → 2/0
```

**两个测试各自约 50% 概率红，且互不相关地独立抖动。**

**归属**：**不是本轮引入**。两者测的都是**前一会话未提交**的 runner 改动：

- `scripts/lib/test-build-freshness.mjs`（未跟踪新文件）
- `scripts/run-tests.mjs` 的跨进程互斥锁 + 递归收集 + 附加目标（R-172 那批；本轮对该文件**只改了顶部注释**）

**已看到的一处机制性脆弱点**（未钉死，供后续定位）：`test-build-freshness.mjs:11` 每次调用都 `spawnSync(GATE_NODE, [tsc, '--showConfig', …])`，而用例的 mtime 基准只差 **5 秒**（`tsconfig.json` 10s 前 / `src/value.ts` 5s 前 / dist 产物 0s 前）。在 G: 盘 + 杀软 + 回收清理器并发 I/O 下，单次 spawn 往返就可能吃掉这个窗口。`test-runner-lock.test.ts` 则是三个进程 + 1 秒级 `sleepSync` 的时序断言，同类敏感。

**为什么这条比"门禁红"更严重**：不稳定的门禁在两个方向都不可信——它放过的和不拦住的一样没有说服力。按止损纪律，**本轮不宣布门禁全绿**。

**本轮不修**：属另一会话的未提交代码，且需先确认那段 runner 改动是否已收工（避免与在途工作对撞）。
