# DSH 便携版 3 — 可移植性报告

> 对象：当前实机便携盘 `G:\DSH-3-Portable`（桌面槽 `1.0.76-local-3cfc4743bb8d1fff`，Harness 活动槽 `0.1.7-rc.2-4d29c691bfdf224c`，独立家园绑定 `v4-rc2b`）。
> 方法：**静态取证**——逐文件读启动链与路径代码、逐处核对实机 `Data/` 里的绝对路径、读 `.modules.yaml` 与用户数据。
> ⚠️ **工具限制（2026-09-26 补记，后续审核发现）**：`grep`/ripgrep **会跳过 `.gitignore` 覆盖的目录**，而 `Data/` 整体在忽略列表内 ⇒ 对 `Data/**` 的任何"目录级 No matches"都是**假阴性**（只有显式给出文件路径时才可靠）。本报告每条"发现"都以**具体文件的显式读取**为依据，结论不受影响；但"全树没有更多硬编码"这类**覆盖面结论不成立**，需按文件白名单逐个核。
> 对照：`src/`、`scripts/`、`docs/`、`test/` 未被忽略，对这些目录做目录级搜索的结论有效。
> **本轮没有执行任何命令**（本会话 shell 不可用，见「四、未验证项」），因此报告里凡涉及"实跑"的结论都标为未验证。

## 一、结论先行（说人话）

**能不能搬走？能。** 换盘符、换机器、插到别的 USB 口以后，**启动器会按"自己现在在哪个盘"重新算出所有路径**，不需要手工改配置；会话、插件、更新槽、更新指针都用相对路径存，桌面更新也走不可变槽 + 自动回滚。

**但有 6 处"洞"会让搬完以后少东西**，其中 2 处是**现在就必须修**的（换了盘就一定会坏，且有实机证据）：

| # | 洞里是什么 | 换盘后的表现 | 级别 |
|---|---|---|---|
| 1 | 数据层（`Data/DSH/storages/**`）里的绝对路径：8 个百炼 MCP 连接、1 个工作区、14 条定时任务工作目录 | MCP 工具全部起不来；工作区打不开；定时任务失败 | 🔴 必坏 |
| 2 | 新一代家园 `Data/DSH-generations/v4-rc2b/home/.../.modules.yaml` 不在启动器的重定位名单里 | 装/更插件报 `ERR_PNPM_UNEXPECTED_VIRTUAL_STORE` | 🔴 必坏 |
| 3 | 旧会话头里的 `cwd` 不做改写 | 历史会话还在，但按旧盘符归组，左下角看起来"历史没了" | 🟠 观感 + 归组 |
| 4 | 用户级技能 Junction、浏览器书签里的盘符链接 | 技能断链（有 `重建技能链接.cmd` 兜底）；书签点开失效 | 🟠 需手工一步 |
| 5 | 文件系统 / 权限要求没有前置检查 | 拷到 FAT32/exFAT/网络盘会**直接坏**（链接与 pnpm 仓库失效） | 🟠 需明示 |
| 6 | 凭据与宿主痕迹 | 便携盘丢了 = 密钥泄露；宿主仍有"最近打开"等痕迹 | ⚪ 已知边界 |

**一句话建议**：搬迁前先按本报告「三、搬迁清单」走一遍（5 步，约 2 分钟），比事后逐个救火便宜得多；第 1、2 条建议做成一次性修复脚本，别靠人手改。

## 三、搬迁清单（换盘符 / 换机器时按顺序做，5 步）

1. **从托盘彻底退出** DSH（不要在有构建/回收清理在跑时搬，见 `AGENTS.md` 止损第 7 条）。
2. **确认目标文件系统是 NTFS**（推荐）或至少不是只读/网络盘。见「四·发现 5」。
3. **整盘目录复制**（不是移动单个文件夹，`Data/`、`工作空间/`、`Customize/`、源码与 `.git` 一起带走）。
4. **新盘首次启动后**，逐项确认：
   - 托盘正常起来、主界面能进（`Data/Updates/Desktop/launcher.log` 无回滚记录）；
   - `.workbuddy` 技能还能读到内容；读不到 → 双击盘根 `重建技能链接.cmd`；
   - 百炼 MCP 类连接是否可用（见「发现 1」，不修必定失败）；
   - 顺手看 `Data/Electron/UserData/plugin-update.log` 有没有 `ERR_PNPM_UNEXPECTED_*`。
5. **改完路径不要立刻构建**：构建会启动脱离进程的回收清理器，与"请人重启激活候选"并发会卡主视图（`AGENTS.md` 止损第 7 条已有实机事故记录）。

## 四、发现（按严重度，逐条附证据与建议）

### 发现 1 🔴 数据层绝对路径：MCP / 工作区 / 定时任务（换盘必坏）

**证据**

- `Data/DSH/storages/mcp_connector.json`：**8 条**「百炼」stdio MCP 连接，每条都写死
  `"command": "G:\\DSH-3-Portable\\App\\resources\\node\\node.exe"` 与
  `"args": ["G:\\DSH-3-Portable\\Data\\DSH\\mcp-bridges\\bailian-mcp-bridge.mjs", ...]`（行 15/36/57/78/99/120/141/162）。
- `Data/DSH/storages/workspace.json:30`：`"path": "G:\\DSH-3-Portable\\宏建云系统"`（唯一工作区的路径）。
- `Data/DSH/storages/dsh_automation.json`：`"cwd": "G:\\DSH-3-Portable\\宏建云系统"` 共 **14 处**（任务与每轮运行快照）。
- 会话投影缓存 `storages/session_projcache_archive_manager*/` 里同样存盘符路径（`cwd` 与工具调用记录里的 `path`）。

**为什么是硬伤**：这些字段是**用户数据**，不是代码；`src/` 与 `scripts/` 里没有任何一处会去改写它们（grep 无命中），命令行不做环境变量展开（官方 pi-ai 只对凭据做 `${VAR}` 解析，MCP 的 `command`/`args` 原样使用）。所以换盘符以后这 8 个 MCP 子进程**必然启动失败**，工作区路径**必然是失效路径**。

**建议**（三选一，推荐 A+B 组合）

- **A（推荐）一次性修复脚本**：新增 `scripts/repair-portable-absolute-paths.mjs`——扫描 `Data/DSH/storages/**`，把命中的**旧便携根前缀**（自动从路径里推出 `/Data/` 或 `/App/` 之前的部分）替换为当前 `DSH_PORTABLE_ROOT`；先备份、只改 JSON 字符串值、幂等、产出改动清单。由启动器在检测到"路径前缀 ≠ 当前根"时提示一次（**不静默改写**，符合本仓"禁止静默回退"的口径）。
- **B** 把它挂进 `Portable-Environment.ps1` 的启动重定位（与 `.modules.yaml` 同一位置），但只做**检测 + 日志 + 一次性提示**，避免每次启动全量重写用户数据。
- **C（仅止血）** 搬迁后手工重装/重配那 8 个 MCP 连接与工作区——成本最高，不推荐。

> 注：修复脚本必须只处理 `Data/DSH/storages/` 这类**用户数据**，绝不能顺手改写会话日志（`Data/DSH/projects/**` 的 jsonl/zstd 是"字节不可改写"资产，见架构基线第 5 节）。

### 发现 2 🔴 新一代家园的 `.modules.yaml` 不在重定位名单里

**证据**

- `Portable-Environment.ps1:78-82` 的 `$stateFiles` 只列三条：
  `Data/DSH/profiles/web/node_modules/.modules.yaml`、`Data/Runtime/dsh-runtime/node_modules/.modules.yaml`、`App/dsh-runtime/node_modules/.modules.yaml`。
- 但当前活动布局已改为**独立家园**：绑定文件 `Data/Updates/Harness/homes/0.1.7-rc.2.json` → `generation: v4-rc2b`，真实 profile 在
  `Data/DSH-generations/v4-rc2b/home/profiles/web/`，其 `.modules.yaml:640-641` 记录
  `storeDir: G:\DSH-3-Portable\Data\Development\pnpm-home\store\v11`、
  `virtualStoreDir: G:\DSH-3-Portable\Data\DSH-generations\v4-rc2b\home\profiles\web\node_modules\.pnpm`。
- 该错误形态**已经在本机发生过一次**（现役布局切换时）：
  `Data/Electron/UserData/plugin-update.log:1` = `[ERR_PNPM_UNEXPECTED_VIRTUAL_STORE] ... currently symlinked from ...\Data\DSH\profiles\web\node_modules\.pnpm`。

**影响**：换到 `H:` 以后，家园 profile 的 `.modules.yaml` 仍写着 `G:`；插件装/更/启停时 pnpm 会判定虚拟仓库位置不符 → 报错或要求重装。**部分兜底存在**：插件安装路径会调 `resolvePnpmStoreDir()`（`src/plugin-seed.ts:152-173`，内部走 `rebasePortablePnpmState`），但那是"安装时才修"，且只覆盖 profile 目录；MCP/工具链等其它读取点仍会看到旧值。

**建议**：把重定位入口从"硬编码三条路径"改成**按布局枚举**——在 `Portable-Environment.ps1`（或更稳的做法：`src/plugin-seed.ts` 已有的 `rebasePortablePnpmState`）里覆盖
`Data/DSH/profiles/web/**`、`Data/DSH-generations/*/home/profiles/*/**`、`Data/Runtime/**/node_modules/**` 三类候选；改动属"路径自愈"，需附回归用例（现有 `test/plugin-seed.test.ts:558` 只测了函数本体，不测"家园目录是否被覆盖"）。

### 发现 3 🟠 旧会话头的 `cwd` 按旧盘符归组

**证据**：`src/session-path-repair.ts:40` 用**头部里的 `cwd`** 算期望目录；修复只把物理目录搬到 `projectKey(cwd)` 下，**不改写 `cwd` 本身**；`Data/DSH/storages/session_projcache_archive_manager*/` 里的 `cwd` 也都是 `G:\...`。

**影响**：搬迁后旧会话仍可打开（内容与字节都在），但它们会继续归在"`G:\DSH-3-Portable\...`"这个历史项目键下；用户按新盘符找工作区时，左栏看起来像"历史会话没了"。这是**观感 + 归组**问题，不是数据丢失。

**建议**：不要动日志字节。要么在发现 1 的修复脚本里**只修派生索引**（`storages/session_projcache_*`、工作区表）并附"历史会话仍按创建时路径归组，属预期"的说明，要么明确写进使用说明，避免用户误判为丢数据。

### 发现 4 🟠 用户级技能 Junction 与浏览器书签里的盘符链接

**证据**

- `.workbuddy/skills/hongjian-erp/SKILL.md:24,26,27` 与 `.workbuddy/memory/MEMORY-HONGJIAN-ERP.md:5`：技能正文与记忆里写死 `G:\DSH-3-Portable\...`；用户级同名入口是 Junction，**换盘符会断链**（Windows 目录链接存绝对路径，跨盘无法用相对路径）；盘根已提供兜底 `重建技能链接.cmd`（其头部注释即说明了这一场景）。
- `Data/Electron/UserData/browser/library.json:286`：书签 URL 里带着 `...?path=G%3A%2FDSH-3-Portable%2F...`，换盘后该条目失效（单条，影响小）。
- `启动本地Ollama.cmd`、`宏建云系统/python/**` 等盘内组件都是 `%~dp0` 自定位，**这部分是对的**；盘内 33 个业务脚本的写死盘符此前已迁移为 `_root.cjs` 自解析（`docs/00-交接入口/07-功能清单.md` 2026-09-13 行）。

**建议**：技能文档里的绝对路径改成"以技能包自身位置为准"的表述（`fix-link.cjs` 已经是自解析的，只有文档与记忆是硬编码）；搬迁清单里保留"双击重建技能链接.cmd"这一步。

### 发现 5 🟠 缺少文件系统与权限的前置检查

**现状**：启动器只检查目录是否可创建/可写，**不检查卷的文件系统类型**。而本方案依赖两类 NTFS 特性：

- **Junction / 符号链接**：`Data/DSH/profiles/web/node_modules/<本地插件>` 是指向 `local/<插件>` 的目录链接（`AGENTS.md`「profile 本地插件已改为目录链接」），家园里的官方层 junction 也一样。**exFAT/FAT32 不提供重解析点支持**，这些链接在拷贝后无法存在；网络共享同样不可靠。
- **pnpm 仓库的硬链接**：仓库与 `node_modules` 之间靠硬链接省空间，exFAT 不支持硬链接（会退化为复制，体积与安装时间显著上升），FAT32 还有单文件 4 GB 上限——而现在单个桌面槽约 780 MB、运行时归档数百 MB，**FAT32 直接放不下**。

**证据**：`Portable-Environment.ps1:84-115` 只重定位 `.modules.yaml`，无卷类型判断；使用说明只写"此目录可以整体放在 U 盘、移动硬盘或可移动 SSD"（`便携版3-使用说明.md:3`），没有写文件系统要求。

**建议**：在 `Start-DSH-Portable.ps1` 早期加一条**只提示不阻断**的检查（卷 DriveType + 文件系统 + 可用空间），并在使用说明里写清："必须是 NTFS；exFAT/FAT32 会导致插件链接与 pnpm 仓库失效"。若要硬拦，只拦"FAT32 且目标体积超限"这类必然失败的情况。

### 发现 6 ⚪ 凭据与宿主痕迹（已知边界，非缺陷但要在搬运/丢失场景明说）

- 凭据在盘内且为**明文可读**：例如 `Data/DSH/storages/mcp_connector.json:21` 直接存 `BAILIAN_MCP_API_KEY` 明文；`Data/DSH/agent-bridge.json` 存本机桥接 token。使用说明已提示"盘丢失等同于数据和密钥可能泄露，建议 BitLocker To Go 或硬件加密盘"（`便携版3-使用说明.md:36`），本报告确认该风险面**覆盖到 MCP 密钥**，不只是登录凭据。
- 宿主痕迹无法归零：Windows 会保留"最近打开"、Toast 通知注册（`DESKTOP_TOAST_ACTIVATOR_CLSID`，`src/app-identity.ts:7`）、安全日志、网络/DNS 缓存等；使用说明第 37 行已如实说明，本轮无新增发现。
- 主进程**没有**写注册表 Run 键/任务计划（`src/` 内无 `registry`/`setLoginItemSettings`/`Startup` 写入点；grep 命中的都是"启动进度""启动检查"等业务词），开机自启完全依赖用户手动放快捷方式——这对可移植性是**正确**的取舍。

## 五、已存在的问题（与可移植性相邻，顺手记账）

- `scripts/diag-fix-links.mjs:7-8` 写死 `G:\DSH-3-Portable\...`。它是诊断脚本，但会让"换盘后照它执行"变成改错仓库——建议改成从 `import.meta.url` 推根（仓库既有的迁移范式）。
- `Data/Updates/**`（备份、诊断、历史事务）里留有大量含 `G:` 的 JSON。它们是**历史留档**，不参与运行；但如果用"全盘搜 `G:`"来评估可移植性，会得到大量假阳性。评估口径应以 `Data/DSH/storages/**`、`Data/DSH-generations/**`、`Data/Electron/UserData/**`、`Customize/**` 为准。
- `src/main.ts:141` 的注释里出现 `G:\DSH-Portable`（旧版 v2），仅注释，无行为影响。
