# I025：官方运行时更新链路修复（家族钉版 / 活动槽保护 / 版本口径）

**日期**：2026-09-11（Asia/Shanghai）
**目标**：用户看到插件「关于」页提示 `@deepseek-ai/dsh 0.1.2-rc.1 → 0.1.5-rc.2 可更新`，点击更新后失败。修复该链路上叠加的三个缺陷，让「提示、目标版本、实际切换」三者一致且不可能损坏正在运行的运行时。
**范围**：`src/bundled-plugins.ts`、`src/harness-runtime-candidate.ts`、`src/plugin-seed.ts`、`src/harness-update.ts`、`src/desktop-host.ts`、`src/dsh-process.ts`、`src/main.ts` + 对应用户数据修复与文档。
**决策**：官方运行时的唯一升级权威是桌面端 A/B 更新器；profile 安装路径永不触碰活动运行时槽。

---

## 1. 背景

用户操作序列与观察：

1. 插件「关于」页显示 `DeepSeek Harness / @deepseek-ai/dsh · 0.1.2-rc.1 → 0.1.5-rc.2  可更新 [↓ 更新]`。
2. 点击「更新」，等待后失败；随后用户重启应用再次点击更新。

事件日志（`Data/Updates/Harness/logs/update-events.jsonl`）完整还原了外壳侧链路：

```
11:54:31 trust-gate blocked  targetVersion=0.1.5-rc.1  detail="候选版本尚未进入桌面端受信发布清单。"
13:48:54 check      start    currentVersion=0.1.2-rc.1
13:48:56 build      start    targetVersion=0.1.5-rc.1
13:54:33 deploy     failure  targetVersion=0.1.5-rc.1  detail="候选 DSH 运行时核心包版本未对齐。"
13:54:33 cycle      failure  durationMs=339497          detail="候选 DSH 运行时核心包版本未对齐。"
```

即：先因受信清单拦下，后因候选家族版本不对齐失败，耗时约 5.7 分钟（构建到校验）。

---

## 2. 根因

### 2.1 家族钉版完全失效（候选构建必然失败）

- pnpm 11.24 **完全忽略** `package.json` 的 `pnpm.overrides`，只认 `pnpm-workspace.yaml` 的 `overrides`。
- 即便写进工作区文件，overrides 的通配选择器（`@deepseek-ai/dsh-*`）**实测不命中**（专项探针验证）。
- 官方发版包把传递依赖写成 `^<同元组预发布>`，pnpm 默认最高版语义会把家族拉成混用：`0.1.5-rc.1` 根包 + `0.1.5-rc.2` 传递包。
- `isOfficialRuntimeFamilyAligned` 门禁**正确**地拒绝了该候选；错的是装配方式。

### 2.2 「关于」页更新会原地改写正在运行的活动槽

旧实现的桥接官方分支直接在 `desktopRuntimeDir`（= 活动运行时槽）上 `writeOfficialRuntimeManifest` + pnpm 安装：

- Windows 下正在使用的文件无法替换，安装必然半途失败；
- 已写入的 `package.json` 留在槽里（`0.1.5-rc.2` 清单 + `0.1.2-rc.1` 的 `node_modules`），槽随即在家族对齐门禁处失效 —— 用户看到的状态就是「更新失败」且运行时版本没变。

实机残留（本次修复前）：`Data/Runtime/Harness/slots/0.1.2-rc.1-2c82a3efc755c12c/package.json` 的 overrides/dependencies 为 `0.1.5-rc.2`，而 `node_modules/@deepseek-ai/dsh` 为 `0.1.2-rc.1`。

### 2.3 两套版本口径不一致（提示与可切换目标天生不同）

- codex-ui「关于」页对官方运行时**故意优先读 npm `next` 标签**（`npmTaggedVersion(pkg,'next') ?? npmTaggedVersion(pkg,'latest')`）→ 显示 `0.1.5-rc.2`。
- 外壳更新器只发现 `[alpha, latest]` → 最高到 `0.1.5-rc.1`，且 `0.1.5-rc.2` 不在受信清单里。

于是「关于」页说什么，外壳都跟不到。npm 当时的 dist-tag 快照：`alpha=0.1.5-alpha.2`、`next=0.1.5-rc.2`、`latest=0.1.5-rc.1`；官方 HEAD 为 `0.1.5-rc.2@c291e796`。

### 2.4 附带缺陷：失败点击留下幽灵待更新项

codex-ui 在安装**之前**就把目标写进 `Data/DSH/profiles/web/.dsh-pending-updates.json`，只在安装成功并挂载后才清除。安装失败时条目不回滚，而 profile 安装路径明确拒绝官方包，于是该条目**永远无法应用**，还会在之后每次插件更新时被合并写回。

## 3. 修复

### 3.1 官方运行时按发布时间解析（`resolutionMode: time-based`）

| 入口 | 改动 |
|---|---|
| 候选槽装配 | `harness-runtime-candidate.ts` 生成 `pnpm-workspace.yaml` 时传 `{ resolutionMode: OFFICIAL_RUNTIME_RESOLUTION_MODE }` |
| 安装参数 | `officialRuntimeInstallArgs` 追加 `--config.resolution-mode=time-based`（双写，任何入口一致） |
| 既有运行时目录 | 新增幂等 `ensureRuntimeResolutionMode`；`applyOfficialRuntimeVersion` 与 `ensureRuntimeScaffold` 调用（旧代码只在文件缺失时写入，已存在就永远补不上） |

按发布时间解析让同元组预发布保持在同一版本，家族不再被最高版语义拆分。

### 3.2 活动槽永不原地改写，转交 A/B 更新器

- `desktop-host.ts`：命令命中官方包且存在 `desktopRuntimeDir` 时，不再安装，改为发出 `REQUEST_HARNESS_UPDATE_IPC`，返回退出码 1 与说明文案「官方运行时由桌面端 A/B 更新器统一升级（候选槽 + 影子验证 + 失败自动回滚），不能在应用运行时原地覆盖。已转交更新器处理目标版本 …」。
- `dsh-process.ts`：新增 `isRequestHarnessUpdateIpc`（兼容字符串与 `{type}` 两种消息形态）。
- `main.ts`：`handleDshIpc` 命中该消息即调用新抽取的 `startHarnessUpdateTask(true)`；设置页按钮复用同一入口，保证「同一时刻只跑一个更新周期」的既有约束不被绕过。

### 3.3 版本口径统一

- 发现通道加入 `next`：`distTags[policy.channel] + distTags.next + distTags.latest`（alpha 预览线 + next 候选线 + latest 稳定线；能否自动切换仍只由受信清单决定）。
- 受信清单新增 `0.1.5-rc.2`（npm integrity 与 `dsh-v0.1.5-rc.2` 标签 commit 已核对），保留 `0.1.5-rc.1` 以支撑回滚/降级。
- 结果：官方 HEAD、插件 peer 声明（`0.1.5-rc.1 || 0.1.5-rc.2`）、「关于」页展示三处口径一致。

### 3.4 幽灵待更新项清理

`applyPendingProfileUpdates` 不再回写官方条目，直接删除登记文件；注释记录原因（profile 路径拒绝官方包 + 旧流程失败不回滚）。

### 3.5 用户数据修复（实机）

- 活动槽 `0.1.2-rc.1-2c82a3efc755c12c` 用正式写入函数恢复为 `0.1.2-rc.1`；重算指纹等于登记的 `2c82a3ef…`，223 个官方包，槽与 `current.json` 一致。
- 删除残留的 `Data/DSH/profiles/web/.dsh-pending-updates.json`（并存条目 `@deepseek-ai/dsh@0.1.5-rc.2`）。
- 清理本次排查产生的临时探针与 `.staging-repro-*` 暂存目录。

### 3.6 部署失败退避闸门（按版本记忆失败，防止失败循环）

**问题**：影子验证用一次性 profile 验证候选（`createHarnessShadowProfile` 只装 `OFFICIAL_PROFILE_BUNDLES`、`cordis.patch.yml` 为空），因此**社区插件从未被验证**。候选可以在影子验证通过、却在真实 profile 切换时崩溃（历史实例：`0.1.5-alpha.1` 抛 `cannot get property webServer without inject`），届时「构建 5.7 分钟 → 切换 → 回滚 → 重启」会在每个检查周期和每次重启后重复，界面变成失败循环。启动自修复（`profile-repair`）只能隔离「无法解析的 bundle」，对 `apply()` 期间同步抛错的服务依赖插件无效。

**修复**：按目标版本记住部署失败次数，失败到阈值后暂停**自动**升级，只保留用户手动重试入口。

| 位置 | 改动 |
|---|---|
| `harness-update.ts` 策略 | 新增 `maxAutomaticDeployAttempts`（1–10，默认 2）与 `deployRetryCooldownHours`（1–720，默认 24），越界回落默认值 |
| `harness-update.ts` 状态 | 新增可选 `deploymentFailures: { [version]: { attempts, lastFailureAt, detail? } }`；版本号走 `isExactVersion` 白名单（顺带挡住 `__proto__`/`constructor` 原型污染键），`attempts` 钳 1–100，`lastFailureAt` 必须 ISO，`detail` 压平并截断 200 字，最多保留 20 条最新记录 |
| `harness-update.ts` 导出 | `recordDeploymentFailure` / `clearDeploymentFailure` / `evaluateDeploymentRetryGate`（`interactive` 手动检查永远放行） |
| `main.ts` 周期 | 受信门禁之后、部署之前插入闸门；拦截时写 `blocked` 状态与 `retry-gate` 审计事件，文案含已失败次数、恢复时间与最近原因 |
| `main.ts` 失败点 | 部署失败（`failed`）与切换回滚（`rolled-back`）记录失败；切换提交（`succeeded`）清除该版本记录 |

---

### 3.7 工作台钉版锚点复核（既有待办收尾）

`Customize/Automation-Workbench/build.mjs` 声明的 `upstreamHash = 21fefb6c…` 与已安装的 `@michengai/dsh-automation@0.1.38` 的 `lib/client.js` 实测 sha256 **完全一致**；两处锚点各命中一次，`IconAlarmClockOutline16` 已消失、`IconListPenOutline16` 存在，与补丁声明的版本差异相符。结论：钉版声明准确，无需改动。

### 3.8 活动槽描述性清单自愈（启动补种）

**问题**：旧桥接原地改写留下的坏槽（清单 `0.1.5-rc.2` + `node_modules` `0.1.2-rc.1`）**没有任何启动检查能发现**——`isOfficialRuntimeLaunchable` 只看入口与 peer 是否存在，指纹只覆盖 lock 与家族清单（根清单被有意排除），槽会带着错误版本号一路用下去（版本号会流到「关于」页与更新器）。上一节修的是「不再产生」这种坏槽，本节修的是「已经存在时能自愈」。

**修复**：`plugin-seed.ts` 新增 `reconcileOfficialRuntimeManifest(runtimeDir)`，在 `seedOfficialRuntime` 的指纹槽分支里调用（即每次启动）：家族版本**单一且可读**时，把根清单与 `resolutionMode` 拉回实际安装版本；家族混用时不动清单，交由 A/B 切换门禁拒绝。

| 决定 | 理由 |
|---|---|
| 只改**已存在**的根清单 | 指纹槽是「不可变制品」，凭空造文件（`package.json`/`pnpm-workspace.yaml`）会打破既有约束与 `通过指纹封存的 A/B 运行时槽在启动补种时保持不可变` 用例 |
| 不动物化依赖，只改描述性清单 | 指纹由 lock + 家族清单决定，根清单不参与——修复不改变制品语义 |
| 家族混用时跳过 | 混用时无法判断该以谁为准，硬写一个版本只会掩盖问题；这类槽由 A/B 门禁按既有路径拒绝 |

## 4. 三项对齐

**真实入口与子界面**：插件「关于」页（codex-ui `settings.section`）→「更新」按钮；桌面端「设置 → 运行时更新」按钮。

| 项 | 状态 | 内容与证据 |
|---|---|---|
| 后端能力 | 通过 | 桥接官方分支改为请求 A/B 更新器（`test/desktop-host.test.ts`：`官方运行时更新绝不原地改写活动槽，而是转交 A/B 更新器` 断言退出码 1、消息为 `REQUEST_HARNESS_UPDATE_IPC`、runner 不被调用）；外壳 `startHarnessUpdateTask` 由设置页与桥接消息共用（`test/main-*` 既有周期约束不变）；家族钉版由 `test/plugin-seed.test.ts`、`test/bundled-plugins.test.ts` 覆盖；部署失败退避由 `test/harness-update.test.ts` 的两条新用例覆盖（连续失败暂停自动升级 + 失败记忆持久化过滤） |
| 前端操作闭环 | 通过 | 点击「更新」不再静默失败或伪成功：桥接返回退出码 1 + 明确文案，外壳启动更新周期并广播状态；设置页快照等待周期结束；自动升级被退避拦截时状态为 `blocked` 且文案给出恢复时间与手动重试入口，用户点击检查（`interactive`）始终放行 |
| UI 界面可用 | 通过（守卫路径） | 「关于」页沿用 codex-ui 既有失败提示与进度条（未改其 UI）；桌面设置页沿用既有更新状态展示。无新增界面，无新增文案 |
| 持久化与恢复 | 通过 | 槽不可变性与指纹校验由 `通过指纹封存的 A/B 运行时槽在启动补种时保持不可变` 覆盖；幽灵 pending 条目现被清除（`只剩官方条目的 pending 文件会被删除`）；失败记忆随 `state.json` 原子持久化并按版本过滤非法键 |
| 总体验收 | 未完成（待重启） | 真实 A/B 切换需在重启后走：候选槽 → 影子验证 → 空闲切换 → 观察窗口；本次已把两个目标版本的候选装配实测通过，切换动作由用户重启触发；若真实 profile 切换失败，退避闸门会阻止失败循环并要求手动重试 |

**未验证项与原因**：从 `0.1.2-rc.1` 到 `0.1.5-rc.2` 的真实切换、观察窗口与回滚演练尚未在实机跑完；`0.1.5` 线的 MichengAI 插件族适配结论仍需以真实 Profile + Loader 组合复核（见 [待办与阻塞](../../00-交接入口/03-待办与阻塞.md)）。
