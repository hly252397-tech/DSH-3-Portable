# 20260921-自调度重启导致无限重启事故复盘

> 本文件记录 2026-09-21 由我（智能体）自造的一次 P0 故障，用于防止再犯。
> 关联固化：仓库 `AGENTS.md` 同条目铁律 + 护栏用例 `test/no-self-scheduled-restart.test.ts`。

## 一句话

我把 `dshDesktopShell.action('app-restart')` 写进了**插件客户端 bundle**，而该 bundle **每次页面加载都会执行** ⇒ 重启 → 页面加载 → 又重启 ⇒ **自激无限重启**。

## 时间线与现象

| 时间 | 事件 |
|---|---|
| 之前 | 为"自动重启激活候选"写了延时探针：页面加载 +2.5s → 等 30s → `dshDesktopShell.action('app-restart')` |
| 触发后 | 用户端：窗口反复重启；**GUI 端口每次都在变**（连续观测到 50553→59351→62472→56771→53674→65413→49823→…）；**所有工具调用返回 `outcome unknown`**（工具链路随重启被杀）；用户明确报「你现在是无限重启了」 |
| 定位 | 重启指令在客户端 bundle 里 = 每次加载都自调度重启 |
| 处置 | 去掉触发行后，主进程存活时长恢复增长（实测 2.5 分钟且持续），循环停止 |

## 根因（三层）

1. **直接原因**：客户端 bundle 是**每次页面加载都执行**的代码路径；把"重启"放进去等于装了一个"自动按重启键"的循环器。
2. **我的判断错误**：我把 `action('app-restart')` 当成"给自己用的工具"，忘了它跑在**公共且高频执行**的路径上；也没做"这个动作会不会再次触发我"的自反性检查。
3. **处置方式错误（更该记）**：第一次切断失败后，我**连续用同一种方式重试**（改同一个文件），而没有第一时间换本质不同的手段（让 bundle 加载不到 / 交给唯一能可靠操作文件的人）。结果在故障里空转，用户反复催。

## 正确做法（本仓库早已具备）

- `local/dsh-restart-button` 就是**规范范例**：仅本机 webServer 可达 + 共享密钥（`x-dsh-agent-token`，未配置则端点整体停用）+ **必须显式 POST** 才触发 → `process.send({type:'app-restart'})` → 外壳 `requestAppRestart`（先调度分离的新实例再优雅关停）。
- 也就是说：**重启这件事本来就有受控、单次、显式的通道**，我不该自己造一个自调度的。

## 固化（三道防线）

1. **铁律入 AGENTS.md**「已踩过的坑」：客户端 bundle 里禁止 `app-restart` / `app-quit` / `dshDesktopShell.action('app-restart'|'app-quit')`；这类动作只能由用户显式操作触发。
2. **护栏用例** `test/no-self-scheduled-restart.test.ts`：扫描全部本地插件的客户端半侧（`lib/client.js`、`lib/client.src.js`）。经**正对照**验证——对事故原文命中 2 条规则、对安全写法（用户点击 → POST）0 误报。宿主半侧不扫（`dsh-restart-button/lib/index.js` 合法暴露显式端点）。
3. **排查提示入铁律**：出现"无限重启"时，先看**进程存活时长**（正常应持续增长）与最近被改过的客户端 bundle；**第一动作是让那个 bundle 加载不到或去掉触发行**，禁止在同一种改法上反复重试。
