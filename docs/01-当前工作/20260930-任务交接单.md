## 2. 待办 ①（最高优先）：顶栏「设置」点击无响应 —— 根因已锁，待修

### 现象
新候选槽实机：真实鼠标点顶栏「DSH 设置」(`#settings-btn`)，按钮**拿到焦点但设置页不打开**。

### 已排除（别重走）
- ❌ 不是白名单：`SHELL_ACTION_IDS` 第 141 行确实含 `'settings'`。
- ❌ 不是 IPC 丢弃：`src/main.ts:3274-3289` 的 `settings` 分支正常派发。
- ❌ 不是 probe 页面选错：设置页确实开在 **DSH Web 视图**（`http://127.0.0.1:60860/`），
  shell DOM 里没有它是**设计如此**——`settings` 由壳驱动 DSH 页面，不走 `dsh-action` 通道
  （`main.ts:3280-3282` 有注释说明为何绕开）。

### 真因（已实证）
`src/main.ts:626` 的 `TOGGLE_DSH_SETTINGS_PAGE_SCRIPT` 按选择器直点：
- 关闭用 `DSH_SETTINGS_BACK_SELECTOR = '.dcu-settings-back, [class*="settings-back"]'`
- 打开用 `DSH_SETTINGS_TRIGGER_SELECTOR = '.dcu-settings-trigger'`

实机 DOM 取证结果：

```
.dcu-settings-trigger  存在，display:grid，visibility:visible，opacity:1
  └─ 直接父 div           display: none          ← 断点在这
      └─ .dcu-settings-seat  display: block, 238×155
          └─ FOOTER.dcu-foot
```

该父 div 的内联样式是 `<div data-slot="sidebar.settings" style="display: none !important;">`。

**结论**：`sidebar.settings` 这个 slot 被内联 `display:none !important` 藏了，触发按钮虽在 DOM 里
却是零尺寸不可见，脚本点它等于空点 → `outcome` 拿不到 `'opened'`/`'closed'`，
`dshSettingsDialogVisible` 保持 false。

> 这与 AGENTS.md 坑清单「别在自己隐藏的容器上用 `offsetParent`」是**同一类问题的镜像**：
> 那条是「隐藏了却拿它当可见」，这条是「拿它当可点目标，实际不可见」。

### 修复方向（三选一，**不要**直接改 npm 包）
1. **改选择器语义**（推荐）：把触发目标换成 DSH 页面上**真正可见**的设置入口。
   先用 CDP 在 DSH 视图里枚举所有可见的、点了能进设置页的控件，别沿用隐藏 slot。
2. **改 slot 挂载点**：让 `sidebar.settings` 挂到可见容器下。风险：可能与 ui-tweaks 的
   四份 `client.js` 只读锁冲突（见 §6 注意事项）。
3. **兜底**：脚本在点之前先 `checkVisibility()`，不可见就沿可见路径回退打开。

改完**必须**走 §5 的验证闭环，且要按 `docs/03-技术架构/UI定制维护契约.md` 追加本轮记录。

## 12. 补充排查：两个设置入口 + 「设置页永久不可见」伪象定性（当日收尾）

用户问「现在的设置有两个界面入口」。排查结论与一个重要伪象的定性如下，**未改任何代码**。

### 12.1 两个入口是设计使然，保留

- **入口 A（外壳顶栏齿轮 `#settings-btn`）**：`src/main.ts` 的 `TOGGLE_DSH_SETTINGS_PAGE_SCRIPT`
  在 DSH 视图里代点 `.dcu-settings-trigger`，并把 `.dcu-settings-back` 的存在回读为「开着」。
  该按钮**兼作内核更新指示器**（`applyUpdate` 写 `data-phase` / `--update-progress`），不可删。
- **入口 B（DSH 侧栏底部「设置」触发钮 `.dcu-settings-trigger`）**：codex-ui 原生入口。
- A 依赖 B 存在（A 只是代点 B）。藏掉任一都会破坏链条或丢更新指示，**决定两个都保留**。

### 12.2 「设置页永久不可见」伪象——机理已实证，非缺陷

排查中用与外壳同语义的判据（`.dcu-settings-back` 存在 = 开）观测到一种卡死态：
页面在 DOM、back 在、外壳认为「开着」，但 `.dcu-settings-page` 计算 `opacity:0`、
且它是 `position:fixed; inset:0; z-index:1000` 的**全屏覆盖层**——视图内一切点击被它吞掉。

复现与对照（CDP 注入点击，DSH 实例 9462 / 60362）：

| 条件 | 操作（开 → 入场 ~20ms 内点返回） | 结果 |
|---|---|---|
| 视图**可见** | 同一竞态序列 | **300ms 内干净关闭**（页面卸载、back 消失）；再开正常至 opacity 1 |
| 视图**隐藏**（最小化/被完整遮挡） | 同一竞态序列 | **冻在 opacity:0**，1500ms 不解；恢复可见后**自行卸载痊愈** |

机理：codex-ui 设置页入场是 `dcu-settings-enter 180ms`（opacity 0→1，无 fill-mode），
**关闭卸载依赖 `transitionend` 事件**。视图隐藏（`visibilityState:hidden`）期间 Chromium
不产出渲染帧 ⇒ `transitionend` 不派发 ⇒ 元素滞留为不可见全屏层。渲染帧一恢复，事件补发、
页面自动卸载。**用户只能在窗口可见时点击，可见时该竞态完全正常**——此态只会在
「探针对隐藏视图注入点击」时出现，属排查工具伪象，不在便携侧修（上游实现选择 + Chromium
隐藏页事件调度固有行为）。

排查中一度误报「入口 B 点两次没反应」——当时视图正处隐藏态，全被透明覆盖层吞掉，同因。

### 12.3 探针纪律（新增）

- **禁止对 `visibilityState:hidden` 的视图注入点击做功能判定**——会制造真实用户不可能遇到的
  伪故障（本节即实例）。注入前先读 `document.visibilityState`。
- Electron 的 occlusion 判定有秒级滞后：盖住/移开遮挡窗口后 `visibilityState` 不会立即翻转，
  采样前留足等待。
- 最小化 ≠ 冻结：最小化隐藏态下入场动画的**时间线照常走完**（懒推进），冻住的只有依赖
  渲染帧的事件（transitionend/animationend）。别拿「动画走没走」判断视图死活。
